6  Running repeatable ML workflows

How can the system reproduce a multi-step ML result after partial failure, schedule delay, code change, or operator handoff? Chapter 5 established durable artifacts and rebuildable derived state. Dependency graphs replace manual command sequences with tasks that have explicit inputs, outputs, resources, retries, and evidence.

The chapter map follows one dependency graph from task definitions into scheduler state, isolated execution, guarded publication, evidence records, and shared-cluster controls.

Chapter map: repeatable ML workflows

Sections 6.1 to 6.3 turn scripts into directed acyclic graphs and task contracts. Sections 6.4 and 6.5 connect those contracts to Airflow’s scheduler, metadata, executor, and task runtimes. Sections 6.6 to 6.9 add controlled retries, guarded state publication, linked run records, reusable task blocks, and tenant controls.

6.1 From manual scripts to automated pipelines

A script can run ingestion, training, evaluation, and deployment in sequence. As the workflow grows, one process cannot reliably express parallel branches, selective retries, historical backfills, resource placement, responsibility, or persistent run state. The dependency definition does not execute the work, and task-attempt state persists across failures.

  • Pipeline: A reproducible set of tasks and dependencies that transforms versioned inputs into versioned outputs while recording execution state.

Orchestration is not the model code. It decides when a task is eligible, where it runs, how its state is recorded, and what happens after failure. The task implementation performs domain work such as preprocessing or training. The artifact store contains large outputs. The metadata store contains orchestration state and small references.

6.2 Scheduling task dependencies with directed acyclic graphs

The workflow’s responsibilities are separated. The orchestrator still needs an unambiguous rule for which tasks may run and which work can happen in parallel. Tasks are nodes, and prerequisite relationships are directed edges without cycles.

  • Directed Acyclic Graph (DAG): A graph whose directed edges encode dependency order. Its lack of cycles means that at least one topological execution order exists.

An edge A → B means B cannot start successfully until A’s required output is available. A does not directly invoke B. Independent branches can execute concurrently. A cycle leaves every node in the loop waiting, so feedback over time is represented by separate DAG runs or external events.

The completion-time bound follows directly from the dependencies. Let \(P\) be the set of all directed paths from the workflow’s start to its finish. For one path \(p\), the condition \(i \in p\) means that task \(i\) lies on that path, and \(t_i\) is that task’s elapsed duration in minutes. Tasks on one dependency path must finish in order, so the workflow cannot finish sooner than their summed durations. Taking the largest sum gives the critical-path lower bound.

This bound assumes that task durations are known estimates and enough workers are available for independent branches. It also assumes that queueing, worker startup, retries, data transfer, and resource contention do not add delay. Under those conditions, work-conserving scheduling can reach the bound. In a real cluster, those omitted delays can make the observed workflow longer, but never shorter for the same dependencies and task durations.

\[ T_{\mathrm{DAG}} \ge \max_{p \in P} \sum_{i \in p} t_i \tag{6.1}\]

Critical path calculation: scheduling duration in a branched DAG

Summing task durations along the longest dependency chain determines the minimum workflow completion time under the stated assumptions:

  • Shared start: Validation takes 4 minutes.
  • Training branch: Training takes 38 minutes and model evaluation takes 8 minutes.
  • Retrieval branch: Embedding takes 20 minutes and index validation takes 6 minutes.
  • Shared release: The promotion gate takes 3 minutes after both branches finish.
  • Training path: Validation → training → model evaluation → promotion takes \(4 + 38 + 8 + 3 = 53\) minutes.
  • Retrieval path: Validation → embedding → index validation → promotion takes \(4 + 20 + 6 + 3 = 33\) minutes.
  • Conclusion: The 53-minute training path controls the lower bound. Accelerating the 33-minute branch alone cannot reduce end-to-end time below 53 minutes.

The compact relationship is also listed in Appendix A, with this section as its full explanation.

Workflow analysis: critical path scheduling implications

Identifying workflow bottleneck dependencies directs pipeline optimization efforts:

  • Doubling workers does not accelerate a strictly serial chain. Only changes to tasks on the critical path reduce the completion-time lower bound.
  • A slow off-path task can still consume capacity and delay later runs, so capacity and critical-path analysis remain separate.

6.3 Defining immutable task inputs and outputs

The DAG states dependency order. A box named ‘train’ is still too vague to retry safely or reproduce after an image, dataset, or configuration changes. Every task has immutable inputs, explicit outputs, resource needs, failure behavior, and validation.

  • Task specification: The complete contract for one pipeline task: identity, immutable inputs, outputs, runtime, resources, retry behavior, validation, and side effects.

  • Idempotent task: A task whose repeated execution with the same declared inputs reaches the same externally visible result without corrupting state or duplicating effects.

Named task fields make repeatability inspectable by both the scheduler and the next task.

Large objects bypass the orchestration metadata database and inter-task message fields. The artifact store holds them, while tasks pass a small immutable reference plus integrity metadata. Each task writes to a unique attempt or generation path, validates its output, and publishes a completion pointer only after success.

6.4 Coordinating workflow runs with Airflow

Task descriptions make the DAG specific enough to operate. A concrete orchestrator still needs components that parse definitions, create runs, choose ready tasks, launch executors, and expose state. Airflow’s components map to those responsibilities around the DAG file.

The component map assigns each Airflow process one control-plane responsibility before the implementation example.

The UI is a view of persisted state, not the execution engine. A green task instance means the operator’s success criteria ran without error. It does not automatically prove that the produced model is good. Domain validation belongs inside task descriptions and release gates.

6.5 Running complete ML workflows in Airflow

The control-plane roles and task description are explicit. The Python definition describes dependencies without performing expensive work during import. Lightweight DAG parsing leaves domain code to isolated task runtimes.

The following abbreviated Python example targets the Apache Airflow 3 DAG interface and its CNCF Kubernetes provider. The Airflow deployment must pin the exact orchestrator and provider versions. PIPELINE_IMAGE pins the domain application and its libraries. The other uppercase names are immutable manifest or configuration identities supplied by the deployment. Importing the file creates a DAG definition. A run then creates task-instance and attempt records in Airflow’s metadata database, while each pod writes domain artifacts to the external artifact store.

Code example: Abbreviated Airflow DAG that passes immutable artifact identities into isolated Kubernetes tasks and applies bounded retries with exponential backoff.


from airflow import DAG
from airflow.providers.cncf.kubernetes.operators.pod import KubernetesPodOperator
from datetime import datetime, timedelta

TASK_RETRY_POLICY = {
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=30),
}

with DAG(
    dag_id="versioned_rag_release",
    start_date=datetime(2026, 1, 1),
    schedule=None,
    catchup=False,
    max_active_runs=1,
    default_args=TASK_RETRY_POLICY,
    tags=["mlops", "rag"],
) as dag:
    validate = KubernetesPodOperator(
        task_id="validate_sources",
        image=PIPELINE_IMAGE,
        cmds=["python", "-m", "pipeline.validate"],
        arguments=["--manifest", DATASET_MANIFEST],
    )
    embed = KubernetesPodOperator(
        task_id="build_embeddings",
        image=PIPELINE_IMAGE,
        cmds=["python", "-m", "pipeline.embed"],
        arguments=["--manifest", DATASET_MANIFEST,
                   "--embedding-version", EMBEDDING_VERSION],
    )
    evaluate = KubernetesPodOperator(
        task_id="evaluate_retrieval",
        image=PIPELINE_IMAGE,
        cmds=["python", "-m", "pipeline.evaluate"],
        arguments=["--suite", EVAL_SUITE, "--candidate", COLLECTION_ID],
    )

    validate >> embed >> evaluate

Code walkthrough: Airflow DAG with bounded retry policy

Declarative pipeline definitions specify idempotent task execution and failure recovery:

  • DAG definition: The DAG object stores scheduling and concurrency policy. schedule=None makes run creation externally triggered.
  • Concurrency guard: max_active_runs=1 keeps only one run of this DAG active. It reduces overlap but does not make external side effects safe by itself.
  • Retry policy: retries=2 permits two retries after the initial attempt. The configured base retry delay is 5 minutes. Exponential backoff increases later delays up to a 30-minute cap, and scheduler jitter can shift the observed timing.
  • Task runtime: Each KubernetesPodOperator launches domain work in the immutable pipeline image after DAG import.
  • Artifact lineage: Task arguments carry dataset, embedding, evaluation-suite, and candidate-collection identities.
  • Dependency state: The shift operators create validation → embedding → evaluation edges. Airflow records each task instance and attempt.
  • Result: The scheduler owns eligibility and task state, while isolated containers own validation, embedding, and evaluation work.
  • Limits: This example retries every task failure reported to Airflow. It does not classify permanent schema or policy failures, define output manifests, configure secrets and service accounts, request resources, send alerts, or promote an alias. A production DAG needs those controls and a separate gated promotion task. The task commands must tolerate repeated execution as described in Section 6.6.

Orchestration principle: DAG import performance safeguards

Maintaining lightweight DAG definitions protects orchestrator scheduler performance:

  • Import-time dataset downloads, GPU initialization, external API calls, and large namespace scans slow parsing and can make scheduler health depend on external systems.
  • The scheduler repeatedly parses DAG files. Expensive or unreliable import-time work slows the control plane and can make every DAG appear broken.

6.6 Controlled re-execution and idempotent tasks

The example DAG can launch isolated tasks. Retries and historical runs will repeat code, so ambiguous partitions and irreversible side effects can duplicate or overwrite production state. Each run is bound to a logical data interval or immutable release identity, while computation and promotion remain separate.

Retries distinguish transient infrastructure failures from deterministic code or data failures. Exponential backoff helps a temporary dependency recover. It does not fix a schema mismatch. After the retry budget, the task state, relevant logs, input identities, and responsible component remain visible without reconstructing the run from a terminal.

Idempotency walkthrough: partition task retry without duplicate writes

Attempt-scoped writes plus a conditional publication step keep incomplete or late attempts from replacing accepted state:

  • Starting state: The committed pointer for partition 07 names generation g19. The coordinator records g19 as the expected current value for this task run.
  • Attempt 1: Partition 07 writes generation g20-a1 to an attempt-scoped path, loses its worker, and never receives permission to publish.
  • Eligibility: The scheduler classifies the failure as transient and retries the same logical interval and input manifest.
  • Attempt 2: The task writes g20-a2, validates row counts and hashes, and emits a completion record keyed by task, interval, input identity, and attempt.
  • Guarded publication: The coordinator conditionally changes the pointer from expected value g19 to g20-a2. The update fails if another coordinator has already changed the pointer.
  • Late completion: Attempt 1 still lacks a valid publication token. A conditional write that expects g19 also fails after g20-a2 is visible, so cleanup can remove g20-a1 without affecting readers.
  • Conclusion: This staged write uses conditional publication to protect state behind one pointer. It does not coordinate a distributed transaction among several independent services, as a two-phase commit protocol would. External notifications, billing calls, or other side effects still need their own idempotency keys or transactions.

6.7 Building reusable task templates

Retry behavior and conditional artifact publication now have explicit controls. Teams still lose consistency when every DAG reimplements data validation, distributed training, inference, evaluation, and registration differently. Parameterized task blocks package common responsibilities through stable inputs, outputs, checks, and platform defaults.

Each reusable block has named inputs, committed outputs, and validation checks.

A reusable block standardizes identity, evidence, secrets, resource requests, telemetry, and output publication while allowing task-specific domain parameters. This division lets model developers change the architecture without reimplementing cluster scheduling or artifact lineage.

6.8 Recording artifact evidence in run manifests

The pipeline can produce versioned artifacts through reusable blocks. The orchestrator, experiment tracker, and telemetry backend record overlapping facts. Copying all data into every system obscures the authoritative record. Each evidence class has one primary system, and stable identifiers connect the records.

A pipeline task can start an experiment run and emit its ID. The tracker records comparable parameters and metrics. The task publishes artifact URIs and commits its status. A later deployment writes the serving-bundle ID into traces. The same identifiers let an incident move backward from one request to its bundle, evaluation report, experiment, DAG run, and source artifacts.

Architecture boundary: authority mapping across systems

Partitioning state authority across platform systems prevents metadata divergence:

  • The orchestrator is authoritative for task attempts and dependency state. The experiment tracker is authoritative for comparable parameters and metrics. The artifact registry is authoritative for immutable files and promotion aliases. Telemetry is authoritative for runtime observations, and the evaluation store is authoritative for cases and raw judgments.
  • Cross-links join these records without copying one system’s mutable state into another. A run manifest records the identifiers and the producer or consumer relationship.

6.9 Isolating teams on shared research clusters

One pipeline has clear responsibilities and evidence. A research organization adds concurrent users, shared clusters, queues, secrets, quotas, interactive work, long-running training, and repeated evaluation. Code, compute, storage, observability, orchestration, and experiment systems collaborate while retaining distinct roles.

A shared research platform combines Git-hosted code, containerized workloads, Kubernetes scheduling, shared and object storage, telemetry, pipeline control, and experiment tracking. Interactive work and scheduled jobs can use the same immutable images and artifact identities, allowing an exploratory result to become a repeatable run.

Reinforcement learning separates experience collection from parameter updates. An actor consumes an environment observation and a fixed policy version, chooses actions, and produces a trajectory containing observations, actions, and rewards for one rollout. A learner consumes batches of those trajectories, calculates the training objective, updates model parameters, and publishes a new policy checkpoint. The workflow records the policy version on each trajectory so learner results can be traced back to the actors that generated their input.

The source dashboard below focuses on trajectory handlers, the actor-side workers that collect and group experience. Its visible panels show active handlers, spawned and completed handler counts, accepted and rejected groups, event-loop blocking time, and shared training-step counters.

The dashboard shows whether experience collection is keeping up and whether generated groups are usable. A complete reinforcement-learning view also needs measurements from the learner: batches consumed, update time, loss, GPU use, and checkpoint progress. It also records the lag between the newest policy and the version used by actors. Reward and sample-efficiency measurements describe the result across both sides. A queue can grow when actors outpace the learner, when the learner cannot process a batch, or when validation rejects trajectories. The same run, policy, trajectory, and checkpoint identities connect those explanations.

Tenant boundary

  • A shared cluster needs separate namespaces or projects, resource quotas, queue limits, service accounts, network policy, and storage prefixes for each team or trust domain.
  • Run and artifact identities remain globally traceable, while payload access follows tenant policy. A scheduler quota alone does not prevent one team from reading another team’s checkpoints or traces.

Chapter 6 summary

  • Core mechanisms: Declarative Airflow DAGs, isolated task execution, bounded retries, idempotent task design, conditional publication, and linked run records.
  • Governing tradeoffs: Fine-grained task isolation adds overhead but improves failure localization. Shared clusters raise utilization but require tenant controls across compute, identity, network, storage, and telemetry.
  • Failure controls: Immutable artifact identities, attempt-scoped writes, guarded pointer updates, quotas, queue limits, and explicit access policy keep a retry or one tenant from silently changing another result.
