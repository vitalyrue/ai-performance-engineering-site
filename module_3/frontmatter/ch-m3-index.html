Introduction: The Operating Problem

A model can be impressive in an isolated experiment and still fail as a product. Production introduces traffic, failures, shared resources, changing data, delayed feedback about correctness, cost limits, and deployment risk. When a result changes or a job fails, the team also needs to know which code, data, model, and settings produced it. Together, these constraints turn a one-time result into a system whose behavior and changes the team can explain.

The supporting systems store model versions, allocate compute, handle requests, and record what happened. Their design depends on the workload. A service can use a pretrained model without running its own training job. Training or adaptation becomes relevant when the existing model does not meet the task’s needs.

The running case: A grounded-answer service

Suppose a company offers its employees a question-answering service over internal policy documents. A typical question is how many remote-work days a contractor may take. The application checks which documents this employee may read, retrieves relevant passages from the current policies, and supplies the question and passages to a large language model (LLM), a model that generates text from the supplied input. The application returns an answer with citations to the passages it used. Policies change weekly, so the service must answer from documents that the model never saw during training.

  • Retrieval-augmented generation (RAG): A design in which the application retrieves passages from a document collection at request time and supplies them to the model as context for generating the answer.1

  • Groundedness: The degree to which every claim in an answer is supported by the passages supplied to the model. A grounded answer can still be wrong if the supplied passage is outdated or incorrect.2

  • Hallucination: Generated content that the supplied evidence does not support or that contradicts it, such as an answer stating a renewal date that appears in no retrieved passage.3

The model has different roles in three operating modes. In inference, the serving system turns a question and passages into an answer using the model’s learned numerical settings. Each adjustable setting is a parameter (weight). In training, a job compares model predictions with target outputs and updates those weights. In evaluation, a job scores answers against reference labels or evidence and records a verdict without changing any weights.

Scope boundaries

The starting knowledge is basic programming, familiarity with code and data files, and arithmetic with rates and percentages. The reader can recognize a trained model but need not know how training clusters, serving engines, vector search, or workflow systems operate. Those ideas are explained where they are used.

The book focuses on the systems around a model: allocating compute, moving and storing data, scheduling requests, finding relevant passages, measuring performance and answer quality, and checking releases. Low-level GPU kernel authoring, proprietary hardware compilation, and model architecture design are outside its scope. Software products illustrate component roles. They are not required purchases or a prescribed deployment stack.

Sources and acknowledgment

This book combines research papers with standards and software documentation. Five core papers support these explanations:

  • The ML Test Score (2017) for testing, monitoring, and release checks in Chapters 4, 7, and 9.4
  • The ZeRO paper (2020) for training memory and communication calculations in Chapter 2.5
  • Retrieval-Augmented Generation (NeurIPS 2020) for the retrieval-and-generation design of the running case.6
  • The PagedAttention paper (SOSP 2023) for Chapter 4’s explanation of how serving systems manage memory while generating answers.7
  • The TFX paper (KDD 2017) for coordinated steps and shared services in Chapter 8’s machine learning workflows.8

Chapter 4 also uses the SGLang paper (NeurIPS 2024) to explain reuse of earlier computation for requests with the same opening text.9 It uses Fast Inference from Transformers via Speculative Decoding (ICML 2023) to explain drafting text with a smaller model and checking it with a larger one.10

Standards and product documentation support the details about software behavior and data formats.

The book was inspired by Nebius Academy’s AI Performance Engineering course.11

Nine operating stages and handoffs

The book follows nine operating stages in three parts. Making training runs repeatable and recoverable (Part I, Chapters 1–3) establishes run identity, shared training work, and recoverable state. Serving answers and assessing their quality (Part II, Chapters 4–7) connects serving and retrieval to request evidence and quality evaluation. Running and improving the complete system (Part III, Chapters 8–9) connects repeatable workflows to incident diagnosis and release checks.

System map

Versioned model files enter serving, while retrieval supplies authorized source passages for each answer. Request traces connect the operations to their release identities. Experiment and evaluation records support a proposed change, and workflow records identify the tasks and inputs that built it. Production measurements guide investigation, and a diagnosed incident becomes a regression case for later evaluation and workflow runs.

Learning path

Chapters 1–3 explain how to identify a run, share its training work, and recover its data and saved state. Chapters 4–7 connect serving and retrieval to request records and quality evaluation. Chapters 8–9 use those results in repeatable workflows and a complete incident investigation.
