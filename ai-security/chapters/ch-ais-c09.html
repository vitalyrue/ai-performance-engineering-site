9  Contain runtime exposure

A runtime exposure analysis follows the identities, interfaces, networks, secrets, and resource limits that determine whether a running AI workload can be reached or abused.

Security question. How can a service intended to run legitimate jobs become an entry point for an attacker?

Reference frame. The reference setting is an organization-operated job service beneath the model laboratory or internal-model application. The reference configuration remains separate from an incident investigation and distinguishes exposed capability from confirmed compromise.

Platform responsibilities become concrete at runtime through interfaces, workload identities, networks, secrets, processes, and resource limits. These controls also bound later tool execution and provide evidence for monitoring.

9.1 Deployment interface exposure

A runtime cannot be contained until every reachable control surface is known. A deployment interface accepts commands or configuration for workloads. An administrative endpoint can change platform state. A job-submission API accepts work and parameters for execution.

NIST’s container guide treats orchestrators and runtime interfaces as high-value control surfaces and identifies unbounded administrative access as an orchestrator risk.1 Kubernetes guidance states that kubelet application programming interface access should be restricted and not exposed publicly.2

The organization enumerates notebook servers, model endpoints, schedulers, orchestration interfaces, management consoles, and health or metrics endpoints. It records network reachability and permitted operations for each. Product-specific checks remain necessary because the packet lacks primary documentation for the selected notebook, scheduler, and model server. Each permitted call path now needs a workload identity.

Example

Concrete interface review (hypothetical). The operating mode is deployment review. The task is to find which interfaces can start or change a model-serving job. The reviewer begins with the service inventory and an external network test.

The intermediate record shows that admin-ui is reachable from outside the intended boundary even though no login was attempted. The conclusion is limited: the route is an exposure that requires removal or a justified access path. It is not evidence that an attacker authenticated or changed state. The values and interface names are hypothetical.

The gateway and network policy enforce the interface decision by checking caller identity, source network, requested operation, and endpoint. The test reports unexpected reachable interfaces over all inventoried interfaces from each tested network. Restricting administration adds access setup and can delay urgent maintenance. An omitted endpoint or alternate route can bypass the result. Recovery removes the route and rotates exposed credentials. After the full inventory test runs again, a zero count shows only that the listed interfaces were unreachable from the tested locations.

9.2 Workload identities and secrets

Shared credentials make it difficult to limit or attribute service actions. A workload identity identifies a non-human process or service. A service account is one way to give a workload such an identity. Token lifetime is the period for which a credential can authorize requests.

Kubernetes service accounts provide workload identities and can be bound to permissions through role-based access control (RBAC).3 NIST’s cloud-native zero-trust model recommends short-lived, cryptographically verifiable service identities and service-to-service authorization.4

The runtime binds each interface call to a workload identity and checks its role. Short-lived credentials arrive through a controlled mount or exchange, whose identity mechanism still depends on narrow permissions and safe token handling. Those identities must also govern network and service boundaries.

Example

Concrete identity trace (hypothetical). The operating mode is job execution. An employee submits a request to evaluate a test set. The application creates job job-417 and requests a token for the worker.

  1. The token record states subject eval-worker, audience job-api, scope jobs:read,results:write, and an expiry 15 minutes after issue.
  2. job-api accepts the token and starts job-417 because its audience and jobs:read scope match the call.
  3. The same worker presents the token to model-admin. That service rejects it because the audience differs and the token has no configuration scope.

The observed result is one accepted task call and one denied administrative call. The conclusion is that the token limits this trace to the intended service and operations. It does not establish that the credential cannot be stolen or that every service validates it correctly. All identifiers and times are hypothetical.

Each receiving service enforces this boundary by checking token subject, audience, scope, expiry, and revocation state before the operation. The test denominator is all attempted service-operation pairs in the identity matrix. Short token lifetimes add issuance traffic and can interrupt work during identity-service failure. A stolen token or a service that skips one check can bypass the design. Recovery revokes the identity and rotates related secrets. After active sessions end, both allowed and denied calls run again. The result covers only the services in that test.

9.3 Network exposure controls

A workload identity has limited value if traffic can bypass the enforcement point. Ingress enters a service boundary, while egress leaves it. Control traffic changes system state or configuration. Data traffic carries prompts, model inputs, outputs, or stored records.

NIST SP 800-207A places cloud-native access policy around application and service identities, with gateways or proxies enforcing identity and network policy.5 NIST container guidance recommends egress control and application-aware filtering where changing addresses limit traditional network rules.6

The organization maps each required flow to a source identity, destination, protocol, and purpose. Enforcement then denies flows outside that map and records decisions. These sources provide architecture guidance, not proof that a proxy or policy cannot be bypassed. The next section assumes one permitted interface is reached and limits what its process can affect.

Example

Concrete network trace (hypothetical). The operating mode is model evaluation. The worker must read a test object and call an internal model endpoint. It must then write a result. The approved flow record contains those destinations and denies other egress.

The unexpected fourth connection changes the review. Its blocked result demonstrates enforcement in the tested path without identifying why the process tried to connect or whether alternate routes are closed. The addresses and identifiers are hypothetical.

The egress gateway enforces the flow map by checking workload identity, destination, protocol, and port. The test reports denied unexpected flows over all attempted flows and separately verifies every required flow. Narrow rules require more policy work and can break jobs when legitimate destinations change. Domain Name System (DNS) changes, proxy paths, or another network interface can bypass an incomplete map. Recovery stops the workload and blocks the observed route. After credential review, the flow matrix runs again. Its result covers only attempted destinations.

9.4 Runtime execution isolation

A submitted job may process hostile input or execute untrusted code, so its host access must be bounded. Execution isolation limits the processes, files, devices, memory, and network resources a workload can affect. A host mount exposes host storage inside a workload. A privilege is an allowed operation that exceeds ordinary process access.

NIST identifies container risks from insecure defaults, excessive privileges, host file access, runtime vulnerabilities, and shared-kernel exposure.7 It recommends separating workloads by sensitivity and constraining privileges, host access, and network access.8

Isolation starts with a restricted user and limited capabilities. Approved mounts, device access, network policy, and resource limits further reduce paths without proving complete containment, especially with a shared kernel. Long-running protection also depends on maintenance and resource controls.

Example

Concrete isolation test (hypothetical). The operating mode is execution of generated analysis code. The task input is a synthetic script that reads the mounted repository, attempts to read /host-secret, and then tries to create a privileged process. The reference policy allows read access only to /workspace and ordinary processes.

The worker record shows /workspace/input.csv opened successfully. The file-open event for /host-secret returns access denied. The process request that asks for an added privilege is also denied, and the job exits after writing its ordinary result. The conclusion is that the tested mount and privilege controls enforced the reference policy for these two attempts. It is not evidence that the shared kernel or runtime has no other escape path. The paths and result are hypothetical.

The runtime and host policy enforce this boundary by checking the process identity, requested path, capability, device, and resource limit. The denominator is the complete set of allowed and forbidden operations in the isolation test. Stronger isolation consumes more memory and startup time and can limit accelerator access. A runtime flaw, unsafe device mapping, or untested host interface can bypass the tested rules. Recovery terminates the workload and preserves its events. The affected runtime or host is replaced before the matrix runs again, and passing results cover only the attempted escape paths.

9.5 Runtime limits and maintenance

An accepted runtime can become exposed as software and workloads change. A runtime patch updates execution software to correct a defect. A resource quota limits consumable compute, memory, storage, or concurrent work. Runaway computation continues beyond the intended cost or time.

NIST recommends monitoring container runtimes for vulnerabilities and remediating findings. It also recommends blocking deployment to unmaintained runtimes.9 NCSC guidance recommends monitoring behavior and treating changes to data, models, prompts, or software as updates that need testing and version handling.10

Common practice combines an approved runtime version with vulnerability response, job timeouts, quotas, concurrency limits, and billing alerts, while the worked deployment uses product documentation and direct tests for accelerator or scheduler limits that the packet does not support. These controls and logs provide the expected baseline for an incident trace.

Example

Concrete resource test (hypothetical). The operating mode is batch inference. A test job intentionally requests repeated generation without a stopping condition. Its reference limits are 10 minutes, 8 GB of memory, and 2 concurrent workers.

At minute 6 the job uses 7.4 GB. At minute 8 a request for a third worker is denied. At minute 10 the scheduler stops the remaining processes and records limit=time. The result is a bounded failed job rather than completion. The conclusion is that the configured time and concurrency controls stopped this test. The values are hypothetical, and they do not establish suitable limits for a real model or accelerator.

The scheduler enforces quotas by reading the job identity, requested resources, current use, elapsed time, and concurrency state before admitting more work or stopping it. The test reports stopped over-limit jobs over all intentionally over-limit jobs and clean completions over all ordinary cases. Tight limits reduce cost exposure but can reject legitimate long work. An unmetered service or work split across identities can bypass a local quota. Recovery cancels related jobs and reconciles usage with billing records. After any justified limit change, both groups run again under the revised threshold, whose result does not establish safe limits for a different workload.

9.6 Runtime exposure incident

An exposed endpoint is evidence of reachable capability, not proof of every later action. Execution exposure is an interface condition that permits unauthorized or unsafe execution. Propagation is movement from the first affected workload to another system. Attribution evidence supports a conclusion about who caused an event and with what confidence.

NCSC guidance recommends logging inputs and monitoring behavior to support audit, investigation, and remediation.11 NIST identifies the misuse of a container in its container security guide to attack other containers, hosts, or systems as a risk class.12

A hypothetical investigation starts with the exposed route and then orders authentication records, request logs, workload creation, process events, credential use, network flows, and resource consumption by time. Missing telemetry leaves a gap rather than evidence of absence. The packet lacks a primary incident report with enough detail for instruction based on a real event. This trace remains hypothetical, and claims about a public event are outside its scope. Chapter 10 carries untrusted runtime and tool output into the instruction and data boundary.

The incident route is contained by the gateway, identity service, scheduler, and network controls according to the affected path. Responders measure confirmed blocked paths over all observed execution paths and record every path for which evidence is missing. Isolation and credential rotation interrupt work and can destroy volatile evidence if ordered poorly. An unknown credential or unlogged route can leave access in place. Recovery preserves volatile state and removes public reachability before credentials are revoked. The worker is then rebuilt and the original attempts replayed. A clean replay does not establish attribution or exclude activity outside the recorded window.

Note

Chapter checkpoint. A hypothetical review finds an internet-reachable administration page, a shared worker credential, unrestricted egress, a host filesystem mount, and no job timeout. Which records and changes would show that the runtime is contained for an evaluation job?

Answer. Record the intended caller and permitted operation for every interface, then remove the public route or place it behind an approved access path. Give the evaluation worker a short-lived identity limited to the job and result services. Allow only the required storage and model flows, remove the host mount, and set tested time, memory, and concurrency limits. Repeat the interface, identity, network, isolation, and resource traces and retain each allow or deny result. Passing those checks supports only the tested configuration. It does not prove that the runtime has no unknown vulnerability or alternate route.
