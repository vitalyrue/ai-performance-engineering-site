18  Using AI safely in defense

This chapter applies the book’s safeguards to a security team’s own AI assistant, keeping human judgment and action authority visible while measuring useful work.

Security question. When does AI improve security work without creating unacceptable new errors or access?

Reference frame. Use a defensive analyst assistant that reads synthetic alerts and intelligence documents through an external model and retrieval application. Add response proposals first and execution only with specified permissions and oversight.

Connection through the book. Chapter 17 separated a demonstrated capability from observed use and measured effect for attacker assistance. This chapter applies the same evidence discipline to a defensive assistant. It also applies the retrieval, authorization, evaluation, and recovery controls already taught. Chapter 19 compares implementations of this fixed task.

18.1 Alert triage

An AI assistant can help an analyst connect related events and draft an alert summary, but the summary must preserve the evidence needed to check it. Inputs include normalized events, identity and asset context, prior activity, and the rule that produced the alert. Evaluation counts missed incidents, unsupported statements, correction work, and analyst time as well as apparent speed.

The NIST incident-response profile calls for analysis and correlation of detected events before responders place them in context and route them.1 It also calls for validation and categorization of reports before prioritization and response.[^c18-s01-respond] The profile does not evaluate AI summaries or define how they should express uncertainty.

In the hypothetical workflow, the assistant links each summary sentence to event identifiers and marks missing context. The analyst can inspect the source events before accepting a priority or incident declaration. A baseline compares the same alert set without the assistant. Strong field evidence for AI-assisted triage quality, time, correction, and missed incidents remains unavailable. The evidence-display rule carries into investigation and threat intelligence.

Control review. The triage application checks whether each summary statement includes an event identifier and whether the analyst accepted the priority. It withholds an incident declaration when either check fails. The test reports unsupported statements and missed incidents over all alerts in the fixed set, together with analyst minutes per accepted alert. Source linking and review add latency. They can still fail when the event store is incomplete or the analyst accepts a weak summary. Recovery returns the alert to the ordinary queue and preserves the draft, correction, and source events. This evidence supports the tested alert population only.

18.2 Threat intelligence and investigation

Investigation moves from observations to explanations. An observation records something seen. An indicator describes a pattern that may support detection or assessment. The assistant can retrieve reports and connect objects, but it must preserve external references, versions, confidence, and competing explanations so that the analyst can inspect the basis of a conclusion.

Structured Threat Information Expression (STIX) 2.1 separates observations, indicators, relationships, external references, confidence, and object versions in a structured threat-intelligence model.[^c18-s02-stix] STIX also defines confidence as a common property and provides example scales.[^c18-s02-confidence] The schema can carry evidence and confidence. It cannot make the assistant’s inference correct.

The hypothetical assistant produces a claim, supporting observation identifiers, external references, confidence method, and at least one plausible alternative when the evidence permits. A confidence number without a method remains a label. Version links show when a report changed. This source-linked record supports later vulnerability and development decisions without hiding uncertainty.

Control review. The investigation workspace checks for a source identifier, source version, confidence method, and review status before a claim enters a case record. It accepts, returns, or marks the claim unresolved. A test counts complete claim records over all assistant claims and separately counts accepted claims later corrected. The check costs analyst time and storage. Copied text that enters another system without its record can bypass the check, while even an attached record does not establish a claim as true. Recovery withdraws the claim and restores the earlier case state. Affected analysts receive an alert.

18.3 Vulnerability and development work

For vulnerability and development work, the assistant may explain a finding or inspect dependency data. It may also draft a patch or propose a test. The security decision still depends on the real code, build, deployment conditions, and authorization for testing. A generated fix needs review and execution evidence rather than acceptance based on a plausible explanation.

The NIST Secure Software Development Framework calls for verification of third-party components, code review, executable-code testing, and triage of results.[^c18-s03-ssdf] Pearce and colleagues found vulnerable suggestions in some scenarios tested with an early GitHub Copilot version.[^c18-s03-pearce] That finding does not transfer automatically to later models or workflows with independent review.

The organization links the assistant’s recommendation to the finding, dependency identity, generated diff, authorized test environment, test output, reviewer, and deployment result. Production testing requires separate permission. A rejected suggestion remains part of evaluation evidence because it contributes to correction cost. These records separate recommendation quality from the authority to act.

Control review. The change pipeline checks the finding identifier, repository revision, test-environment authorization, reviewer decision, and required test result before allowing a merge or deployment. It blocks incomplete or failed candidates. Evaluation reports accepted fixes, rejected fixes, and later regressions over all submitted suggestions, plus review minutes per accepted fix. The gate delays delivery and can miss a defect outside the test set. Because the gate covers only the tested deployment conditions, recovery reverts to the recorded accepted revision and revokes temporary test access.

18.4 Analyst and automation roles

The assistant’s role can range from summary to constrained execution. A suggested action tells the analyst what could be done. A drafted action prepares exact arguments for review. Constrained execution runs only an authorized operation within fixed limits. Escalation transfers the decision and evidence to a person or service with the required authority.

Least privilege and complete mediation support granting only task-specific rights and checking access when the protected object is used.[^c18-s04-saltzer] MCP recommends making exposed tools visible to users and preserving their ability to deny an invocation.[^c18-s04-mcp] These principles do not identify the best division of labor or measure the quality of human approval.

The hypothetical assistant may query read-only telemetry and draft a host-isolation request. A separate service resolves the host and checks policy. Before execution, it displays the effect and records approval. Recovery tests cover an incorrect recommendation and a partial action. Controlled comparisons of analyst-only, assistant-only, and combined workflows remain an evidence gap. This authority map defines what an attacker could misuse.

Control review. The action service enforces the boundary by checking the analyst identity, target host, requested operation, approval, and current incident state. It allows only the approved action or returns a denial. Tests count unauthorized and incorrectly completed actions over all attempted actions, including partial failures. Approval adds delay, while constrained execution adds engineering and support cost. A stale approval or alternate management interface can bypass the intended path. The test does not measure whether the recommendation itself was correct. Recovery cancels pending work and restores the host where possible, while irreversible effects receive escalation.

18.5 Attacks on the defensive assistant

A defensive assistant consumes attacker-influenced material by design. Logs, tickets, repositories, malware reports, and intelligence documents can contain instructions or data crafted to influence its output. The resulting risk depends on sensitive telemetry, retrieval access, tool permissions, and retained memory available to the assistant.

Greshake and colleagues demonstrated indirect prompt injection through external content and effects on connected actions in selected systems.[^c18-s05-greshake] OWASP’s 2026 description includes tool output, retrieved content, and persistent memory as prompt-injection paths and links impact to available functions and permissions.[^c18-s05-owasp] These demonstrations establish selected attack paths, but they do not prove that a current security assistant is vulnerable or that a proposed control works.

A hypothetical test places a hostile instruction in a synthetic ticket that the assistant must summarize. The trace follows retrieval, context, response, proposed tools, and policy decisions. The expected result is an evidence-linked summary with no unauthorized query or action. This test counts failures alongside useful work when the organization measures operational value.

Control review. The retrieval application limits eligible records, and the action service checks every proposed operation independently of model text. The test denominator is all hostile tickets replayed under the specified identities and permissions. It reports summaries changed by hostile text, restricted records returned, and actions allowed. Filtering and independent authorization consume compute and review time. Encoded instructions, a compromised connector, or an unmediated tool path can defeat parts of the design. Recovery removes the ticket from active context and revokes affected credentials. It then restores the accepted configuration and retests the same cases. A clean run does not cover unseen instruction forms.

18.6 Operational value

Operational value is the measured benefit of the assistant after errors, correction work, review, security controls, privacy effects, and total operating cost are included. A fair comparison uses the same alert or investigation workload and a human or deterministic baseline. Quality measures depend on the decision, such as correct triage, supported findings, or safe completion.

The AI RMF MEASURE function calls for documented methods, metrics, test sets, limitations, human review, and monitoring.[^c18-s06-rmf] NIST AI 800-3 says the evaluation target should match the decision and separates item variation from repeated-trial variation.[^c18-s06-8003] The publications do not supply an operational-value result for a security assistant.

The organization reports how often the task succeeds, how much analyst time and correction it requires, which incidents are missed, which consequential errors remain, and what the system and its review cost. Sampling and uncertainty belong in the same report because faster summaries do not justify deployment when they hide missed incidents or create unsafe actions. A strong field study that combines these measures is still needed. Chapter 19 uses this measured task and boundary to compare deployment options.

Operating fallback. The service owner operates a deterministic severity queue and documents an analyst-only path for the same alert population. During a continuity test, the record shows alerts processed through each fallback over all alerts received during the outage, time to first usable result, and unresolved backlog at restoration. Maintaining parallel rules and analyst capacity raises ongoing cost. A fallback can fail when source systems are unavailable or staff capacity is exhausted. Because one exercise does not establish capacity for a longer or broader disruption, recovery returns work in priority order and reconciles duplicate decisions.

Controlled comparison. This hypothetical evaluation runs in evaluation mode. It does not update model parameters or permit an external action. The task is to prioritize 120 synthetic alerts drawn from 12 incident stories. Senior analysts establish the reference priority and supporting event identifiers before the comparison. Each method receives the same alerts, identity context, time limit, and read-only access.

All values are exercise values, not measured findings. The intermediate record for the combined method contains the assistant summary, cited event identifiers, analyst correction, and final priority. In this example, the combined method saves 120 analyst minutes compared with the analyst-only method and has one fewer consequential error. The fourteen corrected drafts show why accepted output alone is an incomplete measure. The result supports a limited pilot under the tested read-only conditions. It does not support autonomous response or transfer to a different alert population.

Note

Chapter checkpoint. Does the lower analyst time for the combined method justify giving the assistant permission to isolate hosts?

Answer. No. The evaluation measured read-only triage under analyst control. Host isolation changes external state and can interrupt service. That operating mode needs a separate authorization path, action tests, recovery tests, and evidence about harmful interventions. The comparison supports only the task and permissions that were tested.

The chapter retains explicit evidence gaps for triage outcomes, analyst and assistant roles, and full operating cost.
