19  Choose a viable deployment

A deployment comparison fixes task, data access, quality target, action limits, and full operating cost before comparing external, managed, and internal models.

Security question. Which combination of model, hosting, and controls fits a specified security task?

Reference frame. The comparison runs the same defensive task and organization workload under explicitly described external-model and internal-model configurations. Data access, allowed actions, quality targets, and oversight requirements remain constant where possible.

A useful defensive task can run through an external service, a managed platform, or an internal model. A fair comparison holds the task and permissions constant while examining rights, duties, quality, cost, and operating constraints.

19.1 Deployment rights and duties

A deployment label leaves inspection rights and operating duties unclear. A hosted model service provides model access through a supplier-operated interface. A self-hosted model deployment runs model software that loads specified weights on infrastructure operated or controlled by the adopting organization. Access to the weights, license rights, runtime control, dependencies, and update duties remain separate facts.

Modification rights are permissions granted by a license or contract to alter and reuse supplied material. The Open Source Initiative definition goes further than access to model weights: it requires freedom to use, study, modify, and share an AI system, together with access to the preferred form for modification.1 This definition does not classify every downloadable model or settle how a license applies in a license dispute.

Security also depends on the operator who patches the runtime and controls the network. Incident handling and failure inspection add separate duties. International secure-design guidance treats model choice as a comparison across security, privacy, performance, and transparency, without ranking one hosting arrangement as generally best.2 These rights and duties define the feasible choices for the intervention comparison that follows.

Rights trace. The hypothetical organization compares a hosted service with a self-hosted deployment for the Chapter 18 triage task. The input is redacted alert text. The target is a cited priority recommendation. Neither option may execute a response. The hosted service contract permits use through its interface but does not provide model weights. The self-hosted option permits local runtime inspection and modification under its selected license, while the organization assumes patching and recovery duties. The observed result is a deployment record with two field pairs: operating control and access to weights, followed by modification rights and update responsibility. The conclusion is that the words hosted and self-hosted do not answer those four questions.

Decision control. Architecture reviewers check those four fields, the allowed data, and the recovery duty before approving either option. They postpone the choice when a required right or operator is missing. The review reports complete deployment records over all candidates and the annual labor required to maintain each accepted option. Contract ambiguity and undocumented subcontracting can defeat the check. Recovery uses the tested alternate service or manual path while the organization resolves the missing right. A complete record does not prove that the supplier or internal operator will meet the stated duty.

19.2 Selecting the smallest intervention

The deployment decision becomes confused when the organization treats every missing capability as a reason to train a model. The useful question is what is missing. Prompting supplies task instructions with a request. Retrieval adds selected external material to the current context. Tool access allows the application to call another function or service. Fine-tuning changes model parameters through further training on task data.

NIST’s generative AI profile says that intended-purpose analysis includes internal or external use, narrow or broad scope, fine-tuning, and retrieval-based data sources.3 The list identifies factors to examine but does not establish the right intervention for a task. The packet lacks a controlled study comparing all four choices under the same task, model, data, and evaluation conditions.

The mechanism determines the security work. Retrieval adds source eligibility and instruction-data confusion. Tool access adds identity and action authorization. Fine-tuning adds training data, versioned parameters, and regression testing. A conservative design uses the smallest change that addresses the observed gap, then treats that choice as a hypothesis to test. The selected intervention determines the evidence and recovery material in the adaptation workflow.

Decision control. Change reviewers record the observed gap and check whether prompting, retrieval, a tool, or fine-tuning changes data access, parameters, or action authority. They allow a pilot only when the selected change has a matching test and rollback point. Results report accepted task cases and security failures over all pilot cases. More capable interventions increase integration, review, and recovery work. The rule can fail when the original gap is measured poorly or several changes are bundled. Recovery disables the added capability or restores the previous model and application state. The pilot supports only the tested intervention.

19.3 Model adaptation workflow

An adapted model or prompt can improve the target task while weakening a security property. The organization needs a controlled path from baseline to candidate version. A held-out test set is the general form of the evaluation holdout used in Chapters 3 and 4: it contains examples excluded from training and reserved for later evaluation. A security regression occurs when a security property becomes worse after a change. A known-good state is the recorded version that generalizes Chapter 4’s model baseline into a complete system state accepted for restoration.

NIST recommends renewed evaluation after a third-party model is fine-tuned and after adaptation to a new domain where earlier assumptions may fail.4 Secure-operation guidance also states that changes to data, models, or prompts can alter system behavior. It recommends versioning major updates and retaining a route to a known-good state.5 These recommendations do not specify one validation set or prove that re-evaluation prevents failure.

The process compares the candidate with the accepted baseline and records every security regression. The release decision also references a rollback condition. A hypothetical support assistant might pass ordinary answer tests after fine-tuning but reveal restricted case details under adversarial prompts. The fine-tuned version would remain a candidate until that regression is understood. This workflow produces versioned alternatives for a comparable evaluation.

Control review. The release pipeline checks the candidate version against the held-out task set and the fixed security regression set. It accepts the version only when every mandatory threshold passes. The report gives failures over all cases for each set and records review time and training cost. Data leakage into the held-out set or an untested attack can create a false pass, so the recorded sets apply only within their data and attacker assumptions. Recovery restores the known-good model, prompt, index, and runtime versions.

19.4 Comparable deployment evaluation

A valid comparison gives each deployment the same task difficulty, permissions, and context allowance. A comparable evaluation tests alternatives with the same task set and decision criteria. A failure cost is the operational consequence assigned to an incorrect, unavailable, or unauthorized result. An adversarial case is a test in which an actor intentionally tries to cause a security failure.

The AI Risk Management Framework calls for validity and reliability under expected deployment conditions and for security and resilience to be evaluated and documented.6 It does not provide a complete head-to-head protocol. A worked comparison under constant workload, permissions, context size, and scoring rules remains an open need.

For a hypothetical incident-triage task, both candidates would receive the same redacted alerts and the same action prohibition. Reviewers would measure accepted classifications and unsafe disclosures. They would also record unauthorized action attempts, latency, and unavailable results. The resulting rates remain specific to that test set and operating setup. They supply the quality and failure evidence needed for the cost model.

Measurement rule. The evaluation harness checks that both deployments receive the same case identifiers, context allowance, permissions, and time window. It rejects a comparison when any of those inputs differ. Each rate uses all assigned cases as its denominator, while latency and reviewer effort use accepted results. Comparable inputs may still omit a feature that matters in production or fail to represent future work. A failed comparison returns the pilot to the accepted baseline.

19.5 Calculate ongoing cost

Purchase price alone can reverse a deployment decision once the system is operated. Unit cost divides the total cost recorded for a period by a defined unit of useful work. Fully loaded cost adds assigned infrastructure, labor, and operating cost to direct service cost. Capacity use is the share of available compute capacity doing useful work.

FinOps describes unit economics as a relationship between technology cost and business outcomes. Example units include cost per token, request, customer, transaction, or case resolved. Its more mature view includes fully loaded costs.7 The same guidance notes costs from data centers and enterprise agreements. Software services, model suppliers, and several cloud providers can add further costs.8 These categories organize the calculation. Actual prices and economic value require deployment evidence.

The calculation adds service charges or hardware depreciation, storage, energy, unused capacity, engineering labor, patching, monitoring, human review, and incident handling. The denominator counts only results that meet the acceptance criteria. Actual prices, staffing effort, capacity use, and incident cost remain organization-specific inputs that require current evidence. This full cost view exposes the availability, fallback, and exit assumptions examined next.

Cost control. Finance and service records supply the period cost, while the evaluation record supplies accepted work for the same period. The decision rejects a unit-cost comparison when either period or acceptance rule differs. Collection and allocation add accounting effort. Shared infrastructure, deferred maintenance, and rare incident costs can remain hidden. The recovery route is to recalculate with a stated range and reopen the deployment decision when actual cost crosses its condition. A lower unit cost does not establish lower risk or better continuity.

Comparable cost calculation. The following exercise values describe one year of the same read-only triage workload. Both options process 600,000 alerts and must meet the same quality threshold. Accepted work is the number of alert results that pass review. The values are hypothetical and use currency units rather than current supplier prices.

The hosted unit cost is 414,000 divided by 570,000, or about 0.73 currency units per accepted result. The self-hosted unit cost is 547,000 divided by 576,000, or about 0.95. The self-hosted option accepts 6,000 more results in this example, but costs 133,000 more. Cost alone favors the hosted option. Data-transfer limits, supplier exit, inspection needs, or a failed continuity test can still change the decision. The calculation is a comparison method, not evidence that either option has these costs in practice.

19.6 Test operational fit

An option with good test results and acceptable cost can still fail an operating requirement. An outbound dependency is an external service required during operation. A fallback is an alternate service or manual path used when the primary path fails. Exit cost is the work and cost required to leave a supplier or deployment design.

NIST recommends documenting dependence on third-party AI data and systems. It also recommends identifying fallbacks and testing rollover or manual procedures.9 Secure-development guidance also recommends recording where models, data, prompts, software, logs, and assessments are stored and retaining versions that permit restoration.10 The selected organization still needs legal analysis for location rules and system tests for continuity.

The final deployment record joins task quality, rights, action limits, full cost, required service level, fallback test results, and exit cost. A hypothetical internal model may remove an online supplier dependency while adding scarce operations staff and hardware recovery duties. A hosted service may reduce local maintenance while adding transfer and supplier-exit constraints. This bounded record becomes the input to organization-wide adoption in Chapter 20.

Continuity control. The service manager tests supplier loss and internal runtime loss against the same workload. The application routes work to the manual or deterministic fallback when the health check fails. The test reports completed fallback cases over all cases arriving during the disruption, time to switch, backlog, and total staff hours. Standby capacity and rehearsals raise ongoing cost. A shared identity, network, or data dependency can disable both paths. Because one exercise does not prove continuity for every outage duration, recovery restores the approved service and reconciles duplicate work. Normal routing resumes after credential verification.

Note

Chapter checkpoint. Choose between the two hypothetical deployments in the cost table. The pilot permits redacted alerts and prohibits response actions. It also requires a tested manual fallback. State the decision and one condition that would reopen it.

Conclusion. The hosted option is the current choice because it meets the stated task while producing the lower cost per accepted result. The approval remains limited to redacted, read-only triage. A failed supplier-exit test, a change in transfer rules, or evidence that local inspection is required would reopen the decision. This conclusion does not claim that hosted service is generally safer or cheaper.
