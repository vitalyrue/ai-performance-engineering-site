4  Protecting model training

A training-integrity analysis traces how changes to training data, labels, weights, or adaptation records can alter learned behavior and how the organization detects and recovers.

Security question. How can an attacker change what a model learns?

Reference frame. In the isolated model laboratory, its operator controls the training examples, model files, and configuration, while the attacker can alter a stated subset of the examples. The organization still has no access to an external provider’s base-model training.

Permitted data sources do not establish that training data is trustworthy. Training integrity depends on who can change examples, labels, updates, and model files; acquired models require a different evidence path when training cannot be inspected.

4.1 Points of training influence

A training failure can begin at several write points, so the first decision is which point the attacker can influence. Data poisoning changes the examples used during parameter updates. Model poisoning directly changes model parameters, an adapter, or a contributed update. Ordinary data errors may cause similar symptoms, but the security analysis adds an attacker capability and objective.

NIST classifies poisoning as a training-stage attack and distinguishes data poisoning from direct model poisoning.1 The taxonomy organizes access and attack classes but does not estimate how likely any class is in this laboratory.

The mechanism starts with a path from attacker-controlled input to a training-stage write: source record, label, preprocessing result, contributed update, checkpoint, or final weights. Recording that path separates a corrupt source record from a directly altered model. The next section attaches a measurable objective and budget to the identified influence point.

Example

Concrete influence trace (hypothetical). The operating mode is training a small message classifier. The task is to distinguish ordinary support messages from account-abuse reports. The input contains 1,000 reviewed examples, and the accepted dataset digest is the reference. An external contributor can change 20 source records but cannot write labels, code, checkpoints, or final weights. The preparation job imports 18 altered messages and rejects 2 malformed ones. The observed run record links those 18 record identifiers to the new dataset digest and model output. The conclusion is that the attacker influenced source content within an 18-record effective budget. It is not evidence of direct model poisoning or of a successful attack objective.

The training-data admission service enforces the first boundary. It checks source identity, writable fields, review status, and dataset version before allowing or quarantining records. Evidence includes source IDs, rejected records, the prepared-data digest, and the training job that consumed it. Coverage is admitted and rejected records divided by all records presented to the preparation job. Review and isolation add delay and storage. A write path outside the importer or a false source assertion can bypass the check. Recovery quarantines the affected version and returns to the last reviewed data set. The record proves neither that admitted content is harmless nor that poisoning achieved its objective.

4.2 Poisoning goals

Knowing that an attacker can write data is not enough to design a test. Availability poisoning seeks broad loss of useful performance. Targeted poisoning seeks an error for selected inputs or classes. A clean-label attack keeps the visible label unchanged, and an attack budget states how many records or updates the attacker may alter.

NIST separates availability and targeted poisoning and discusses changed-label and clean-label attacks under different constraints.2 Steinhardt, Koh, and Liang developed certified defenses that bound worst-case loss under explicit assumptions about clean-data concentration and outliers.3

A valid experiment fixes the attacker’s writable fields, budget, target, and success measure before modifying data. Fractions or thresholds reported for one data set are not universal. A targeted objective leads to the special case in which harmful behavior appears only when a trigger is present.

The release evaluator checks a clean holdout set and attack-focused test sets before approving the candidate model version. It reports clean errors out of all clean holdout cases and attack successes out of all eligible target cases, with the modified training records and attack budget attached. Larger test sets and repeated training consume compute and review time. An attacker outside the stated writable fields or budget can bypass the tested model. If the threshold fails, the release gate blocks the artifact and rebuilds from the last accepted data version. Passing does not cover another objective, population, or attack budget.

4.3 Backdoor triggers

A model can perform normally on the clean evaluation set yet fail on a narrow condition. A backdoor is conditional attacker-selected behavior learned during training. The trigger is the feature or pattern that activates it, and the target output is the result the attacker seeks.

NIST describes backdoor poisoning as associating a trigger with an attacker-selected target while clean inputs may retain expected behavior.4 This mechanism explains why aggregate clean accuracy can miss the change: the test distribution may contain no trigger-bearing inputs.

A hypothetical image classifier might retain its ordinary accuracy but map images containing a small, attacker-chosen patch to one class. The example demonstrates the test shape, not a general success rate. Trigger persistence depends on the model, training process, later adaptation, and tested trigger variants. The same conditional behavior may arrive through acquired weights or adapters, which shifts attention from examples to artifacts.

The targeted evaluator checks trigger-bearing and clean cases separately. It records target outputs produced out of all eligible trigger cases, clean-task errors out of all clean controls, trigger variants, and model version. Dedicated tests add design and execution cost, while broad trigger searches can become expensive. A trigger outside the selected variants or a condition absent from the test set can bypass detection. Recovery blocks the artifact and restores a known-good checkpoint. It also removes suspect source records before rerunning both test sets. A zero observed success rate does not prove that no backdoor exists.

4.4 Inspect acquired models

An organization may receive a base model together with an adapter and preference data without observing how each was produced. An adapter is a smaller parameter set applied to change a base model. Behavioral regression is a measured change from an accepted baseline on selected tests.

NIST treats direct modification of a trained model as model poisoning and notes that compromised federated clients can submit malicious updates.5 Its generative-model taxonomy also includes data and model poisoning in the supply chain.6 These categories do not show that every unexpected behavior in an adapter or preference-tuned model is malicious.

The intake mechanism first compares the acquired artifact with an approved base identifier. Clean-task and targeted tests then produce a record of changed outputs before deployment. The current packet lacks a strong source on adapter poisoning and regression testing after preference tuning. Claims about those methods remain open research tasks. The next section focuses on the versions and access controls needed to reconstruct the pipeline.

Example

Concrete adapter comparison (hypothetical). The operating mode is evaluation with fixed parameters. The task is to compare an approved base model with a supplier adapter. Both receive 200 clean cases and 20 targeted trigger cases. The base model returns 174 expected clean answers and rejects all 20 targeted requests. The adapted model returns 176 expected clean answers but follows 7 targeted requests. The intermediate record fixes the prompt set, decoder settings, base digest, adapter digest, and test harness. The observed result is a targeted behavioral regression despite similar clean performance. The conclusion is to withhold this adapter pending investigation. The numbers cannot establish why the behavior changed or whether the supplier acted maliciously.

The artifact intake gate enforces that decision by checking the base digest, adapter digest, loader, clean results, targeted results, and approved environment. It allows isolated evaluation, blocks production use, or admits the exact combination. The report keeps both denominators: 200 clean cases and 20 targeted cases. Testing consumes compute and delays an update. A behavior outside the selected prompts or a different base model can bypass the evidence. Recovery removes the adapter and restores the accepted combination while preserving the failed test record, which does not identify the cause of the regression.

4.5 Secure the training pipeline

Recovery is difficult when a training run cannot be reconstructed. A dataset version identifies the exact records and transformations used by a run. An artifact digest is a cryptographic hash used to compare bytes. A checkpoint records model state during training, and a known-good baseline is a previously accepted artifact with recorded evidence.

NCSC and partner guidance recommends access controls for models, data, training and processing pipelines, plus cryptographic hashes or signatures for model files, data sets, and checkpoints.7

In common practice, a run record links code revision, dataset version, configuration, software dependencies, identities that approved the job, output digest, and evaluation results. A digest detects a byte change but does not show that behavior is safe. These records make rollback and comparison possible. They also supply the baselines needed for poisoning evaluation and response.

The training orchestrator checks this run record before starting a job and the release gate checks it again before admitting the output. Missing or mismatched inputs cause quarantine rather than training or release. Evidence includes resolved versions, access decisions, job logs, checkpoints, and output digests. Coverage is resolved required inputs divided by all inputs in the approved run specification. Reproducible records require storage and controlled build time. An undeclared dependency or compromised approved input can still bypass the check. Recovery stops the job and isolates its outputs. Work resumes from a trusted checkpoint only when that checkpoint and its inputs remain accepted.

4.6 Poisoning evaluation and recovery

The response decision is whether the organization can return to a trusted checkpoint or must rebuild from reviewed inputs. A clean holdout is the Chapter 3 evaluation holdout used for ordinary task behavior, with its data excluded from training. A targeted test measures the specified attacker objective. Evaluation contamination occurs when the data used to judge the model have also been changed or exposed to training.

NIST reports limits in poisoning and backdoor mitigations and notes that many certified results depend on narrow assumptions about models and data, including assumptions about triggers.8 NCSC guidance treats changes to data, models, or prompts as behavior-changing updates that need testing and version handling.9

The evaluation compares a clean holdout, targeted cases, and version records against the known-good baseline. Rollback is useful only if the checkpoint and its inputs remain trusted. Retraining is needed when the trusted point cannot be identified or when contaminated inputs persist. The packet still lacks direct empirical evidence comparing recovery choices after confirmed poisoning, so no universal rule is claimed. The reviewed artifact and its residual risk now become the target of Chapter 5’s query-disclosure analysis.

The response owner blocks release or removes the deployed version when either the clean or targeted threshold fails. The record reports clean errors against all clean holdout cases, attack successes against all eligible targeted cases, and affected training records against the complete prepared-data version. Rollback is faster but retains risk when the checkpoint or its inputs are uncertain. Rebuilding costs more compute and review time. Contaminated holdouts, unknown write paths, or triggers outside the test set can hide failure. Recovery preserves evidence and revokes training writes. It rebuilds the inputs before retesting and redeployment, without proving the absence of another poisoning objective.

Note

Chapter checkpoint. An isolated classifier retrains from 1,000 reviewed records after an external contributor can alter at most 20 source messages. Clean accuracy falls from 90 percent to 89 percent, while success on a fixed 20-case trigger set rises from 0 to 7. What must the training record and response decision contain?

Answer. Record the attacker’s writable fields and effective record budget, source and prepared-data versions, code and configuration, job identity, checkpoint and final digests, clean holdout results, and the separate targeted results. The clean score alone would hide the conditional failure. Restore a known-good checkpoint only if its data and build path remain trusted. Otherwise rebuild from reviewed inputs. The hypothetical results show a regression under one trigger test. They do not identify the cause or establish behavior under untested triggers.
