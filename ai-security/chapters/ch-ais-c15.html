15  Keeping the live system in bounds

This chapter turns the controls and failure paths already identified into runtime records, alerts, limits, and response routes that remain useful after release.

Security question. Which harmful actions can be prevented or detected while the system is running?

Reference frame. Operate an action-capable organization application with organization-side traces and only the provider records actually available. An internal-model variation adds serving and infrastructure observations rather than assuming identical visibility.

Connection through the book. Turn the tested failure paths from Chapter 14 into useful events and response triggers. Chapter 16 consumes those records when an incident is suspected.

15.1 Control placement

Runtime controls differ in what they can actually stop. An advisory check produces information for a model or person. A blocking check sits at an enforcement point and can prevent the protected operation. Control placement identifies the input, retrieval, output, or action boundary where a decision is made and the object that decision protects.

Complete mediation calls for checking access where each protected object is used, while least privilege limits the rights available to a process.1 The NIST Generative AI Profile recommends comparing observed behavior with organizational risk limits and monitoring third-party models within stated bounds.[^c15-s01-genai] These sources guide placement and monitoring but do not establish the accuracy of a filter or detector.

The hypothetical application screens incoming content and checks retrieval permissions before context assembly. It validates structured output before the business service authorizes the resolved action. A model warning may advise, while the service decision can block. Each control record states its input, outcome, fail state, and protected action. Those decisions form the application trace examined next.

The control review tests each enforcement point with allowed and forbidden inputs and records blocked protected operations over all eligible attempts. It also reports clean operations completed over their separate denominator. Added checks increase latency and can reduce availability when a dependency fails. An alternate action path or a warning that is mistaken for enforcement can bypass the intended boundary. Recovery disables the exposed route and restores the last accepted policy before both case groups run again. A passing control at one point does not prove that later components preserve its decision.

15.2 Application traces

An application trace links one user request to the identities, model call, retrieved sources, policy decisions, tool arguments, external results, and final response that followed. Correlation identifiers connect events across services. The trace also has a security boundary because prompts, retrieved text, outputs, and tool results may contain sensitive information.

NIST log-management guidance treats generation, transfer, storage, access, analysis, retention, and disposal as one managed process.[^c15-s02-logs] The NIST incident-response profile calls for logs to be generated and available for continuous monitoring.[^c15-s02-ir] The older log guidance does not define AI-specific fields, and neither source supports indiscriminate recording of sensitive content.

The organization records stable identifiers and decisions by default, then retains sensitive payloads only when a stated purpose and access rule justify them. Encryption, field-level removal, restricted access, and retention limits follow the data classification. A trace schema that covers identity, retrieval, model, policy, and tool events still lacks one stable industry standard. Infrastructure observations add evidence that the application alone cannot see.

The logging pipeline enforces trace admission and access by checking event type, correlation identifier, sensitivity, reader role, retention rule, and storage result. The coverage measure is expected events received over all expected events in sampled requests, with late and unreadable records counted separately. Rich traces cost storage and can increase privacy exposure. Dropped events, clock skew, or reused identifiers can break reconstruction. Recovery preserves local records and repairs the pipeline. Retained events are replayed where possible, and permanent gaps are marked because complete expected events do not prove that every relevant action emitted a log.

15.3 Infrastructure observations

Application logs show intended operations, while infrastructure observations show processes, containers, network connections, accelerator use, storage access, scheduler events, cloud control-plane activity, and billing. Application and infrastructure observations answer different questions. A tool call can look normal in the application trace while the worker contacts an unexpected destination or consumes unusual resources.

NIST continuous-monitoring guidance separates organization, mission or business process, and information-system monitoring levels.[^c15-s03-levels] It also describes a strategy and program for collecting, analyzing, and reporting security information.[^c15-s03-program] The guidance supplies a program model rather than current telemetry fields for accelerators, hosted models, or token billing.

The hypothetical worker attaches the application correlation identifier to its job, process, network, and cloud events. Monitoring joins these events without assuming that a hosted-model provider exposes equivalent detail. An internal model adds serving and accelerator observations, while an external model may expose only request identifiers and supplier reports. These signals support runtime failure indicators.

Concrete control-event trace (hypothetical). The operating mode is live retrieval-based inference. Request req-882 starts worker job job-417 for employee E17. The application trace records one model call and no approved tool action.

Joining on the request and job identifiers connects a normal model response to unexpected worker behavior and two blocking decisions. The infrastructure controls observed and stopped those events in this trace without explaining the worker’s intent or proving that no other connection succeeded. Times, identifiers, and results are hypothetical.

Host sensors, network controls, and the scheduler enforce or observe different states, while the join service checks request, job, workload, and time links before correlating them. The measurement reports joined expected events over all events required by the trace design. Telemetry collection consumes storage and processing and may expose operational details. Missing provider records, clock errors, or an uninstrumented host can bypass the joined view. Recovery contains the workload and preserves each available source. Collection is repaired before the timeline is reconstructed with explicit gaps. Correlation does not establish intent or attribution.

15.4 Runtime failure indicators

A runtime indicator is a measurable condition associated with a tested failure path. Examples include access to a forbidden resource, a new external destination, repeated failed tool calls, an abrupt resource increase, or use of stale retrieved content. An indicator needs enough request and system context to distinguish a likely boundary violation from ordinary variation.

NIST continuous-monitoring guidance says monitoring should support assessment of the security impact of changes and response to findings.[^c15-s04-iscm] The NIST Generative AI Profile recommends evaluating post-deployment monitoring and comparing behavior with defined risk limits.[^c15-s04-genai] These sources leave detection rates, base rates, and thresholds unspecified for prompt injection, retrieval poisoning, and unusual tool use.

The organization derives each indicator from a Chapter 14 test case and records the expected signal, threshold, required context, and response owner. A forbidden-resource event can be exact, while a resource spike needs a workload baseline. Evidence for realistic AI runtime indicator performance remains incomplete, so initial alerts need measurement and review. Their usefulness depends on alert quality and routing.

The detector evaluates the current event and baseline. It can allow ordinary processing or block a protected operation where it has authority. Otherwise, it sends an alert. Evaluation reports detected failures over all confirmed failures and valid alerts over all alerts, with latency and review count beside them. Lower thresholds catch more variation but increase interruptions and analyst work. Drift, sparse context, or an attacker staying below threshold can bypass detection. Recovery contains the affected path and adjusts or disables a faulty rule before labeled cases run again, while detector performance remains insufficient evidence that unobserved failures were absent.

15.5 Alert quality and response routing

Alert quality depends on both detector performance and the frequency of the underlying event. When true incidents are rare, even a detector with good sensitivity can produce many false positives. Priority also depends on the protected asset, possible impact, confidence, and time available for containment. An alert without supporting context shifts reconstruction work to the responder.

The NIST incident-response profile calls for detected events to be analyzed, correlated, placed in context, routed, and declared as incidents when criteria are met.[^c15-s05-detect] It also calls for reports to be triaged, validated, categorized, and prioritized.[^c15-s05-respond] The profile defines desired outcomes rather than an AI alert score or measured analyst workload.

Each alert includes the trace identifier, triggering evidence, affected identity and asset, relevant control, severity basis, and responsible route. Suppression groups repeated manifestations of the same event without hiding distinct users or targets. Investigation outcomes update the indicator’s measured precision and workload. The control still needs predictable behavior when its detector, policy service, or reviewer is unavailable.

The routing service sets priority and destination from incident criteria, asset impact, confidence, and response ownership. The denominator is every generated alert, with delivered, acknowledged, suppressed, escalated, and missed alerts counted separately. Faster escalation takes analyst time and can interrupt low-risk work. Broad suppression, stale ownership, or unavailable communication can hide an urgent case. Recovery removes faulty suppression and reroutes queued alerts. The fallback owner then reviews the affected interval because delivery and acknowledgment do not prove correct triage.

15.6 Control resilience

Control resilience concerns the system’s behavior when a detector, policy service, log sink, or human reviewer becomes slow or unavailable. A fail-open path continues an operation. A fail-closed path blocks it. The choice depends on the safety and availability consequences of each state. Quotas, rate limits, time limits, and stopping rules can remain enforceable even when a secondary detector fails.

Saltzer and Schroeder’s fail-safe-defaults principle bases access on permission so that failure does not silently broaden access.[^c15-s06-saltzer] The NIST Generative AI Profile recommends defined limits and monitoring for third-party models.[^c15-s06-genai] These sources do not decide the fail state for every service or test degraded policy, logging, approval, and detector components.

The hypothetical action service blocks consequential changes when current authorization is unavailable but may serve a clearly marked read-only fallback from approved data. It preserves minimal local evidence until the protected log path returns and applies the normal retention rule afterward. Failure-injection evidence and the balance between privacy and incident records remain open. Chapter 16 begins with the event and retained evidence produced by this runtime design.

Fault injection tests the enforcing service with unavailable policy, detector, log, approval, and identity dependencies. The report counts protected operations that entered the intended fail state over all injected failures and measures clean availability separately. Fail-closed behavior can stop legitimate work, while fail-open behavior accepts more security risk. A shared dependency failure or untested fallback can defeat both paths. Recovery restores the service and reconciles actions with local records from the degraded interval. The injection then runs again, although the correct fail state does not prove that retained evidence is complete.

Note

Chapter checkpoint. A hypothetical application trace shows a normal answer and no approved tool action. Infrastructure records for the same request show denied external egress and a stopped process after the job exceeded its process limit. How should monitoring represent this event?

Answer. Join the application, scheduler, process, and network records with stable request and job identifiers. Preserve the model version, worker identity, destination, policy decisions, process counts, and final task state. Route an alert for unexpected egress plus resource-limit enforcement, with the joined records attached. The evidence supports a blocked abnormal path and an incomplete request. It does not establish attacker control or show that every route was observed.

The chapter retains explicit evidence gaps for trace schemas, AI-specific indicators, and degraded-control tests.
