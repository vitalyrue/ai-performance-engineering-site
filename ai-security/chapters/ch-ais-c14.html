14  Deciding whether to release

This chapter defines the evidence needed to release or change a system, including a reproducible test scope, adversarial conditions, uncertainty, and a decision owner.

Security question. What would count as convincing evidence that the system is secure enough for its intended use?

Reference frame. Evaluate the organization application and the model laboratory as separate stated systems. Keep attacker access, deployment configuration, tool authority, and task success fixed within each comparison.

Connection through the book. Bring the earlier branches together into reproducible evidence. A result qualifies the tested setup. Chapter 15 decides what to observe after release, and Chapter 22 uses the evidence in decisions.

14.1 Evaluation scope

An evaluation scope states the system, task, protected assets, expected behavior, attacker access, failure conditions, and deployment configuration covered by a test. Without this record, a strong result for a laboratory model can be mistaken for evidence about an application that also has retrieval, tools, identities, and external services.

The NIST Artificial Intelligence Risk Management Framework (AI RMF) MAP function calls for documentation of intended purpose, deployment context, users, impacts, risks, and requirements before risk is measured.1 NIST’s adversarial machine learning taxonomy recommends specifying attacker goals, capabilities, knowledge, and life-cycle stage.[^c14-s01-aml] These frameworks organize scope but cannot show that the chosen boundary is complete.

The hypothetical evaluation record identifies the organization application, external model version, retrieval snapshot, tool permissions, employee role, and harmful outcomes. It also states excluded components and the reason for each exclusion. Reviewers can then match every test and conclusion to the same system. That scope determines which clean and adversarial cases belong in the evaluation data.

The release owner enforces scope acceptance by checking every inventoried component, protected asset, attacker capability, and planned exposure against the evaluation record. The coverage denominator is all items in the approved system and threat maps, with tested, excluded, and missing counts kept separate. Wider scope increases test cost and can delay release. An omitted interface or changed deployment can bypass the conclusion. Recovery blocks or narrows release while the missing item is added. Affected tests then run again, although complete mapping does not prove that the chosen threats are exhaustive.

14.2 Evaluation data

Evaluation data represents the tasks and failures that govern release. Clean cases measure intended operation. Realistic cases preserve deployment constraints. Held-out cases reduce direct tuning to the test. Adversarial cases exercise stated attacker capabilities. Coverage records show which assets and failure paths have cases. Overlap with training or development data can make results look stronger than they are.

NIST AI 800-3 distinguishes variation between evaluation items from variation across repeated trials of the same item.[^c14-s02-8003] The AI RMF asks organizations to document test sets, metrics, tools, limitations, data quality, and representativeness.[^c14-s02-rmf] These sources do not supply a contamination detector, a current security data set, or a safe substitute for sensitive records.

The organization builds cases from the scoped task and replaces real secrets with synthetic values that preserve access and disclosure behavior. It records each case’s source, version, expected result, attacker capability, and coverage tags. Another review compares development prompts with known training disclosures where evidence exists. Benchmark contamination and faithful sensitive-data substitution remain open evidence gaps. The resulting set supplies the cases for a fixed attack protocol.

The evaluation-data gate admits a case only after checking its source, version, expected result, access assumptions, coverage tags, and known development overlap. The denominator is every required coverage item and every candidate case, with missing coverage and rejected cases reported separately. Held-out maintenance and realistic substitutes consume expert time and may omit rare failures. Undetected contamination or an unrealistic substitute can make results look stronger than deployment. Recovery quarantines affected cases and rebuilds the set. Every result that used those cases then runs again. A clean overlap check cannot prove absence from unknown model training data.

14.3 Attack protocols

An attack protocol states what the evaluator knows, can change, and can observe during one trial. It fixes the query, time, and interaction budgets, reset conditions, success rule, and stopping point. Repeated trials matter when sampling or external state can produce different results from the same item.

NIST AI 800-3 recommends choosing the evaluation target before the estimator and models repeated trials to separate item and sampling variation.[^c14-s03-8003] The NIST Generative AI Profile includes red teaming, security testing, and reassessment among its measurement actions.[^c14-s03-genai] The publications do not select an attack budget or trial count for this release decision.

For each case, the evaluator starts from a recorded state and applies only allowed changes. The harness records each query and response before success is judged from the predefined outcome. The protocol also captures failed attempts because they affect cost and uncertainty. A fixed protocol supports comparison, but a defense may exploit its weaknesses. Adaptive red teaming checks whether the result remains after an evaluator learns from those weaknesses.

The evaluation harness enforces the protocol by checking initial state, allowed attacker operations, query and time budgets, reset state, and stopping rules. It reports successful attacks over all eligible trials, with protocol violations excluded and counted. Repeated trials consume model calls, reviewer time, and external-service capacity. Hidden state, incomplete resets, or a test-aware defense can bypass the comparison. Recovery restores the recorded state and corrects the harness before affected trials run again. A reproducible protocol does not establish that its attacker strategy is strong.

14.4 Adaptive red teaming

A fixed attack may fail because it cannot reach the defense’s real weak point. Adaptive red teaming allows the evaluator to inspect observed failures and form a hypothesis about the control. The evaluator can then change the attack within the stated threat model. The resulting evidence is stronger when another evaluator can reproduce the bypass and when a fix is tested against both the original and changed attack.

Athalye, Carlini, and Wagner described signs of obfuscated gradients and adapted attacks to the defense instead of treating failure of an unchanged attack as evidence of security.[^c14-s04-method] In the nine defenses they examined, seven relied on obfuscated gradients. Their attacks fully bypassed six and partly bypassed one.[^c14-s04-result] Those numbers apply to adversarial-example defenses in that study, not to prompt injection or tool-using agents.

The transferable lesson is methodological. A failed test can reveal a weak test as easily as a strong defense. In the hypothetical evaluation, the red team changes placement, encoding, timing, and interaction strategy while keeping access and budget fixed. Reviewers record why each adjustment is allowed and what it demonstrates. The observed outcomes then need metrics that state both the denominator and uncertainty.

The red-team lead enforces the threat model and budget while allowing changes to attack strategy. The report counts reproduced bypasses over all eligible cases and records attempted adaptations that failed. Adaptation adds specialist time and makes comparisons harder when evaluators choose different paths. Missing expertise, undisclosed defense behavior, or a narrow budget can leave bypasses unseen. Recovery repairs the control and preserves the successful trace. An independent replay and clean-task regression then qualify the change, although failure to find another bypass does not prove that none exists.

14.5 Metrics and uncertainty

A security metric is interpretable only when its eligible trials and success conditions are explicit. Attack success rate divides successful attacks by eligible attack trials. Precision and recall describe different detector errors, while the base rate affects how many alerts correspond to real failures. Reviewer workload belongs beside these rates because a detector can shift cost to people.

NIST AI 800-3 separates the quantity an evaluation intends to estimate from the statistic computed on observed trials.[^c14-s05-target] It also models variation across items and repeated trials and warns that simpler estimators can omit uncertainty.[^c14-s05-variance] The NIST/SEMATECH handbook provides Wilson and exact binomial intervals for a proportion.[^c14-s05-ci] A simple binomial interval can mislead when trials cluster by task, prompt, model, or evaluator.

The release report states the denominator, point estimate, interval method, item grouping, repeated-trial design, and number of human reviews. It reports utility failures separately from security failures. Sparse high-impact cases remain visible instead of disappearing into an average. These calculations support a decision only if versions, graders, and procedures can be checked, which leads to evaluation reliability.

Worked denominator and uncertainty example (hypothetical). The operating mode is release evaluation of one fixed application version. The evaluator runs six adversarial tasks three times each, for 18 eligible trials. The success rule is a protected value appearing in the final answer. The result is three successful trials.

The attack success rate is (3 / 18 = 0.167), or 16.7 percent. A 95 percent Wilson interval for 3 successes in 18 trials is approximately 5.8 to 39.2 percent. The point estimate alone hides that wide range. The 18 trials also come from only six tasks, so a binomial interval that treats every trial as independent can understate uncertainty created by task clustering.

The release record keeps the 3 successful attacks and the 18 eligible trials. It also records that those trials came from 6 distinct tasks. The observed rate exceeds zero and remains imprecise, while these hypothetical values do not establish a real system’s risk. The interval also cannot correct poor task coverage or a biased success grader.

The release rule converts these measurements into allow, staged, or block decisions after checking the denominator, uncertainty, impact class, and clean utility. Review cost includes duplicate trials, adjudication, and investigation of false alerts. Clustered tasks, a weak grader, or averaging across high-impact cases can defeat the metric. Recovery rejects the affected estimate and corrects the design or grader. The decision is then recomputed from retained trial records. A precise interval does not prove representative coverage.

14.6 Evaluation reliability

Evaluation reliability concerns whether another qualified team can understand and repeat the result closely enough for the same decision. The record includes model and application versions, system prompts, tool schemas, data snapshots, sampling settings, random seeds where available, external service state, grader versions, and adjudication rules. Hosted services may leave some state unavailable, which becomes a stated limit.

The AI RMF calls for documenting measurement methods, metrics, test sets, tools, limitations, and independent review where appropriate.[^c14-s06-rmf] NIST AI 800-3 shows that conclusions depend on the statistical model, its assumptions, and the target quantity.[^c14-s06-8003] These sources do not validate an automated grader or remove model-version drift.

The organization samples automated grades for human review and records disagreements. It reruns a stable subset after version changes. Supplier benchmark claims enter the record with their task, configuration, and access assumptions rather than serving as direct release evidence. Research on language-model judges and reproducible hosted-agent evaluations remains incomplete. The release owner can now weigh measured results with these limits.

Before accepting a result, the service verifies versions, configuration, data snapshots, grader identity, and adjudication rules. The review process accepts a result only after those checks pass. The denominator is every required rerun, with reproduced decisions and material disagreements reported separately. Duplicate execution, storage, and human review add cost. Hosted drift, unavailable random state, or shared grader errors can bypass reproducibility checks. Recovery freezes the claim and restores an inspectable version where possible. The stable subset then runs under independent review. Agreement does not prove that the underlying success rule is valid.

14.7 Release and change criteria

A release decision joins test results with the organization’s risk limit and the planned exposure. The record states minimum utility and security thresholds, unresolved cases, the responsible owner, staged user or data scope, rollback conditions, and changes that require reevaluation. A threshold has meaning only for the scope, data, protocol, and uncertainty already documented.

The NIST Generative AI Profile recommends minimum thresholds, go or no-go policies, and a plan to halt deployment when risk is unacceptable.[^c14-s07-go] It also recommends evaluation before and during deployment, periodic review, and after-action review.[^c14-s07-review] The profile leaves the threshold and risk acceptance authority to the organization.

The hypothetical decision may allow a proposal-only pilot for one department while blocking external actions until action tests pass. A model, retrieval corpus, tool schema, permission policy, or control change can trigger focused or full reevaluation according to its possible effect. Release evidence qualifies the tested setup and expires as that setup changes. Chapter 15 turns these accepted limits into runtime enforcement and observations.

The deployment gate enforces the decision by checking approved versions and measured thresholds. It also checks unresolved failures, the exposure limit, the owner, and rollback triggers before each stage. The denominator is the planned users, data classes, and capabilities for that stage, with actual exposure compared against each limit. Staging delays access and requires parallel support for rollback. An unrecorded configuration change or alternate deployment route can bypass the gate. Recovery removes access and restores the accepted version. Failed traces are preserved for reevaluation before expansion. Approval does not transfer to a wider population or changed system.

Note

Chapter checkpoint. A hypothetical release candidate is the organization support application with external inference, approved retrieval, and proposal-only tool access. It completes 94 of 100 clean tasks. It also has 3 successful attacks in 18 eligible adversarial trials drawn from 6 tasks, with a Wilson interval of about 5.8 to 39.2 percent. The release rule requires at least 90 percent clean completion and no demonstrated high-impact disclosure. What is the decision?

Answer. The candidate meets the clean-task threshold but fails the security rule because three trials produced the stated high-impact disclosure. The organization should record a blocked release for this scope and preserve the versions and traces. It should repair the failure path before rerunning both the clean and adversarial cases. The wide interval also shows that the test gives an imprecise rate. It does not weaken the zero-tolerance rule for an observed high-impact outcome. All values are hypothetical.

The chapter retains explicit evidence gaps for data overlap, automated graders, and evaluations of changing hosted systems.
