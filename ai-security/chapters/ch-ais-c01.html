1  Mapping the system

This chapter establishes the components, people, identities, data, operators, permissions, and records that make up the AI system before it discusses attacks.

An employee sees one text box. Behind it, the organization depends on identity services and document stores. An application connects those services to models, external providers, action services, logs, and people. A useful security review identifies that larger system before it can make a useful claim about risk.

This chapter starts with an organization that operates an assistant application and uses an external model for inference. The application may provide chat or document retrieval. It can also propose actions or pass confirmed operations to services that enforce policy. Later chapters also examine supplier-operated assistants, managed platforms, and organization-operated models. The book treats every arrangement as a mix of direct control, supplier responsibility, and facts that require evidence.

The chapter produces a system record that identifies components, operators, identities, data, transfers, permissions, possible state changes, and available evidence. Chapter 2 uses that record without changing its assumptions.

The organization scenarios are hypothetical

The organization, employees, records, permissions, and observations in this chapter are hypothetical. They do not describe a real company or product. The supplied presentation identifies relevant topics. Research and official guidance support the general claims used here.1

1.1 The request and the system boundary

Consider an authenticated employee using an internal assistant to find the approval required for a supplier contract. The answer may depend on private policy documents. A later configuration may let the assistant prepare a purchase request, but a separate service must decide whether the operation is authorized.

The visible request does not tell us which components receive the question, which records enter the model context, or which service can change business state. The map separates the visible model, its application, and the complete operational system:

This book uses AI system for the complete set of components and parties whose behavior matters to the decision under review. The U.S. National Institute of Standards and Technology (NIST) AI Risk Management Framework treats AI risk across lifecycle stages and among several actors.2 International secure-development guidance also covers systems assembled from internal components, hosted models, external APIs, and several providers.3

The relevant boundary depends on the decision. A parser unit test may examine one function. A release decision for the assistant includes the application, model service, connected records, identities, suppliers, action services, monitoring, and response process.

For this chapter, the decision is whether the organization can allow employees to use the assistant for policy questions and limited business-action proposals. NIST AI RMF MAP 1.1 calls for context such as intended purpose, users, deployment setting, assumptions, limits, and possible impacts.4

The baseline fixes these facts:

  • The organization operates identity, application, retrieval, logging, and business-action services.
  • An external provider operates model inference.
  • An employee may read approved policy and assigned customer or supplier records. The employee may not read payroll or another business unit’s restricted records.
  • The provider receives only the request and context that the application sends. Direct access to the document store or action service is outside this setup.
  • A generated proposal cannot change business state. An authenticated user and the action service must pass current policy checks.
  • Provider retention, model-improvement use, processing region, and provider logs remain supplier facts that require evidence.

These assumptions create a baseline. A later chapter may change one operator, data path, attacker capability, or application capability while keeping the remaining facts fixed.

1.2 Enough model behavior to read the map

The system map contains a model as one component. Readers need to know which state changes during training, which state remains fixed during inference, and what an evaluation result can establish.

A predictive model maps an input to one or more estimated outputs. A fraud model may accept transaction features and return a score. A generative model produces a sequence or structured object. A large language model (LLM) accepts context and generates tokens.

Training uses examples, an objective, and an update procedure to change model parameters. A parameter is an adjustable numeric value used by the model. Training may use labels, demonstrations, preferences, or other feedback. The training result includes parameters and configuration, not a database of ordinary records that the application can query directly.

Inference applies fixed parameters to an input and produces an output. The input contains the user request and application instructions. It may also include conversation history or retrieved text. A token is a unit that a language model reads or generates. Context is the sequence of tokens available for the current model call.

Evaluation measures behavior on selected cases without updating the parameters. An evaluation must state the model version, input set, expected result or scoring rule, and conditions. A result on one set does not establish behavior for every possible input.

During text generation, the model converts the available context into scores for a possible next token. A decoding rule selects one token, appends it to the context, and repeats. Sampling settings can make repeated calls differ even when the initial text is identical. The generated sequence remains model output. Its meaning, permitted use, and consequences depend on the application.

Generalization is useful behavior on cases that were not used for parameter updates. Memorization is the retention of training details strongly enough to affect later behavior. A model can show both. Chapter 5 explains why disclosure claims need a precise query interface and measurement rather than an assumption that every output came from one stored record.

The application flow remains ordinary software around the model call:

Code example: Pseudocode for a small chat path that uses external inference.

session = identity_service.verify(request.session_token)
context = application.build_context(user=session.user, text=request.text)
disclosure_policy.check(context, destination="external-model")
draft = external_model.generate(context)
return application.validate_and_display(draft)

Authentication, context assembly, transfer, validation, display, logging, timeouts, and error handling belong to the application and related services. Those paths can fail even when the model behaves as its operator intended.

Concrete trace (hypothetical). The operating mode is inference. The task is to classify an employee request for routing, using fixed model parameters. The input is "Reset access for account 417", and the reference is an approved test label of account-support. The application creates 6 input tokens, the model produces scores of 0.72 for account-support and 0.18 for general-help, and the decoding rule selects the larger score. The observed result is a routing proposal. The parameters remain fixed, and the business record is unchanged. The conclusion is that inference produced a candidate output, while the application still controls validation, routing, and any later action.

1.3 Who operates each part and what it can do

Record the operator for each component and the data or actions available to the application. These facts describe an AI system more clearly than one deployment label:

  1. Component operator.
  2. Data and actions available to the application.

The book does not assume an on-premises model or complete external control. Common operating arrangements include:

An organization-operated model can still depend on cloud administrators, firmware, package repositories, acquired weights, and external identity systems. A provider-operated model does not automatically receive the organization’s complete document collection. A complete map identifies the actual transfer and responsibility for each component.5

Application capability is a separate question:

An application can combine any operating arrangement with several capabilities. The examples below state both facts directly:

Adding retrieval changes data exposure. Adding execution changes possible consequences. Moving inference in-house changes operational responsibility and available evidence. Each change leaves the other decisions open.

The deployment record controls this choice. Its reviewer checks every listed component, operator, transfer, and reachable action before allowing the configuration. The release record, route configuration, provider receipts, and action-service logs show which choice became active. Coverage is the number of reviewed components and routes divided by all components and routes in the approved map. This review costs engineering time and may delay a provider or platform change. An undocumented connector or administrator path can bypass it. Recovery disables the changed route and revokes its credentials. The last approved configuration is then restored. A complete record does not prove that every supplier behaves as described.

Concrete comparison (hypothetical). The task is to decide whether an internal policy assistant can answer a restricted employee question. In the first arrangement, the organization operates the application and an external provider operates inference. In the second, the organization operates both. The same request and permitted passage enter each run. The intermediate record shows that only the first run crosses the provider boundary. Both runs return the same draft answer in this example. The observed difference is operator access, transfer evidence, and incident responsibility, rather than answer quality. The conclusion is that deployment location changes the trust record even when application capability and observed output remain unchanged.

1.4 Components, assets, identities, and boundaries

A useful system record specifies concrete objects. At minimum, it includes user and service identities, the application, model service, source systems, indexes, prompts, action services, logs, operators, and provider interfaces.

An asset is something whose disclosure, unauthorized change, loss, or unavailability would matter to the decision owner. Secure AI guidance includes models, data, prompts, software, documentation, logs, and assessments among the assets that may need protection.6

The same information may appear in several places. A policy document can exist in a source repository, a search index, a model request, a cache, and a log. Different people or services may read each copy. Its retention and deletion rules may also differ.

User identities and service identities also have different jobs. A user’s identity supplies current person and tenant claims. An ingestion service may read a broad source collection to build an index. An application service may call the model. Because an action service receives a narrower credential and checks business policy, broad ingestion access does not grant the same access to each employee.

A trust boundary is a point where data or control crosses between operators, users, tenants, privilege levels, or policy domains that cannot simply trust one another. An application programming interface (API) is an interface. It becomes a relevant trust boundary when the caller and receiver have different authority, evidence, or operating responsibility.

This inventory lets the reader trace one request without treating every arrow as equivalent.

The configuration gate checks each discovered asset against the inventory before deployment. It allows the version when its operator, permissions, copies, and recovery owner are recorded, and blocks or quarantines an unlisted component. Evidence includes inventory revisions, discovery results, access decisions, and deployment records. Coverage is the number of discovered assets linked to a reviewed row divided by all assets found by the selected discovery methods. Maintaining this record adds review work and can slow urgent changes. A shadow connector or an asset that the discovery methods miss defeats the check. Recovery revokes the related identity and removes reachable copies where possible. Rebuilding the map leaves the existence of unknown assets unresolved.

1.5 A chat request across an external model boundary

Start with the smallest runtime path. The employee submits text. The organization’s application authenticates the session and builds a request. It checks what may leave the organization before calling an external model. The application then records and displays the result. No document connector or business-action service is reachable on this path.

If the output says that an action occurred, the statement is still generated text. An authoritative business record would be needed to establish a state change. The organization can inspect its serialized request and local logs. Evidence of receipt and later processing must come from the provider.

Concrete trace (hypothetical). The operating mode is inference, and the task is producing a summary of a non-sensitive meeting note. The input contains 180 characters of employee text plus the application instruction. The application records request ID r-204, the exact serialized fields, and an allowed destination decision. The provider returns response ID p-771 and a 42-word summary. The application records both identifiers and displays the text. The observed result proves what the organization sent and displayed. It does not prove which provider replicas held the request or when each copy disappeared. The conclusion is that local and provider evidence answer different parts of the same transfer claim.

The application gateway enforces the transfer rule. It checks destination, data class, and serialized fields, then allows, removes fields from, or blocks the request. A test set records forbidden fields caught out of all seeded forbidden fields, along with permitted requests accepted out of all permitted controls. Filtering adds latency and can block legitimate text. An unfamiliar encoding or an unclassified field can bypass the rule. Recovery disables the route and revokes the provider credential. Deletion and incident work then follows for affected request IDs. A passing sample does not establish provider erasure or detection of every sensitive format.

This path establishes the external model boundary. The next section adds retrieval while preserving the same inference operator.

1.6 Retrieval and document access

The application retrieves source passages while processing a request. A relevance score cannot answer the access and authority questions that follow.

The retrieval boundary separates four questions:

  1. Who may add or change source content?
  2. Which passages may the current user read?
  3. Which passages may the organization send to this model provider?
  4. Can retrieved text authorize an action or change application policy?

Lewis and colleagues introduced retrieval-augmented generation models that combined a learned generator with a dense external index and retriever.7 Current products use several architectures under the broad RAG label. This book’s application pattern preserves source identity and access metadata. It checks current user permissions before selecting text. The application sends only permitted context to the model. It does not claim to reproduce the paper’s jointly trained design.

Suppose search returns four candidate passages:

Relevance answers whether text may help answer the query. Authorization answers whether this user may read it. A disclosure rule answers whether the organization may send it to the provider. Retrieved text remains data even when it contains sentences that look like instructions.

If a forbidden passage enters the serialized model request, a later refusal to repeat it does not undo the transfer. If provider receipt cannot be observed, the record must say that it is unknown. Chapter 3 follows these copies through their retention and deletion paths. Chapter 11 returns to retrieval access, poisoning, and evidence quality.

Concrete trace (hypothetical). The operating mode is retrieval followed by inference. The input is an employee request for the travel reimbursement limit. Search returns four passages with scores 0.91, 0.86, 0.79, and 0.74. The second passage belongs to another department and fails the current access check. The fourth contains payroll data and fails the provider disclosure rule. The application sends the first and third passages to the model. The observed answer cites both permitted passages. The conclusion is that relevance produced candidates, while user authorization and provider disclosure independently reduced the context from four passages to two. All scores and records in this trace are hypothetical.

The retrieval service enforces document access, and the disclosure service enforces transfer to the provider. They check the current user, document metadata, destination, and selected text before context assembly. The report gives forbidden passages rejected out of all seeded forbidden candidates and permitted passages retained out of all permitted controls. Fresh authorization adds lookup cost and may reduce cache reuse. Stale metadata or an index that loses source identity can bypass the intended decision. Recovery invalidates cached results, removes the affected index version, and rebuilds from approved sources. This evidence does not show that admitted text cannot mislead the model.

1.7 From a proposal to an authorized action

A model may produce structured fields for a possible operation:

Code example: A model-generated proposal before authorization.

{
  "operation": "create_purchase_request",
  "supplier_id": "supplier-204",
  "amount": 1200,
  "currency": "USD",
  "reason": "replacement equipment"
}

Before displaying the proposal, the application validates the operation name and schema, although structural validation cannot establish that the operation is correct or authorized.

Execution requires a separate path. The application displays the exact operation, destination, amount or scope, and source information. The employee confirms those fields. The action service checks the authenticated identity, current permissions, business limits, and retry state. It records either a denial or one state change.

The model supplies candidate arguments. Authority comes from identities, current policy, and the service that records the business state. A sentence in a retrieved document cannot change those rules. Chapter 12 develops this separation for tools and agents.

Concrete trace (hypothetical). The operating mode is inference followed by a possible external action. The task is to reimburse 120 currency units to an employee. The model proposes amount 120 and destination acct-9. The application validates the fields and shows them for confirmation. Before the employee confirms, a simulated retry changes the destination to acct-8. The action service compares the confirmed reference fields with the submitted fields and denies the mismatch. The observed business state contains no payment, while the audit record contains the proposal, confirmation, denial, and operation key. The conclusion is that model output proposed an action but did not grant authority to execute it.

The action service enforces the final decision. It checks authenticated identity, exact confirmed fields, current business rules, and the operation key before allowing, blocking, or changing the requested operation. Tests report unauthorized attempts denied out of all unauthorized attempts and authorized controls completed exactly once out of all authorized controls. Confirmation and policy checks add delay and can reject legitimate work after a policy change. An alternative action path that skips the service defeats the control. Recovery suspends that path and revokes its credential. The business reversal process handles a state change when reversal is possible. A denial test does not prove that displayed advice is safe or correct.

1.8 Lifecycle and evidence

One request trace shows runtime behavior. A security decision also depends on how the system was designed, acquired, evaluated, deployed, changed, operated, and retired. The UK National Cyber Security Centre (NCSC) guidelines organize secure AI development into secure design, development, deployment, and operation and maintenance.8 The following table is this book’s expanded working sequence.

Evidence varies with the operating arrangement. An organization can inspect its own context assembly and authorization code. For external inference, it may receive provider documentation and request identifiers. Usage records and contractual commitments provide other evidence. Operating the model exposes more technical state and also creates more patching, monitoring, and recovery duties.

A release and change gate enforces the lifecycle decision. It checks the approved artifact versions, identities, routes, required tests, and rollback target before allowing a deployment or update. Deployment records and joined runtime logs show which version ran. Review coverage is the number of changes that received their required checks divided by all changes found in the release history. The gate adds release time and record storage. An emergency or manual change outside the recorded path can bypass it. Recovery disables the affected version and revokes obsolete credentials. The last accepted state is then restored. These records prove neither supplier behavior nor the absence of unrecorded changes.

1.9 Worked system-mapping task

An organization plans to move document indexing and search from its own services to a managed platform. The application, identity service, source repository, external model provider, and business-action service remain unchanged.

First record the components that move: document parsing, embedding generation, index storage, query embedding, and candidate search. Then add the new transfers. Source text and metadata may cross to the managed search provider during ingestion. Query text may cross during search. Search results return to the application before user authorization and model-provider disclosure.

Preserve the permission mechanism. The managed index may store tenant and document metadata, but the organization must still identify where current user authorization runs and how permission changes invalidate cached results.

Record the evidence expected from each operator: source version, ingestion identity, indexed object identifiers, search request, candidate identifiers, authorization decision, serialized model request, and deletion result. Missing provider evidence remains an explicit limit.

Conclusion. Moving search changes operators, transfers, retained copies, and available evidence. It does not automatically change what the application may execute. Chapter 2 can now ask what unwanted outcomes follow from this specified arrangement.

Worked comparison (hypothetical). The task is to compare the old and new maps. The input is the approved five-component baseline plus the planned managed-search change. The reference requires every changed operator, transfer, copy, and evidence source to appear. The old map has one external recipient and two organization-held document copies. The new map has two external recipients and adds source text, an index copy, query text, and search-result records at the search provider. Application permissions and action authority remain unchanged. The observed result is four changed rows and no action-path change. The conclusion is that Chapter 2 should analyze new disclosure and source-integrity paths without inventing a new execution capability.

The change gate checks every changed row against an approved operator, permission rule, test, and recovery owner before allowing the managed search route. The comparison covers four changed rows out of the four found in this exercise. Provider review and migration add cost, and missing a temporary copy or support path leaves the map incomplete. Recovery returns search to the prior service and revokes the managed route. This worked result supports the stated map comparison, not the managed provider’s behavior.

1.10 From the map to the threat model

The completed system record contains:

  • The decision and system version.
  • Users and service identities.
  • Components and their operators.
  • Training, evaluation, and inference roles.
  • Stored data and runtime transfers.
  • User, disclosure, and action checks.
  • Possible state changes.
  • Logs and evidence gaps.
  • Assumptions that trigger a new review when they change.

Chapter 2 adds a bounded attacker and an unwanted outcome to this record. It then identifies an enforcing component, a test, and the remaining risk.

1.10.1 Chapter checkpoint

At this point, a reader should be able to distinguish the model, application, and operational system. The reader can state who operates each component, separate chat and retrieval from action, and identify which evidence belongs to the organization or an external provider.
