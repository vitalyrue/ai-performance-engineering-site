8  Limit platform access

An infrastructure trust map identifies which provider and platform components can access workloads in organization, cloud, and provider-managed environments.

Security question. Which provider and platform components can access the workload, and how is that exposure reduced?

Reference frame. The comparison covers an external model API, an organization-operated model on rented infrastructure, and an on-premises model service. It identifies administrators, key holders, network recipients, and the evidence available for each layer.

An accepted component still depends on the hardware, virtualization, storage, network, identity, and administrators of the platform where it runs. The deployment record assigns those responsibilities before runtime access is configured.

8.1 Cloud responsibilities

Moving a workload changes which parties operate its layers. Shared responsibility divides security duties between customer and provider. The control plane manages resources, identities, and configuration. Administrative access is the authority to change or inspect those layers.

NCSC guidance states that modern AI systems often combine software, data, models, and remote services from several parties, making responsibilities harder for users to inspect.1 NIST Zero Trust Architecture removes implicit trust based only on network location, affiliation, or ownership and focuses access decisions on resources.2

The organization maps who operates hardware, firmware, virtualization, storage, network, identity, model service, and application layers. Zero trust still depends on administrators, hardware, identity systems, and policy enforcement. The packet lacks a provider-neutral duty table for managed AI services, so the comparison must use each service’s current contract and evidence. That map exposes the tenant boundaries to test next.

The deployment reviewer enforces the responsibility decision. The reviewer checks every platform layer, administrator path, customer duty, supplier duty, and available evidence before allowing the arrangement. Coverage is reviewed layers divided by all layers in the approved platform map. Contracts, configuration records, access logs, and test results show what was reviewed. More direct operation increases patching and on-call cost, while more provider operation can reduce direct evidence. An undocumented support path or external dependency can bypass the map. Recovery disables the affected service path and moves to the accepted fallback arrangement, without proving supplier performance.

Example

Concrete responsibility comparison (hypothetical). The task is to locate administrative access for the same inference workload in three arrangements. The input is a layer list covering hardware, firmware, virtualization, guest system, model service, application, and identity. For an external model API, the provider operates every layer through the model service. On rented infrastructure, the organization operates the guest system, model service, and application. On premises, it also operates hardware and firmware, although suppliers still provide components and updates. The observed comparison has no arrangement with zero external trust. The conclusion is that control moves between parties, while update, identity, and hardware assumptions remain explicit evidence questions.

8.2 Tenant isolation tests

A multi-tenant platform needs a boundary that prevents one workload from reading or changing another. Tenant isolation is that separation across compute, memory, storage, network, and management paths. A container isolates processes while sharing the host operating-system kernel. A virtual machine supplies a separate guest operating system above a virtualized hardware boundary.

NIST states that containers share a kernel and identifies risks around containers, hosts, images, registries, and orchestrators.3 It recommends layered isolation and application-aware network controls instead of simple host separation alone.4

The test identifies the actual boundary and limits validation to authorized cross-tenant checks, while virtual-machine and accelerator-memory isolation need current evidence beyond the older container guidance. The packet still needs current primary evidence for accelerator clearing and multi-tenant tests. Encryption and key custody address different exposure paths.

The hypervisor, container runtime, storage service, and network policy enforce different parts of tenant separation. The tests verify whether the platform checks tenant identities, memory and storage objects, network routes, and management permissions before allowing permitted access or blocking a cross-tenant attempt. The report states blocked attempts over all seeded cross-tenant attempts and successful permitted accesses over all controls. Stronger isolation can reduce accelerator sharing and increase cost. A host flaw, stale device memory, or management path outside the test can bypass the boundary. Recovery evacuates the host and revokes affected identities. The platform procedure clears or replaces resources before service is restored elsewhere. Passing does not establish every accelerator or provider isolation property.

8.3 Control encryption keys

Encryption claims must specify the state of the data and who can release the key. Data at rest is stored data. Data in transit moves between endpoints. Data in use is being processed in memory. Key custody identifies which party or component can use or release a cryptographic key.

NIST key-management guidance treats key generation, distribution, storage, use, backup, recovery, revocation, and destruction as lifecycle functions.5 NIST zero-trust guidance requires authentication and authorization before a session to an enterprise resource is established.6

The organization traces key generation and release for each data state. General key guidance still cannot show that a provider lacks plaintext or key access. A key-release policy must bind identity, workload state, purpose, and expiry. The packet lacks a stable confidential-computing architecture source for this mechanism, so the claim remains an evidence requirement. Protected execution provides one possible state input, which the next section examines.

Example

Concrete key-release trace (hypothetical). The operating mode is inference on rented infrastructure. The task is to decrypt one document only for an approved workload. The input is encrypted document D-18, workload identity W-4, a current approval, and a key request. The reference policy requires the approved identity, measured workload state, document purpose, and a five-minute expiry. The key service accepts the identity and purpose but receives no trusted workload-state result, so it denies release. The observed result is an encrypted document and a denial record. The conclusion is that encryption at rest protected this denied path. It does not show who could access plaintext after a valid release.

The key service enforces the release decision. It checks workload identity, appraised state, document purpose, approval, and lease expiry before allowing or denying key use. Evidence includes each request, checked policy version, decision, lease, and later revocation. Tests report unauthorized releases over all seeded unauthorized requests and successful permitted releases over all controls. Short leases and repeated appraisal add latency and availability risk. A copied key, alternate decryption path, or incorrect identity binding can bypass the policy. Recovery revokes the lease, rotates the key where possible, and isolates affected workloads. A denial does not prove plaintext was never available through another path.

8.4 Data protection during use

Data-in-use protection depends on a smaller boundary than the whole provider. A trusted execution environment, or TEE, is a protected execution area whose isolation and measured state form part of the security claim. A root of trust is a component accepted as a starting point for measurement or verification.

RFC 9334 separates a target environment from the environment that collects evidence and requires claims to be securely associated with the target.7 This architecture explains evidence relationships but does not define or guarantee TEE isolation.

A TEE claim needs the protected memory and execution boundary, excluded interfaces, firmware trust base, update process, measurement method, and key-release relationship. The packet has no provider-neutral source with sufficient detail on TEE isolation and side-channel limits. Those properties remain explicit evidence requirements. Remote attestation carries measurements to a decision outside the workload.

Example

Concrete TEE boundary trace (hypothetical). The task is to state what an organization would need to verify before placing document plaintext inside a protected execution area. The input record identifies the workload image, protected memory, entry and exit interfaces, firmware version, measurement method, and key-release path. The host administrator is outside the claimed protected area but still controls scheduling and can deny service. Model output and allowed logs leave through explicit interfaces. The observed boundary record supports the listed memory and execution area only when its platform evidence is valid, without extending the conclusion to side channels, availability, output confidentiality, or unlisted firmware. Those remain separate evidence requirements.

The platform’s protected-execution mechanism enforces the claimed memory and execution boundary. Admission checks the workload measurement, firmware state, entry and exit interfaces, and supported feature set before placing plaintext inside it. Evidence includes measurements, platform reports, key decisions, and observed exits. Coverage is tested interfaces and supported states divided by all interfaces and states in the declared boundary. Protected execution can limit hardware choice, reduce observability, and add cost. Side channels, malicious trusted firmware, rollback, or an unmeasured device can bypass the claim. Recovery stops key release and rotates affected secrets. Moving the workload to an accepted environment still does not prove isolation by itself.

8.5 Remote attestation evidence

A remote system needs a mechanism that tests observed workload state before releasing data or keys. An attester produces evidence about an environment. A verifier appraises that evidence against policy. A relying party uses the result for an application decision.

RFC 9334 defines these roles and their evidence flow.8 It treats freshness as a policy-dependent limit on evidence age while warning that state can change immediately after evidence is produced.9

The relying party validates evidence, applies reference values and appraisal policy, then decides whether to release a resource. The architecture leaves the evidence format, trust anchors, policy, and protected workload to each deployed system. Fresh evidence narrows age but cannot prove future state. The final section places these limits beside provider evidence.

Example

Attestation evidence flow (hypothetical). The task is to release document key K-18 only to approved workload W-4. First, the relying party sends a fresh challenge. The attester returns evidence that binds the challenge to a measured environment and workload value. The verifier checks the evidence signature and freshness, compares the measurement with approved reference R-12, and applies policy version 5. It returns an appraisal result that says the observed state matched at 10:03. The relying party checks that result and releases a five-minute key lease. The workload decrypts the document and returns a summary. The observed records are the challenge, evidence, reference, policy, appraisal result, key decision, and output. The conclusion is that the release was bound to one appraised state and time. It does not prove future state or properties outside the measured boundary.

The verifier enforces appraisal, and the relying party enforces key release. The verifier checks the challenge and evidence signature against the trust anchor. It also checks the reference value and policy version before evaluating freshness and workload identity. The test reports accepted approved states and rejected stale or altered states over all seeded cases. Attestation adds service dependencies, latency, reference-value maintenance, and a possible availability failure. A compromised trust anchor, rollback accepted by policy, or state change after evidence collection can bypass the intended condition. Recovery stops release, revokes the lease, updates reference values when justified, and rebuilds the workload. A valid appraisal proves only the measured claim under the accepted roots of trust.

8.6 Provider evidence and limits

A certificate or audit report covers only its stated deployment claim. An audit scope states the systems, controls, locations, and time period examined. A side channel leaks information through effects outside the intended data path, such as timing or resource use. Rollback returns software or state to an earlier version.

RFC 9334 states that its architecture alone cannot show whether a deployed system mitigates its threats and ties assurance to roots of trust and protected policies. It also requires separation among the roles.10 NCSC guidance asks providers to state which security aspects remain the user’s responsibility and where data may be used, accessed, or stored.11

The comparison records administrators, key holders, isolation claims, attestation path, update and rollback behavior, metadata exposure, audit scope, and customer duties. The packet lacks a strong general source for TEE side channels and rollback and does not map an audit to one deployed configuration. Those remain review items rather than assumed protection. Chapter 9 receives the remaining interfaces, identities, and duties as runtime constraints.

The deployment owner can accept, restrict, or reject the platform after matching provider evidence to the exact configuration and time period. Coverage is supported control claims divided by all required claims in the platform review, with unknowns retained as unknowns. Deeper supplier evidence costs review time and may not be contractually available. A broad certificate, expired report, or configuration outside the audit scope can create false confidence. Recovery disables the affected route and revokes its keys and identities. The workload then moves to the recorded fallback, without establishing side-channel resistance, availability, or provider actions outside the evidence scope.

Note

Chapter checkpoint. The scenario requires a rented-infrastructure model to read an encrypted document. The provider operates the hardware and firmware. The organization operates the workload and key policy. State the evidence flow that can gate key release and the claims that remain open.

Answer. Record the workload and environment measurement, a fresh challenge, attester evidence, verifier trust anchors, approved reference values, appraisal policy and result, and the relying party’s key decision. Bind a short key lease to the approved identity, purpose, and appraisal. This can support the tested release decision under the stated roots of trust. It does not establish the TEE’s isolation by itself. Provider administrators, firmware defects, side channels, denial of service, exposed outputs, and state changes after attestation remain outside or at the edge of the claim.
