7  Admitting trusted components

This chapter treats every acquired dataset, model, adapter, package, container, and skill as a component that needs a stated intake decision before it reaches a trusted environment.

Security question. What must be trusted before an acquired component is allowed to run?

Reference frame. The organization evaluates a model package, adapter, and dependencies for an internal-model configuration. For an external model, inspect the organization application’s dependencies and the available supplier evidence. Hidden provider weights remain outside the organization’s inspection scope.

Connection through the book. Chapter 4 explains harmful learned behavior. This chapter explains acquisition and loading, then hands an admitted component to the compute and deployment decisions in Chapters 8 and 9.

7.1 The AI dependency inventory

An intake review can miss the component that actually introduces risk. An AI dependency is a model, data set, library, service, prompt resource, or other component on which the AI path depends. A transitive dependency is used through another dependency rather than selected directly.

NCSC guidance includes models, data, libraries, modules, middleware, frameworks, external interfaces, prompts, logs, and assessments among AI supply chain components or assets to track.1 The NIST Secure Software Development Framework (SSDF) calls for an inventory of software components and their relationships.2

The inventory links each component to its version, supplier, acquisition channel, dependants, update path, and execution environment. SSDF covers software, so the organization must extend the record to data sets, weights, adapters, and remote model services. The next section separates inert data from formats and loaders that can execute code.

The admission gate checks the complete component record before allowing a build or deployment. It blocks a missing, unresolved, or unapproved dependency. Evidence includes the resolved dependency graph, supplier and version records, download locations, and the build that consumed them. Coverage is reviewed components divided by all direct and transitive components found by the selected resolver and runtime trace. Inventory work adds update delay and storage. A unrecorded runtime download or undeclared service can bypass the record. Recovery stops the build and revokes affected credentials. Using the last accepted graph for the next build still does not prove that every listed component is safe.

Concrete inventory trace (hypothetical). The task is to identify everything required to run an internal support model. The input is one deployment file that directly lists a model package, tokenizer, inference library, and container. Dependency inspection adds a numerical library and a model loader used through the inference library. The reference is the approved component record. The observed inventory has six components, two of them transitive, with versions, suppliers, download locations, and update paths. The conclusion is that reviewing only the four direct entries would leave two executable dependencies outside the intake decision.

7.2 Model loading and code execution

A file described as model weights may still cause code to run when loaded. Deserialization reconstructs software objects from stored bytes. A data-only artifact is intended to contain values under a restricted schema. An executable artifact can invoke code through its format, loader, package hooks, or custom model implementation.

PyTorch states that torch.load uses an unpickler and warns against loading data from an untrusted source.3 PyTorch also documents that weights_only=True restricts imports selected at load time and object construction but does not prevent denial of service and may not prevent every memory-safety problem.4

Intake starts in an isolated environment with no production credentials or unnecessary network access. The loader and file format determine what execution remains possible. Restricted loading reduces one class of risk but does not establish safe behavior. Distribution paths and supplier accounts are the next source of uncertainty.

Concrete loading test (hypothetical). The operating mode is isolated model loading, not inference. The input is a supplier package whose recorded digest matches the downloaded bytes. The reference environment has no production credentials, a read-only model directory, and blocked outbound network access. A general object loader attempts to create a custom class and open a network connection. The restricted data-only loader rejects the custom object before model construction. The observed result is a blocked load and one denied network attempt. The restricted loader reduced this execution path without establishing resistance to denial of service, memory-safety faults, or a different file format.

The isolated runner enforces filesystem, credential, process, memory, and network limits while the restricted loader checks the artifact schema. It allows data-only objects and blocks unsupported construction. The runner also records denied side effects. The test reports packages blocked out of all malicious fixtures and valid packages loaded out of all permitted controls. Isolation consumes extra compute and may differ from production. A kernel flaw, resource exhaustion, or another loader can bypass the tested boundary. Recovery destroys the environment, rotates any exposed test credential, and quarantines the artifact. A clean load does not establish safe inference behavior.

7.3 Repository and registry attacks

The correct loader cannot protect an artifact replaced before download. Dependency substitution causes a build or user to obtain an attacker-controlled component in place of the intended one. A look-alike package uses a confusing identifier to attract mistaken installation.

Supply Chain Levels for Software Artifacts (SLSA) models threats where an attacker changes source, dependencies, build steps, or artifacts and connects them to verified build evidence.5 NCSC guidance recommends obtaining third-party AI components from verified developers and monitoring the supply chain through the system life cycle.6

The mechanism may start with a confusing package identifier or a compromised maintainer account. An altered release or transitive dependency can then enter the build. Without primary incident or measurement evidence for these paths in AI repositories, this section does not claim a frequency. It instead motivates byte identity, signatures, pinned versions, and build records.

Concrete substitution trace (hypothetical). The task is to rebuild the accepted model service from a locked component list. The input requests package vector-helper version 2.4 from the controlled registry. A test build with the registry setting removed resolves a confusingly spelled public package at version 9.1. The intermediate record shows a different supplier, download location, and digest. The observed build is rejected because those values do not match the approved reference. The conclusion is that identifier spelling alone cannot establish component identity. This trace demonstrates the check, not the frequency of substitution attacks.

The dependency resolver and registry policy enforce the source decision. They check the exact package identifier, version, registry, supplier identity, and digest before allowing resolution. Lock files, resolution logs, and downloaded digests show the outcome. Tests report substituted packages rejected out of all seeded substitutions and approved packages resolved out of all controls. A controlled registry adds maintenance and can delay updates. A compromised approved account or undeclared installer download can bypass the rule. Recovery revokes the supplier key or account, removes the affected release, and rebuilds from the accepted lock. Passing does not prove the supplier source was benign.

7.4 Artifact integrity and builds

The organization needs evidence that downloaded bytes match an approved release. A digest is a cryptographic hash of an artifact. A signature binds a statement or artifact to a signing key under the verification scheme. A build origin record states how a build platform produced an artifact from a described definition.

NCSC guidance recommends hashes or signatures for model files, data sets, and checkpoints so consuming systems can validate them.7 SLSA defines a signed statement about how a build platform produced artifacts from a build definition.8

Verification recomputes the digest, checks the signature chain and expected identity, then compares the build record with the approved source and build policy. A match establishes identity or build evidence under those assumptions. It does not show that model behavior is acceptable, so behavioral intake tests remain necessary.

Concrete integrity check (hypothetical). The input is a model archive, signature, signer certificate, and build statement. The approved reference specifies supplier key K-7, source revision a41c, and build profile gpu-inference-3. The organization recomputes the archive digest and obtains d92e. The signature validates over d92e, and the build statement reports the expected revision and profile. The observed evidence supports byte identity and the asserted build path under the trusted key and builder. The conclusion does not cover training-data integrity, hidden behavior, or later runtime configuration.

The verifier enforces byte and build identity before admission. It checks the recomputed digest, signing identity, signature, source revision, and build policy, then accepts or quarantines the artifact. Evidence consists of each verification result and the exact trust anchors used. Coverage is verified artifacts divided by all artifacts in the release. Signing and controlled builds add key-management and build cost. A stolen trusted key or compromised approved builder can produce evidence that still passes. Recovery revokes trust, blocks affected digests, and restores an earlier accepted release. Verification does not establish harmless behavior.

7.5 Behavioral intake tests

An artifact can have an accepted digest and still behave harmfully. A behavioral intake test runs clean-task and targeted security cases against an acquired component. The isolated test also monitors side effects before admission.

NCSC guidance recommends security evaluation before release and continuing measurement of model and system behavior.9 NIST’s model-poisoning taxonomy shows that a model artifact can contain malicious functionality even when it loads correctly and its identity is known.10

The test compares behavior with an accepted baseline and monitors network, file, and process activity in isolation. The packet lacks a reproducible source for detecting all unexpected side effects during model and adapter intake. Passing selected tests is limited evidence, not proof of harmlessness. The final decision combines this result with supplier and rollback information.

The evaluator used at intake blocks admission when clean quality, targeted behavior, or side-effect thresholds fail. It reports clean results over all clean cases, targeted failures over all eligible targeted cases, and unexpected events over the complete monitored test run. Broader tests cost compute and analyst time, and isolation may change behavior. A dormant trigger, delayed action, or unmonitored interface can bypass the suite. Recovery quarantines the artifact, destroys the test environment, and restores the last approved version. Passing does not show that every input or side effect was examined.

7.6 Acquisition and change decisions

Admission is a recorded decision whose conditions come from the organization. An acceptance criterion states the evidence and threshold required for use. An approved artifact is the exact version admitted for a stated environment and purpose. A rollback point is a prior accepted state that can be restored.

SSDF supplies shared secure-development practices that producers and purchasers can use in supplier communication and acquisition.11 NCSC guidance recommends alternate solutions for mission-critical systems when suppliers do not meet security criteria and calls for versioned update processes.12

The intake record joins inventory, loader behavior, source identity, build evidence, behavioral tests, license conditions, supplier commitments, and rollback readiness. Approval applies only to the recorded version and environment. A rollback cannot remove every downstream effect of earlier execution. Chapter 8 takes accepted components and examines the platform trusted to execute them.

Concrete admission decision (hypothetical). The task is to decide whether model package 3.2 may enter a restricted test environment. The input record has matching bytes and signature, a data-only load, no unexpected side effects in selected tests, and one unresolved supplier commitment about update notice. The reference criteria require all technical checks plus a documented update condition. The organization approves only isolated evaluation for 14 days and blocks production credentials and network access. The observed result is a conditional admission tied to one version and environment. The conclusion is to reopen the decision if the package, loader, supplier key, or environment changes. Earlier side effects would still require investigation after rollback.

The release controller enforces the conditional admission. It checks the exact artifact, environment, time limit, network policy, credentials, supplier condition, and rollback point before allowing use. Evidence includes the policy decision, deployed digest, denied capabilities, and expiry event. The review reports satisfied criteria over all required criteria, while technical test denominators remain visible separately. Restricted admission consumes an isolated environment and reviewer time. Credential drift or a copy moved to a different environment can bypass it. Recovery stops the deployment and revokes its identity. The accepted artifact is restored, while effects produced before removal remain.

Note

Chapter checkpoint. A supplier model archive has a valid signature and matching digest. Its general loader creates a custom object, while a restricted loader rejects that object. Clean behavior tests pass. Can the organization approve production use?

Conclusion. The signature and digest support byte identity under the trusted signing key. They do not establish safe loading or acceptable model behavior. The rejected custom object shows that loader choice changes the execution path, and clean tests do not cover targeted behavior or every side effect. The defensible decision is limited admission to the tested isolated environment until loader, targeted-test, supplier, update, and rollback criteria are satisfied. Any later version requires a new decision.
