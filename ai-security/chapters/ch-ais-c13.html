13  Confining agent environments

This chapter applies the same authority analysis to browser, coding, and multimodal environments where a model can encounter untrusted instructions and stronger capabilities.

Security question. What changes when an agent can modify software or navigate accounts, and when it can interpret images and audio?

Reference frame. Change the support tool to a browser session or coding workspace. State the session identity, files, secrets, network access, and permitted operations. Keep the distinction between proposed and executed actions visible.

Connection through the book. Apply the instruction, retrieval, and authority analysis from Chapters 10-12 to richer environments. Chapter 9 supplied the general runtime containment matrix. This chapter adds model-selected steps, untrusted workspace state, state drift, and stopping behavior. The resulting traces become end-to-end test cases in Chapter 14.

13.1 Handling workspaces with untrusted content

An untrusted workspace contains files and messages needed for a task but not authorized to direct the agent. Source files, issue text, logs, test output, web pages, and downloads can all contain text that resembles a user instruction. The agent still needs to read that material without letting it replace the employee’s task or expand permitted actions.

Greshake and colleagues showed that external data retrieved during a task can deliver indirect prompt injection to an integrated language-model application.1 OWASP’s 2026 risk description includes retrieved content and tool output among possible injection inputs.[^c13-s01-owasp] These sources cover selected delivery paths and a community risk model. They do not measure every coding-agent workspace or build system.

The hypothetical coding assistant keeps the employee request in a trusted task record and labels repository, issue, and command output as data. Each proposed action still passes the tool contract and policy checks from Chapter 12. A test places conflicting text in an issue and verifies that the agent reports it without executing its request. This input boundary sets the review rules for generated software and dependencies.

The workspace reader preserves source labels, while the action gateway enforces the allowed task from the trusted request, current identity, proposed operation, and destination. The test reports unintended actions over all eligible hostile-workspace cases and clean completion over all ordinary cases. Restricting actions and reviewing conflicts can slow coding work. Encoded instructions, mislabeled trusted files, or an alternate tool route can bypass the tested path. Recovery stops the session and revokes its credentials. Unreviewed changes are discarded before attack and clean cases run again. A blocked request does not prove that the model ignored the instruction.

13.2 Generated software and dependencies

Generated code is a proposed software change whose effect depends on the repository, build configuration, dependencies, and deployment target. Review has to establish what changed, which package identities entered the build, what secrets or permissions are accessible to the code, and which tests cover the affected behavior. Fluency and successful compilation supply little evidence about security.

The NIST Secure Software Development Framework calls for verification of third-party components across their life cycle and for review and testing of executable code.[^c13-s02-ssdf] Pearce and colleagues found security weaknesses among GitHub Copilot suggestions in the scenarios and product version they studied.[^c13-s02-pearce] Their result does not describe later versions, all languages, or workflows with independent testing.

The organization records the generated diff, dependency lock changes, scanner results, tests, reviewer decision, and deployment scope. Package references resolve to approved repositories and fixed identities before installation. Synthetic credentials test for accidental secret disclosure. These checks treat model output like any untrusted change while adding evidence about its generation path. The reviewed artifact can then enter a browser or execution environment with limited authority.

The build service checks the exact diff, dependency identity, test results, secret scan, reviewer decision, and target environment before the release gate accepts a change. The denominator includes every changed file, dependency, required test, and synthetic secret case. Independent review and isolated builds consume compute and release time. Incomplete tests, build substitution, or a dependency that changes behind an accepted label can bypass the record. Recovery blocks deployment and reverts the change. The prior lock and artifact are restored before the full gate runs again. Passing does not prove security outside the covered behavior and environments.

13.3 Browser authority

A browser agent uses authority available through authenticated sessions, open tabs, browser storage, downloads, uploads, and clipboard access. A browser origin identifies a web protection domain based on scheme, host, and port. It helps isolate sites, but it does not express the employee’s business intent to submit a form or transfer data.

RFC 6454 defines origins as protection domains used by the same-origin policy.[^c13-s03-origin] The RFC also documents limits such as ambient authority and dependence on Domain Name System and transport security.[^c13-s03-limits] Those browser facts do not form a complete authorization model for an AI agent using an already authenticated session.

The hypothetical agent records the active tab, origin, session owner, target URL, form fields, upload or download path, and resulting state. Navigation and reading may fit one permission set. Submission, payment, file transfer, and clipboard use require separate checks because current evidence does not yet establish a complete browser-agent control model. The same separation is needed when instructions arrive through images, audio, or video.

The browser controller and action service enforce each operation by checking session identity, active origin, target origin, data movement, resolved object, and user approval. The test matrix reports blocked consequential actions over all forbidden cases and successful read-only tasks over their eligible set. Isolation and confirmation add friction and can break sites that change flows. Pop-ups, redirects, shared browser state, or an unmodeled clipboard path can bypass incomplete rules. Recovery closes the session and revokes its tokens. Transferred data is withdrawn where possible before the origin and action matrix runs again. Passing does not establish that page content was trustworthy.

13.4 Multimodal inputs

A multimodal model can receive text, images, audio, or video in one task. Recognized text from a screenshot and transcribed speech can affect the same context as the employee’s request. The security decision concerns the source and authority of the content rather than the modality used to present it.

NIST’s adversarial machine learning taxonomy covers attack paths for multimodal models across several input types.[^c13-s04-nist] OWASP’s 2026 prompt-injection description states that input may be represented in text, images, audio, or video and may be hidden from the rendered interface.[^c13-s04-owasp] These references describe possible paths without giving a success rate for action-taking systems.

A test image can contain visible task data and hidden or low-contrast instructions. The trace records the original media, extracted text, model input, proposed action, and enforcement decision. Separate modality tests reveal failures in optical character recognition, transcription, or model interpretation. Current literature still needs stronger evaluations of attacks and defenses across these modalities. Confinement limits the damage when interpretation fails.

The media processor records extracted content, and the action gateway enforces the final decision from source labels, current task, proposal, and destination. The denominator includes every eligible image, audio, and video case plus clean controls for each supported form. Extraction and human inspection add compute and delay. Hidden content, parser differences, or a newly supported modality can bypass the corpus. Recovery quarantines the media and stops dependent actions. Prior state is restored where possible before the case runs through the full path again. A denied action does not prove correct interpretation of the media.

13.5 Execution environments

An execution environment is the operating-system and network context in which agent-generated commands run. Its filesystem mounts, process rights, credentials, package installation, network routes, and time or resource limits define the maximum technical effect of a mistake. The environment must match the task rather than the full authority of its host.

NIST container guidance separates risks in images, registries, orchestrators, containers, and hosts, including shared-kernel and unrestricted-network concerns.[^c13-s05-risks] It recommends controls at each layer and discusses separating workloads by sensitivity.[^c13-s05-controls] Saltzer and Schroeder’s least-privilege principle supports granting only the rights needed for the task.[^c13-s05-least] These sources leave the escape resistance of a selected sandbox unproved.

For a hypothetical code repair, the environment mounts one repository copy and supplies a short-lived test credential. It blocks production networks and caps processes, time, and storage. A container shares a kernel with its host, while a virtual machine adds a different isolation boundary at extra cost. Current empirical evidence for agent-specific sandbox escape and credential exposure remains incomplete. The bounded environment supports controlled multi-step action sequences.

Concrete confined-execution trace (hypothetical). The operating mode is an agent repairing a test repository. The task is to change one parser and run its unit tests. The reference environment allows writes under /workspace, access to packages.internal, and use of a test-only credential. It blocks production services and host storage.

The agent reports a partial result and does not publish the change because the success condition required all 19 tests to pass. The conclusion is that the tested mounts, route rule, process limit, and stopping rule constrained this run. It does not exclude unknown escape paths or establish that the code change is secure. The paths, counts, and results are hypothetical.

The runtime checks mounts and process rights. Credentials and destinations are checked at the network gateway, while the job controller applies resource limits. The denominator is every allowed and forbidden operation in the confinement matrix. Stronger isolation adds startup time, memory, and administrative work and can limit required tools. Kernel flaws, device access, or an unmetered route can bypass the tested boundary. Recovery terminates the environment and preserves its events. Exposed credentials are rotated, and the affected image or host is replaced before the matrix runs again. Passing covers only the attempted escape paths.

13.6 Action sequences and verification

A multi-step task can fail even when each command is allowed in isolation. An early action can change the state on which later authorization depends. A retry can repeat a non-repeatable operation, while a tool can report success before the external system settles. The sequence needs expected states, success checks, stopping rules, and a recovery path.

Complete mediation calls for checking each access instead of assuming that an earlier decision covers later access.[^c13-s06-mediation] MCP recommends confirmation for tool invocations and preserving a person’s ability to deny an invocation.[^c13-s06-mcp] These principles do not define transaction handling, state drift, safe retry, or rollback for an agent workflow.

The hypothetical agent reads the current repository state and proposes a patch. It applies the patch in the confined copy, then runs tests. After comparing the resulting diff, it stops before deployment. Each transition records its input state and observed result. An ambiguous result blocks automatic retry until the service can establish whether the action occurred. Evidence for general agent transaction protocols remains open. Chapter 14 treats this full sequence as the system behavior that must pass evaluation before release.

The workflow controller enforces each transition by checking the prior verified state, current authorization, action budget, expected result, and retry key. The test reports correctly stopped or recovered failures over all injected sequence failures and successful completion over clean workflows. Verification adds service calls and can leave work unfinished when external state settles slowly. Eventual consistency, missing result fields, or an irreversible side effect can defeat automatic recovery. Recovery resumes from the last verified state when possible. Otherwise, it applies a supported compensating action or transfers the case to an authorized person. Passing one sequence does not establish safe composition for other tools.

Note

Chapter checkpoint. A hypothetical coding agent must repair a parser and install an approved dependency. It must then run tests and return a patch. The repository also contains issue text instructing the agent to upload credentials. What execution and verification record supports a bounded result?

Answer. Keep the employee’s repair request as the trusted task and record the issue text as untrusted workspace data. Mount only the repository copy, provide a short-lived test credential, permit only the approved package destination, block production routes, and set process, time, and storage limits. Record each proposed command, policy decision, filesystem change, network result, and test outcome. Return the patch only if the stated tests pass, and retain the failed upload attempt as evidence of enforcement. This supports the observed run and does not establish that the sandbox has no unknown escape path.

The chapter retains explicit evidence gaps for coding workspaces, browser agents, multimodal attacks, sandbox performance, and multi-step transactions.
