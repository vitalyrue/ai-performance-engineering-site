11  Control retrieved context

A retrieval review treats document ingestion, current access, provider disclosure, and deletion as authorization and evidence problems as well as search problems.

Security question. Can the system retrieve the right information without exposing or accepting the wrong information?

Reference frame. The reference setting uses the organization index and retrieval service with an employee identity, a forbidden personnel record, a revoked business record, and a readable hostile external document. The managed-retriever comparison locates equivalent policy checks and evidence.

Prompt injection becomes more dangerous when retrieval adds documents the user did not write or inspect. Ingestion, current permission, provider disclosure, and instruction handling therefore need separate checks.

11.1 Retrieval pipeline

Retrieval-augmented generation (RAG) is useful when an answer depends on information outside the model’s fixed parameters. The security decision is which stored material may become part of the current user’s model input. A document chunk is a bounded passage prepared for retrieval. Chapter 3 defines the embedding used for similarity search. An index stores searchable mappings. A retriever returns candidate chunks, a reranker reorders them with another score, and context assembly selects and formats text for the model call.

Lewis and colleagues introduced a research architecture that combined a sequence-to-sequence model with a dense document index and conditioned generation on retrieved documents.1 NIST later illustrated RAG as an application that retrieves external information and adds it to the model input.2 These sources establish the basic flow. They do not describe every parser, filter, cache, or reranker in a deployed service.

For the hypothetical organization, the trace records the query, employee identity, candidate chunk identifiers, ranking result, access decision, assembled context, model version, and answer. A failure at any step can change what the model sees without changing the user’s words. The next section starts at the first such step: admitting a document to the index.

The retrieval service and context builder enforce which candidates enter the model request by checking query state, chunk identity, current permission, version, and context limits. The test reports permitted chunks included and forbidden chunks excluded over every ranked candidate. Extra checks add latency and can lower recall when records are incomplete. A stale cache or missing source link can bypass the decision. Recovery removes the affected index version and clears derived context. The index is rebuilt from approved sources before the query set runs again, and its result does not prove that omitted relevant material was safe or complete.

11.2 Document ingestion controls

Before retrieval can enforce access or show evidence, ingestion has to preserve what the source is and which version entered the index. An ingestion job fetches a file and parses its contents, sometimes with optical character recognition. It then creates chunks with metadata and writes the index records. A transformation can drop a label or misread content. A hostile file can also attack the parser.

International secure AI guidance recommends checking and sanitizing inputs and documenting data, models, and system decisions across development.3 Greshake and colleagues showed that attacker-controlled external content could carry instructions into applications that retrieve it.4 The first source gives a broad development practice, while the second demonstrates selected delivery paths. Their evaluated scope excludes many office files, archives, images, and parser products.

The hypothetical ingestion record links each chunk to the source system, source object, version, parser, extraction time, and access labels. Parser isolation and file-type checks limit damage during processing, while retained identity supports later authorization. Evidence for hostile document handling and metadata preservation remains incomplete, so those controls require system-specific tests. The retained labels become the inputs to permission checks in the next section.

The ingestion service admits content to the index only after checking file type, size, source identity, parser result, and required metadata. The test denominator includes every submitted file and every produced chunk, with rejected files and metadata losses reported separately. Isolation and repeated parsing consume compute and can delay updates. Parser flaws, nested content, or dropped labels can bypass the intended checks. Recovery quarantines the file and removes its chunks. If the parser is affected, it is replaced before the index is rebuilt. Passing does not establish safety for file forms outside the test corpus.

11.3 Permissions during retrieval

Search relevance does not answer whether the current employee may read a result. The retrieval service needs the employee’s verified identity, the resource identity for every candidate chunk, and the current access rule. Tenant and department labels can narrow search, but the authoritative decision still belongs to the organization’s access-control system.

NIST zero trust guidance calls for least-privilege, per-session access to resources and states that access to one resource does not grant access to another.5 It also describes decisions that use the subject, requested resource, service, and device rather than network location alone.6 This architecture principle does not prove that an index filter matches the source system’s rules.

In the running path, the retriever finds candidates and resolves each chunk to its source object. It then submits the current subject and resource to an access decision. Context assembly receives only allowed text. A second check before response delivery protects against stale caches or changed permissions. This mechanism depends on accurate chunk-to-resource mapping, which ingestion must preserve. Allowed content still needs a separate trust check.

Example

Concrete permission trace (hypothetical). The operating mode is retrieval-based inference for employee E17. The task is to answer a question about the organization’s travel policy. Similarity search returns three candidate records before access checks.

Context assembly records only chunk-44 and chunk-17. Before delivery, the service checks both source objects again and receives two allow decisions. The observed answer cites those objects and contains no marker placed in the denied draft. The conclusion is that the tested request enforced current source permissions after ranking. It does not prove that every chunk is mapped correctly or that a later permission change reaches all caches. Identities, scores, and records are hypothetical.

The access service makes the allow or deny decision from the current employee and source object, and the context builder accepts only allowed chunks. The permission suite reports forbidden chunks excluded over all forbidden candidates and allowed chunks returned over all allowed candidates. Rechecking increases request latency and can reduce availability when the policy service fails. Incorrect chunk mapping or a stale derived store can bypass it. Recovery revokes access and invalidates caches. Affected chunks are removed before the suite runs again, whose result does not prove tenant separation for untested identities or stores.

11.4 Prevent knowledge poisoning

An authorized document can still be false, misleading, or written to steer the model. Knowledge poisoning covers changes to source text, chunks, metadata, or ranking that make manipulated material influence an answer. Indirect prompt injection is the narrower case in which instructions arrive through external content rather than the direct user prompt.

NIST describes indirect prompt injection through external resources and places it in an adversarial machine learning taxonomy.7 Greshake and colleagues demonstrated manipulated summaries, connected actions, and persistent influence in selected applications.8 OWASP’s 2026 risk description also lists retrieved content, tool output, media, and persistent memory as possible input paths.9 These sources establish feasible mechanisms, not a prevalence estimate or universal success rate.

The hypothetical test inserts a readable external document containing a conflicting instruction and a false business fact. The trace records ranking exposure, data labeling, answer content, and any resulting action. Source signatures and editorial controls can help with origin, while instruction handling and corroboration address different failures. The resulting paths define where sensitive information might leave its allowed boundary.

The ingestion service can quarantine unapproved sources, and the answer path can require corroboration or abstain when trusted sources conflict. The test reports harmful answers or actions over all eligible poisoned cases and preserves clean-task completion separately. Review and corroboration add delay and may exclude timely information. A trusted writer, compromised source system, or false statement repeated across sources can bypass origin checks. Recovery withdraws the source and clears derived entries. After the record is corrected, affected questions run again. A blocked payload does not establish that the knowledge is true.

11.5 Retrieval disclosure paths

Disclosure can occur before, during, or after model generation. An overbroad connector may ingest material the application should never see. A stale permission filter may place forbidden text in context. A shared cache can return another user’s result, while an answer, link, or proposed tool call can carry sensitive text to a new destination.

OWASP separates prompt injection, sensitive-information disclosure, excessive agency, and improper output handling because an input compromise and its consequence can occur in different components.10 The indirect-prompt-injection study includes tested cases where manipulated content caused information to move through links or connected application behavior.11 The examples depend on the permissions and rendering behavior of those systems.

An end-to-end disclosure test marks synthetic sensitive text at the source, then watches ingestion, retrieval, context, answer rendering, cache keys, network requests, and tool proposals. This locates the component that crossed the boundary instead of assigning every leak to the model. Direct evidence for cross-user cache leaks and connector overreach in deployed RAG systems remains limited. The next section checks the evidence supporting an allowed answer.

The connector, access service, cache, renderer, and action gateway each enforce a separate boundary using source, user, destination, and request state. The measurement reports synthetic disclosures over all eligible canary cases and clean completions over all ordinary cases. End-to-end tracing costs storage and can itself expose sensitive content. An uninstrumented cache, alternate output channel, or reused identifier can hide a leak. Recovery disables the route and revokes affected access. Reachable copies are purged before the canary suite runs again. A clean canary result proves only that the monitored paths did not expose those markers.

11.6 Check grounding quality

A fluent answer may cite a real document and still misstate it. A grounded answer is one whose material claims are supported by the retrieved evidence used for that response. Citation support is narrower than source authority: it checks whether the cited passage entails the claim, while authority and freshness ask whether the source itself should be trusted for the decision.

The NIST Generative AI Profile includes false statements and false citations under confabulation risk and recommends comparison with known ground truth through human review, automated evaluation, or both.12 In the original RAG study, changing the Wikipedia index year reduced accuracy for answers that had changed between index versions.13 That experiment shows that collection freshness can affect an answer, not that every newer document is correct.

The application can return source identifiers with exact passages. It compares each important claim with those passages and flags conflicts. When support is missing, it can abstain. A separate rule chooses which version is current for the business decision. Automated citation checks also need validation because they can repeat the model’s error. These checks remain dependable only while deletion, correction, and permission changes pass lifecycle tests.

Example

Concrete support check (hypothetical). The operating mode is answer evaluation against the exact retrieved passages. The task requests the reimbursement limit. Context contains travel-policy-v5, which states a limit of 150 currency units, and an older FAQ, which states 120.

The expected result gives 150 and identifies the current policy. It omits or flags the two unsupported claims. This conclusion concerns support from the assembled context under the stated version rule. It does not establish that the current policy is authentic or that the automated checker will detect every mismatch. The documents and values are hypothetical.

The answer service enforces the support rule by checking each material claim against the exact retrieved passage and the current-version decision. The denominator is every material answer claim, with supported, contradicted, and unsupported counts reported separately. Abstention and human review reduce speed and may lower answer coverage. A plausible claim, weak automated grader, or authentic but false source can bypass the check. Recovery withdraws the answer and corrects or replaces the source. Derived state is rebuilt before the question runs again, while high citation support remains insufficient evidence of source authority or factual truth.

11.7 Lifecycle permission tests

Retrieval security changes over time even when application code is unchanged. A document can be corrected or deleted. An employee can lose access, and a connector can be revoked. An old answer can remain in a cache. The operational decision is how quickly every derived store must reflect each change and what evidence shows that the old state is gone.

The NIST Generative AI Profile recommends tracking data-set deletion and correction and examining effects on records about content sources.14 NIST media-sanitization guidance distinguishes the sanitization method from verification and validation of its result.15 Media sanitization does not cover every logical copy, embedding, supplier backup, cache, or model parameter.

A lifecycle test creates and indexes a synthetic document. It confirms authorized retrieval before removing the employee’s access, then repeats the query against indexes and caches. A second test deletes or corrects the source and checks each derived store against a stated deadline. Current literature does not supply one universal proof of deletion from all RAG stores, so the organization records inaccessible supplier evidence as a limit. Chapter 12 now takes this tested context and asks which proposed actions may execute.

The source connector and store managers enforce revocation or deletion across each tracked derived store. The test reports stores meeting the deadline over all known stores and queries that still return old content over all revocation cases. Short deadlines increase processing cost and can interrupt service during rebuilds. An unregistered cache, supplier copy, or model parameter can remain outside the route. Recovery blocks access before tracked stores are purged or rebuilt. The organization requests supplier action and retests until the deadline is met. Passing cannot prove deletion from a component the organization cannot inspect.

Note

Chapter checkpoint. A hypothetical employee submits a request for the current travel limit. Search ranks one allowed policy, one forbidden draft, and one allowed but older FAQ. What must the retrieval record show before the answer can be accepted?

Answer. Link each chunk to its source object and version, record the employee identity, preserve the ranking, and show the access decision that excluded the forbidden draft. Record the final assembled context and repeat authorization before delivery. Then compare each material answer claim with the exact allowed passages and apply the organization’s rule for choosing the current version. This evidence supports the tested answer path. It does not establish source authenticity, complete cache invalidation, or general grounding accuracy.

Current sources do not establish an end-to-end control for every retrieval path.
