16  Recovering from AI incidents

This chapter treats an AI incident as an evidence and recovery problem, distinguishing model error, policy failure, hostile content, account compromise, and infrastructure compromise.

Security question. How does an organization contain an AI incident and know that recovery is complete?

Reference frame. Investigate one organization incident packet, with document versions, identity decisions, tool requests, and incomplete supplier records. A second packet covers a compromised organization-operated worker.

Connection through the book. Walk backward from the observed consequence and test competing explanations. Reuse Chapters 3, 9, 11, 12, and 15 to contain the path and verify recovery before returning to service.

16.1 Incident triage

A security event is an observable occurrence relevant to security. An incident is an event that meets the organization’s criteria for response. Triage separates ordinary model error from policy violation, hostile-content influence, account or infrastructure compromise, disclosure, and resource abuse. Classification matters because each path needs different evidence and containment.

NIST distinguishes cybersecurity events from incidents and places validation, categorization, prioritization, and incident declaration in the response process.1 It also presents response as part of continuing cybersecurity risk management rather than a separate linear phase.[^c16-s01-cycle] The profile does not supply AI-specific categories or one universal declaration threshold.

The hypothetical responder starts from a routed alert and checks the affected asset, observed outcome, identities, time window, system version, and supporting trace. A low-quality answer with no boundary violation remains a model-quality issue. A forbidden disclosure or unauthorized action enters incident handling. The declaration record states confidence and missing evidence. Preservation begins before containment changes volatile state.

The incident lead enforces triage by checking the event against documented criteria and affected assets. Observed outcomes and available evidence determine whether it is declared, downgraded, or escalated. The denominator is every routed event, with declarations, later reclassifications, and time to decision reported separately. Rapid triage consumes responder capacity and can interrupt service. Missing traces or an incorrect model-error label can hide an incident. Recovery reopens the case and preserves newly found evidence. Any containment change includes the reason for reclassification. A correct category does not prove complete scope.

16.2 Evidence preservation

Evidence preservation keeps records available and trustworthy enough to reconstruct the event. Relevant material can include prompts and outputs with retrieved document versions. Policy decisions, tool traces, model and code identities, process state, network events, credentials, and supplier records may also matter. Some data may already be missing or inaccessible, which belongs in the evidence record.

The NIST incident-response profile calls for recording response actions and preserving the integrity of incident records and data.[^c16-s02-ir] NIST forensic guidance begins with identifying, labeling, recording, and acquiring relevant data while preserving integrity.[^c16-s02-forensics] The forensic publication predates current AI systems and does not supply an AI evidence list or legal procedure.

The responder copies volatile records first and records the acquisition time with its method. Stable files receive hashes. Access is restricted while original versions are preserved. Provider records are requested through the available contract, while unavailable fields remain explicit. Hashes can reveal later file changes but cannot prove that the original record was complete or truthful. Preserved artifacts provide the basis for timeline and scope analysis.

Concrete preservation record (hypothetical). The operating mode is incident response to request req-882, which attempted an unapproved external connection. The preservation task starts before the worker is terminated because process and memory state are volatile.

For each stable export, the evidence register identifies the collector, time, method, access restriction, and file hash. It marks the provider trace as missing rather than treating silence as proof that no provider event occurred. The conclusion is that the listed artifacts can support a bounded timeline and integrity check. The shortened identifiers and results are hypothetical, and hashes cannot show that the original logs were complete.

The collection process preserves evidence only after checking each expected source, acquisition method, time, integrity record, access rule, and storage result. The coverage denominator is all sources required by the incident map, with acquired, unavailable, overwritten, and untrusted items separated. Preservation costs storage and can retain sensitive content longer than ordinary operations allow. Volatile loss, tampered source logs, or inaccessible supplier records can bypass the record. Recovery captures later snapshots and requests external evidence. Weak artifacts receive restricted use when conclusions are updated. A matching hash proves only that the captured file did not later change.

16.3 Investigation and scope

Investigation links the initial entry point to affected identities and accessed records. It then checks executed actions and modified artifacts. Observed harm is recorded separately. A timeline orders evidence from application, identity, retrieval, tool, provider, host, and network sources. Competing explanations remain under consideration until the records distinguish them. Attribution confidence remains separate from confidence about the technical path.

NIST forensic guidance separates collection, examination, analysis, and reporting across files, operating systems, networks, and application data.[^c16-s03-forensics] The NIST incident-response profile includes root-cause analysis as a response outcome.[^c16-s03-root] These sources provide process structure without making attribution certain or defining AI-specific artifacts.

In the hypothetical case, the team correlates a hostile document version with its retrieval, the model request, a proposed tool call, the policy decision, and the external result. It checks whether account compromise or a changed tool service could produce the same trace. Each conclusion cites supporting and conflicting records. The scoped identities, components, sources, and destinations define the containment set.

The case lead accepts or rejects each path hypothesis after checking its required events against the preserved timeline. The denominator is every system, identity, record, and destination reachable from the supported path, with examined and unresolved items reported separately. Wider scope consumes time and delays restoration. Missing telemetry, false correlation, or a second entry point can leave the scope too small. Recovery expands containment and collects new sources. The revised timeline then supports another review of affected conclusions. A coherent path does not establish actor attribution or exclude concurrent activity.

16.4 Containment

Containment reduces ongoing harm while preserving enough state for investigation. Available actions include revoking credentials and suspending a tool. The organization can also isolate a worker or block a destination. Freezing an affected data source and narrowing user access address other paths. The sequence depends on which path is active and whether a change would destroy volatile evidence.

The NIST incident-response profile calls for incidents to be contained and eradicated.[^c16-s04-ir] International secure AI guidance recommends preparing incident procedures and mechanisms for responsible deployment and operation.[^c16-s04-ncsc] These outcome statements do not choose the right containment action or sequence for the current incident.

For the hostile-document case, the organization first preserves the source and traces, then disables the affected connector and action credential. If a worker compromise remains possible, it isolates that workload and blocks external routes. Each containment action has an owner, expected effect, validation check, and reversal condition. Once the path is stable, recovery can restore known assets and permissions.

The identity service and connector manager revoke access according to the supported path. Destination blocking occurs at the network gateway, while the workload controller isolates execution. The measure is confirmed blocked paths over all known active paths, with service impact and unresolved routes recorded beside it. Broad containment interrupts legitimate work and may destroy volatile state if applied too early. Unknown credentials, alternate connectors, or a compromised control plane can bypass local action. Recovery widens isolation and rotates related access. Affected control components are replaced before each path is validated again, while blocking known routes remains insufficient evidence that the incident has ended.

16.5 Recovery verification

Recovery restores a known state and demonstrates that the incident path no longer works. Affected state may include application code and model packages. System prompts, indexes, caches, agent memory, credentials, tool schemas, and access policy may also require restoration. Service availability alone cannot establish recovery if the same disclosure or action remains possible.

The NIST incident-response profile calls for checking restoration assets before use and verifying restored systems. It also calls for confirmation of normal operation before recovery is declared complete.[^c16-s05-ir] The NIST Generative AI Profile recommends post-incident review and practice of response plans.[^c16-s05-genai] These sources leave AI-specific checks for indexes, caches, memory, and authorization to the recovery design.

The hypothetical recovery rebuilds the index from approved source versions and clears affected caches. It rotates credentials before restoring reviewed configuration and rerunning the original failure trace. It also runs clean task cases to confirm that the service still works. Each affected asset has a test and expected result. Passing those tests supports a bounded recovery decision and provides evidence for follow-up actions.

The recovery owner authorizes return to service only after checking every affected asset, original failure case, clean task, identity, destination, and remaining evidence gap. The denominator is all required recovery checks, with pass, fail, blocked, and unavailable results kept separate. Rebuilds and repeated tests extend downtime and can lose useful cached state. An untracked copy, unchanged supplier component, or weak regression case can preserve the failure. Another failed check rolls back the attempted restoration and narrows service. The missing state is corrected before the gate runs again. Passing supports the tested state only.

16.6 Follow-up and retirement

Follow-up turns incident evidence into changes to controls, tests, contracts, and training. It also decides which records remain for legal, operational, or research purposes and which data and access must be removed. Service retirement includes revoking identities and disabling connectors. It also ends supplier access and checks known derived stores.

The NIST incident-response profile integrates lessons and improvement into risk management after response and recovery.[^c16-s06-lessons] NIST media-sanitization guidance separates the sanitization decision from verification and validation of the result.[^c16-s06-media] Media sanitization alone cannot prove deletion from hosted-model parameters, supplier backups, indexes, or distributed caches.

The organization assigns each corrective action to a responsible owner and links it to a test or contract result. Retention and notification follow current sector and jurisdiction rules, which require separate legal sources. Supplier exit evidence records what the organization can verify and what remains outside its visibility. The incident record also shows why harmful activity does not by itself prove that AI caused or improved it. Chapter 17 changes the object of analysis from an AI system under attack to an attacker using AI, then applies the same separation of observation, inference, and unsupported attribution.

The closure owner chooses retention, deletion, retirement, or reopening after checking corrective-action evidence, access revocation, supplier response, and applicable obligations. The denominator is every agreed follow-up action and every service identity or connector in the retirement record. Longer retention raises storage and privacy cost, while early deletion can weaken later investigation. An unlisted supplier copy or forgotten credential can bypass retirement. Recovery extends the hold when justified and revokes remaining access. Missing evidence is requested before closure checks run again because administrative closure does not prove deletion from systems outside organizational visibility.

Note

Chapter checkpoint. A hypothetical hostile document influenced request req-882, which then attempted external egress. The worker was stopped, but the provider trace is unavailable. What response record supports containment and recovery?

Answer. Preserve volatile process and connection state first, followed by application, retrieval, policy, tool, runtime, identity, and network records. Record acquisition details, hashes for stable exports, access limits, and the missing provider evidence. Reconstruct the path before revoking credentials and isolating the affected worker. Rebuild the index from approved document versions, clear affected caches, rotate exposed credentials, and rerun the original failure trace plus clean tasks. Recovery is supported only when the prohibited path fails and intended work still succeeds. Missing provider evidence remains a limit on scope and attribution.

The chapter retains explicit limits for supplier evidence, logical deletion, and jurisdiction-specific notification duties.
