3  Control data use

A data-use record states which organizational data may enter each AI path, which party receives it, and which evidence tests retention and deletion.

Security question. Which data may enter the system, and how is its use controlled over time?

Reference frame. The organization stores customer, personnel, policy, and external-source records. It operates ingestion and indexing but sends selected context to an external model. The comparison covers a supplier-operated assistant and a managed platform that also operates selected components.

The asset map now gains data categories, permitted purposes, recipients, and copies. Those records also constrain what query responses and retrieved documents may expose.

3.1 Data classes and purposes

Before approving an AI path, the organization needs to know what data will cross it and why the processing is needed. It also records which party will receive the result. Data classification groups records by the harm that disclosure, alteration, or loss could cause. A processing purpose states the reason for a use. The receiving party is the organization or service that obtains the data, including an external model provider.

The NIST Privacy Framework separates the inventory of systems, people, data actions, purposes, and processing environments from the policies that govern them.1 Its Generative AI Profile also recommends checking training-data use for intellectual-property and privacy risk.2 These sources structure the decision but do not determine whether a specific use is lawful.

A useful record identifies the data category and processing purpose. It also assigns a responsible internal role and lists every receiving party. That record supplies the allowed-source and purpose rules for collection and preparation.

The context-assembly service enforces this record for model requests. It checks the field classification, purpose, recipient, and current user before allowing, removing, or blocking each field. The serialized request and policy decision are the observable evidence. Coverage is the number of classified fields checked divided by all fields found in the tested request set. Classification and review add maintenance work and can remove useful context. An unclassified derived field or another transfer path can bypass the rule. Recovery disables the route and identifies copies created by affected requests, without proving lawfulness or completeness beyond the tested data and path.

Example

Concrete classification trace (hypothetical). The operating mode is inference through an external provider. The task is to draft a response to a customer support request. The input contains a ticket number, account email, free text, and an internal fraud flag. The reference record permits the ticket number and free text for response drafting. The email remains inside the organization, and the fraud flag is excluded from this purpose. Context assembly keeps the ticket text, substitutes an internal case identifier for the email, and drops the fraud flag. The observed serialized request contains only the permitted fields. The conclusion is limited to this data class, purpose, recipient, and tested request path.

3.2 Collection rights

An approved purpose for the system does not show that every training or evaluation record was collected with permission for that use. A source record identifies where a data item came from and the permission asserted for its use. Data minimization removes fields or records that the stated purpose does not require. An evaluation holdout is a test set kept outside parameter updates so it can measure behavior on unseen cases.

NIST treats data actions, purposes, elements, and processing environments as inputs to privacy-risk management.3 NIST also recommends examining whether proprietary or sensitive training data are used consistently with applicable requirements.4 In common practice, a preparation job reads approved source records and filters disallowed fields. A documented rule controls duplicate removal before the job writes separate development and evaluation outputs.

The current evidence packet does not yet support a general claim about how much overlap between training and evaluation data distorts a score. The organization should treat overlap detection as an open test requirement. The resulting prepared records now have to be followed through each distinct data path.

The job that prepares data enforces source and purpose rules before writing training or evaluation outputs. It checks the asserted permission, required fields, duplicate rule, and holdout assignment, then admits, changes, or quarantines a record. Job logs, rejected-record reports, and output digests show the decision. Coverage is reviewed records divided by all records in the prepared version, with overlap counts reported against both training and evaluation totals. The checks add processing and review cost. Incorrect source assertions or similarity outside the duplicate rule can bypass them. Recovery quarantines the version and rebuilds from the last accepted source set, without proving that the asserted permission was legally valid.

3.3 Separate data paths

Permission to use a source record for one purpose does not automatically cover training copies, prompt records, embeddings, telemetry, or logs. A training corpus changes model parameters during training, while a prompt record affects one inference request. An embedding is a numeric representation used for comparison or retrieval. Telemetry records operational events such as latency, errors, or resource use.

The Privacy Framework calls for an inventory of data actions, data elements, purposes, and internal, cloud, or third-party processing environments.5 Applied to the reference system, the inventory follows source files into preparation jobs and their outputs. Separate entries cover indexes, embeddings, prompts, retrieved context, feedback, telemetry, and logs. This AI-specific list is a system decomposition based on common architecture rather than a structure prescribed by the framework.

Derived forms should remain linked to their source and purpose because transformation does not by itself remove sensitive information. The packet lacks a reviewed source that traces every listed form through one representative application, so the map remains a hypothesis to verify against the running application. Each resulting path becomes the subject of a separate disclosure-control decision.

The copy register is checked by the release reviewer before a new data path is enabled. The reviewer allows the path only when its source, purpose, recipient, retention rule, and recovery owner are present. Evidence consists of the approved row, effective configuration, and a traced sample. Coverage is mapped copies divided by all copies found by the selected storage and request trace. This inventory costs discovery and maintenance time. Hidden telemetry, temporary files, or provider replicas can escape it. Recovery closes the path and traces affected source IDs through known copies. A complete register does not prove that no unobserved copy exists.

3.4 Data disclosure controls

Once the paths are visible, the disclosure policy states which identity may send each field and identifies the permitted recipient. A connector scope is the set of resources and operations granted to an integration. Redaction removes or masks selected content. Pseudonymization replaces direct identifiers while retaining a controlled way to reconnect records. A data loss prevention check inspects content or metadata against disclosure rules.

The Privacy Framework calls for managed permissions and authorizations based on least privilege and separation of duties.6 The UK National Cyber Security Centre (NCSC) and its partners recommend controls before potentially sensitive information is sent to an external application programming interface (API).7

These controls work at different points. Permissions limit who can request data, while connector scopes restrict what a service can fetch. Content checks apply to the permitted transmission. Because detection quality depends on the data type and rule set, the absence of universal performance evidence means that secret scanning, redaction, and pseudonymization each require tests against representative records. The next question is how long protected copies survive.

Example

Concrete disclosure test (hypothetical). The operating mode is retrieval followed by inference. The task is an authorized contract summary. The input contract contains one seeded test credential and a customer identifier. The employee may read the document, but the disclosure rule excludes both fields from reaching the external model. The connector returns the document, the content check removes the credential, and pseudonymization replaces the customer identifier with customer-17. The observed serialized request lacks the credential and direct identifier. The conclusion is that the tested rules changed this transfer. It does not establish their detection rate for other secret formats or identifiers.

The disclosure service records blocked seeded items out of all seeded items and accepted permitted fields out of all permitted controls. It also records added latency and manual-review volume. More aggressive detection can reduce exposure while increasing false blocks and loss of useful context. Encoded secrets, novel identifiers, or a connector that sends data before the check can bypass the control. Recovery disables that connector and revokes its credential. Following the affected request IDs into the copy register still does not show that every sensitive value is detectable.

3.5 Set retention and deletion

A retention rule is incomplete if it mentions only the original file. A retention period specifies how long a copy may remain. Logical deletion removes ordinary access to a record, while media sanitization makes access to target data on storage media infeasible for a specified level of effort. A derived artifact is a later object, such as an index or embedding, created from source data.

NIST defines media sanitization by the effort needed to recover target data and treats sanitization as a managed program.8 That definition is useful for storage media but does not establish deletion from a provider replica, conversation history, index, cache, backup, or learned parameter.

The mechanism is a copy register in which each source record points to active stores, derived artifacts, provider-held copies, backups, expiry rules, and the evidence available after deletion. This register exposes an evidence gap because the packet does not yet supply a general method for verifying erasure across all those locations. A deletion request or interface response remains weaker than recovery testing, storage records, and provider evidence taken together. Those distinctions determine what the review must test.

Example

Concrete deletion trace (hypothetical). The task is to remove customer record C-104 after its approved retention period. The input is a copy register with the source file, search index entry, cached passage, conversation record, daily backup, and provider request ID. The reference rule requires immediate logical deletion, cache invalidation within one hour, backup expiry after 30 days, and provider deletion evidence under the contract. The source, index, cache, and conversation checks return no accessible record. The backup remains until day 30, and the provider returns only a deletion receipt. The observed result supports removal from tested organization stores while leaving backup expiry and provider erasure as bounded claims.

A deletion coordinator enforces expiry across the copies that the register can address. It checks the source identifier, copy type, retention rule, legal hold, and provider obligation, then deletes, expires, or preserves each copy. Evidence includes deletion results, failed operations, backup expiry records, and provider receipts. Coverage is completed deletion actions divided by all copies listed for the request. Longer backup windows reduce recovery risk but extend retention. An unregistered replica or learned parameter lies outside this mechanism. Recovery retries failed actions and disables access to unresolved copies. Missing provider evidence is escalated. Completion does not prove physical erasure from an external system.

3.6 Data use review

Policies describe intended handling, but the review tests whether the running system follows them. Configuration evidence records effective settings and permissions. Contract evidence records supplier commitments. A handling test submits controlled data and observes where it appears, who can retrieve it, and whether expiry changes that result.

NIST Privacy Framework Profiles compare current outcomes with target outcomes so an organization can identify gaps and plan improvements.9 NCSC guidance asks providers to explain where and how user data may be used, accessed, or stored.10 A statement about design or settings does not prove that the effective configuration or supplier behavior matches it.

A review compares policy and contract with effective configuration, access logs, and controlled tests. In a hypothetical employee disclosure test, a unique marker first enters a restricted document. The reviewer queries only approved paths before searching authorized logs and stores for that marker. The result is evidence about the tested path and time, not every future request. Chapter 4 uses this controlled, traceable data as the input to training-integrity analysis.

The review owner can keep, change, or suspend a data path after comparing those records. The handling test reports locations containing the marker out of every location in the copy register, along with permitted control requests that still work. Repeated tests consume model calls, log searches, and reviewer time. A path omitted from the register or a provider store hidden from the organization limits the result. Recovery suspends the route, corrects configuration, and starts deletion and incident work for the affected copy IDs. A passing review does not establish future supplier behavior.

Note

Chapter checkpoint. A support assistant uses an external model. Its source ticket contains an email address, free text, an internal fraud flag, and a seeded test credential. Specify the allowed processing purpose, the fields sent to the provider and every copy to track. Include one handling test.

Answer. Permit response drafting from the free text and a case identifier. Keep the email and fraud flag inside the organization, and reject or remove the credential before transfer. Track the source ticket, prepared record, retrieval index, cache, serialized request, conversation history, logs, backups, and any provider copy. Submit a controlled ticket containing the marker, then inspect authorization decisions, the exact provider request, accessible stores, expiry results, and provider evidence. A passing run supports only the tested fields, path, configuration, and time. It does not prove that every identifier is detected or every external copy is erased.
