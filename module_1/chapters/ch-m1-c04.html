4  Evaluation-based system improvement

Chapters 1 through 3 produced a versioned model request and an auditable context assembly path. One convincing answer still cannot show that a change helps across users, slices, repeated trials, and operational constraints. Every optimization becomes an experiment with fixed inputs, explicit scoring, uncertainty, and a decision.

The evaluation loop connects task specifications, golden examples, baselines, slices, uncertainty, and release gates; an isolated score needs explicit scope and failure costs before it can support a decision.

4.1 Evaluation criteria: success and failure

A deterministic program often has one expected output for one input. Language tasks may have many acceptable answers, human raters can disagree, and a response can improve one property while harming another. Evaluation therefore begins by naming the dimensions and failure costs the product actually cares about.

An answer can be factually correct but too slow, unsafe, unsupported, or expensive. It can satisfy an automated text metric while violating the user’s intent. Model versions and benchmarks also change quickly, so a public benchmark score cannot replace product-specific evaluation criteria.

  • Evaluation: A repeatable procedure that runs defined inputs through a defined system version, scores observable outcomes, and supports a named decision.

  • Trial: One attempt at one evaluation task. A stochastic model or agent can produce different outcomes across trials.

  • Slice: A meaningful subset of evaluation cases, such as language, customer tier, risk level, query type, document length, or tool requirement.

Those definitions divide the evaluation specification into four observable families:

  • Quality: correctness, relevance, groundedness, completeness, style, or task success.
  • Operational behavior: latency, throughput, failure rate, token use, and monetary cost.
  • Safety and policy: refusal behavior, harmful content, authorization, privacy, and escalation.
  • Reliability: variance across trials, environments, model versions, and data slices.

A multidimensional evaluation specification links product behavior to separate observable dimensions. Quality may include correctness, relevance, completeness, clarity, and grounding. Operations add latency, cost, throughput, and availability. Safety and policy add refusal quality, authorization, privacy, and escalation. Each dimension has its own measurement method and decision rule.

Aggregation can summarize ordinary variation, while veto conditions protect non-negotiable behavior. A high average cannot compensate for exposing private data or executing an unauthorized action. The evaluation record therefore keeps per-example scores and slice labels alongside any headline metric, allowing a release decision to distinguish broad improvement from a severe local regression.

4.2 Golden evaluation sets

A multidimensional evaluation specification names the product outcomes that matter, but it does not yet supply the cases on which they will be measured. A convenient sample can overrepresent easy cases and hide the failures that carry the greatest product harm. A golden set provides versioned test cases to evaluate whether model outputs comply with product requirements across real traffic, labeled outcomes, edge cases, and critical slices.

A golden set is a versioned collection of evaluation tasks with expected outcomes or grading criteria. It can include human-authored cases, sampled production records, synthetic variations, and adversarial inputs. Production records should be de-identified or handled under the product’s privacy controls.

Start from decisions. A support-routing system needs ordinary FAQ cases, legitimate escalations, ambiguous cases, out-of-scope requests, multilingual messages, and policy-conflict cases. If missing an escalation is costly, oversample that slice or report it separately; do not let its small traffic share disappear inside an average.

Synthetic evaluation data

Synthetic cases cover known dimensions and failure hypotheses that are underrepresented in available production data. They are useful when a new feature lacks traffic, a rare safety case must be exercised, or controlled counterfactuals are needed.

Start from a written specification, generate candidate cases, remove duplicates, and have people or deterministic rules validate the labels. Synthetic cases expand coverage, while real failures keep the suite connected to actual product behavior.

A limit to keep in mind: A generator reproduces its own assumptions and may miss real user language or operational constraints.

Hidden stratification

An overall score can rise while a critical subgroup declines. Publish important slice results beside the headline metric and preserve enough examples to diagnose why the slice moved.

Evaluation-driven development compares two named system versions under a controlled protocol. The run record includes the task set version, model, prompt, retrieval index, tool implementation, decoding policy, evaluator, code revision, and timing environment. A baseline is meaningful only when the comparison changes the intended variable and preserves the remaining conditions.

Repeated runs are relevant when sampling, routing, tools, or environment state introduce variation. The comparison reports the distribution of outcomes across the full run set. When data, rubric, or judge changes are necessary, the lineage record marks a new protocol version so the result is not presented as a direct continuation of an older score.

4.3 Baseline comparisons

The golden set now fixes the representative cases and risk-focused slices that must remain visible across versions. A comparison is still anecdotal when the model, prompt, retrieval, workflow, or scoring setup changes without a recorded baseline. Evaluation-Driven Development (EDD) runs the fixed set through a versioned baseline, changes one controlled factor, and inspects the resulting delta.

EDD adapts the discipline of Test-Driven Development to systems with probabilistic outputs and imperfect proxies. An eval combines the fixed cases, a scoring procedure, a comparison target, and the product decision it informs. The eval itself is versioned because user behavior and models change.

The evaluation loop begins with defined test cases and requirements. Write the eval before inspecting a preferred output so it measures the underlying behavior across cases.

A score without the input set, system version, trace, and decision threshold cannot be reproduced or interpreted safely.

  1. Define the behavior and observable final state the product must achieve.
  2. Create and version representative cases and risk-focused slices before tuning.
  3. Run the current system on the fixed set and store outputs, traces, latency, cost, and version metadata.
  4. Change one model, prompt, retrieval, workflow, or policy factor.
  5. Rerun the same evaluation, estimate uncertainty, and inspect failures.
  6. Ship, revise, or revert according to the decision rule; add new failures to the suite.

The fixed set keeps ordinary, boundary, adversarial, and production-derived cases visible in the comparison. Validated production failures can become regression cases after privacy review and label validation. Control duplicate or near-duplicate cases across development and held-out partitions, and retain each case’s expected outcome, rubric version, source record, and adjudication status.

4.4 Interpretable experiments

The task specification and golden set define what remains fixed across a comparison. A run is still uninterpretable when model, prompt, data, tools, sampling, or evaluator versions change together. An experiment manifest pins every input to the run, repeats variable components, and stores per-case artifacts before computing aggregate results.

The manifest records the case-set revision, model and provider identifier, prompt hash, context policy, retrieval index, tool versions, decoder settings, seed when supported, judge and rubric versions, code revision, and runtime environment. Each result row stores raw output, parsed output, validation results, latency, token usage, tool calls, citations, and final-state evidence. This lineage makes the baseline reproducible and reviewable.

Code example 4.1 - an evaluation harness keeps configuration and per-case evidence together.

Code example: Code example 4.1 - an evaluation harness keeps configuration and per-case evidence together.

from dataclasses import asdict
from time import perf_counter

def run_case(case, system, config):
    started = perf_counter()
    response = system(case.input, config=config)
    elapsed_ms = 1000 * (perf_counter() - started)
    return {
        "case_id": case.id,
        "slice": case.slice,
        "config": asdict(config),
        "raw_output": response.raw_output,
        "parsed_output": response.parsed_output,
        "validation": response.validation,
        "trace": response.trace,
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens,
        "latency_ms": elapsed_ms,
    }

The harness does not choose the metric or release threshold. Its role is to preserve the observations from which those decisions are calculated. When retrieval or model sampling can vary, the same case is run several times and each trial remains a separate record.

4.5 Uncertainty, release thresholds, and decisions

A controlled manifest makes baseline and treatment runs comparable. Finite case samples and stochastic components still make the observed difference uncertain, while a quality gain may violate latency, cost, or safety limits. Bootstrap intervals describe case-sampling variation, slice analysis exposes heterogeneous effects, and multi-metric gates determine release.

A bootstrap confidence interval resamples the evaluation cases with replacement many times and recomputes the statistic for each resample. “With replacement” means a case can appear more than once in one resample while another case is absent. The resulting statistics form an empirical distribution around the observed metric.

\[ CI_{1-\alpha}=[q_{\alpha/2}(m_{1:B}),q_{1-\alpha/2}(m_{1:B})] \tag{4.1}\]

Here, \(m_b\) is the metric calculated on bootstrap sample \(b\), \(B\) is the number of resamples, and \(q\) selects empirical quantiles. For a 95 percent interval, set \(\alpha=0.05\): the lower endpoint is the 2.5th percentile and the upper endpoint is the 97.5th percentile. The interval captures variation caused by the observed case sample; it does not correct biased labels, repeated tuning on the same set, correlated users, or deployment drift.

Worked calculation - paired bootstrap improvement

Four cases have baseline scores \((0.60, 0.80, 0.50, 0.90)\) and treatment scores \((0.70, 0.75, 0.55, 0.95)\). Pair each treatment score with its own baseline score before resampling, giving deltas \((+0.10, -0.05, +0.05, +0.05)\). The observed mean improvement is \(0.0375\).

  1. A resample can select cases 1, 1, 3, and 4, producing deltas \((+0.10, +0.10, +0.05, +0.05)\) and a mean of \(+0.075\).
  2. Another can select cases 2, 2, 3, and 4, producing \((-0.05, -0.05, +0.05, +0.05)\) and a mean of \(0\).
  3. Repeat this sampling many times, then take the percentiles for the selected \(\alpha\).

Interpretation: Pairing keeps each case’s baseline and treatment together. If the lower endpoint is at or below zero, the observed average gain does not yet support a clear improvement under this case sample.

Code example 4.2 - percentile bootstrap intervals retain the resampling unit.

Code example: Code example 4.2 - percentile bootstrap intervals retain the resampling unit.

import numpy as np

def paired_bootstrap_delta_ci(baseline, treatment, draws=10_000, seed=17):
    baseline = np.asarray(baseline, dtype=float)
    treatment = np.asarray(treatment, dtype=float)
    if baseline.shape != treatment.shape or baseline.size == 0:
        raise ValueError("baseline and treatment need the same non-empty shape")
    deltas = treatment - baseline
    rng = np.random.default_rng(seed)
    estimates = [
        deltas[rng.integers(0, len(deltas), size=len(deltas))].mean()
        for _ in range(draws)
    ]
    return tuple(np.quantile(estimates, [0.025, 0.975]))

The resampling unit must match the independence assumption. When one user contributes many correlated requests, resample users or sessions as the evaluation unit. A release gate can then require a positive lower-bound quality delta, no regression on critical slices, bounded p95 latency and cost per successful task, and zero severe policy failures. Here p95 latency means the 95th-percentile latency: 95 percent of the measured requests completed at or below that time, while the slowest 5 percent took longer.
