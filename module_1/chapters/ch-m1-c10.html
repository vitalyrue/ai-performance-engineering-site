10  Agent planning and tool connections

Chapter 9 established controlled tool use and final-state evaluation while keeping authorization, budgets, and execution in application code. Planning, shared tool connections, and retrieval recovery extend that loop while preserving the same controls. A single sequential loop is not always the best execution shape: some tasks benefit from an evolving plan, a dependency graph, or code-native computation, and shared tools may need a standard boundary. Planner selection follows task structure, uncertainty, dependency latency, opportunities for parallel work, and the need for sandboxed code.

The map compares stepwise action, explicit plans, dependency graphs, and sandboxed code, then binds MCP consent, scopes, and credentials, and stops retrieval recovery inside an explicit budget.

10.1 Planning strategy and task structure

A planner is the policy that converts a goal and current state into the next executable work. Planner alternatives are not successive maturity levels; they express different assumptions about uncertainty, dependencies, parallelism, and the value of executable code.

  • Planner: The component or policy that decides which actions should be attempted, in what dependency order, and when the accumulated evidence is sufficient to stop.

The useful question is not which planner sounds most advanced. It is which control-flow assumption matches the task while preserving a bounded execution layer.

The comparison becomes actionable when each planner is tied to its control structure, task fit, and dominant operational risk:

Plan-and-Execute provides an inspectable upfront plan but needs an explicit invalidation path. ReWOO replaces immediate observations with named variables, which can expose reusable dependencies but delays error discovery. Reflexion uses an evaluator’s critique as state for another attempt, so its value depends on feedback quality and a strict retry budget. Plan-and-Act revises after each observation and therefore occupies the middle ground between a static plan and fully incremental ReAct.

Selection rule

Use ReAct as the simple default when the next useful action depends strongly on the latest observation.

Add explicit planning only when the plan itself provides value: auditability, cheaper execution, parallelism, or coordination.

Do not let a more elaborate planner bypass the tool schemas, authorization gates, iteration limits, or outcome checks established in Chapter 9.

10.2 Plan revision from observations

The default agent loop already replans implicitly after every observation. A separate plan becomes useful when the product needs visible remaining work, a stronger planning model, or a cheaper execution model. The distinction is whether planning remains implicit in each step or becomes persistent state that is deliberately revised.

Incremental control makes ReAct adaptable and easy to inspect, but its serial loop needs a hard maximum and an explicit stopping condition.

ReAct

This method applies to goals for which the next action is uncertain until the latest tool result is observed. It is useful when the search space is exploratory, the tool set is focused, and frequent adaptation matters.

The model selects one typed action, the application executes it, and the resulting observation returns to state before the next decision. This is the smallest general agent loop and therefore the right baseline before adding planner machinery.

A limit to keep in mind: serial tool calls, repeated reasoning tokens, tool-selection errors, and infinite-loop risk without a step budget

The replan node is the defining addition. A static plan-and-execute system cannot absorb newly discovered constraints without a separate correction path.

A replanner returns either remaining work or a final response.

This abbreviated Python example assumes that state has the fields read below and that objective_satisfied, compose_answer, and revise_using are supplied by the application. It returns a Plan or Response; a malformed state should be rejected before this replanner runs.

Code example: A replanner returns either remaining work or a final response.

from dataclasses import dataclass

@dataclass
class Plan:
    steps: list[str]

@dataclass
class Response:
    response: str

def replan(state) -> Plan | Response:
    if objective_satisfied(state):
        return Response(response=compose_answer(state))
    remaining = revise_using(
        objective=state.objective,
        original_plan=state.original_plan,
        completed=state.past_steps,
        observations=state.observations,
    )
    return Plan(steps=remaining)

Plan-state invariant

The plan should contain only unfinished work. Completed steps and their observations belong in execution history, and the final response should be produced only when the objective and policy checks pass.

10.3 Dependency-aware parallel scheduling

Plan-and-Act stores remaining work as a sequence. A sequence serializes tasks that may be independent, so wall-clock time can remain unnecessarily high. A dependency graph makes those independence claims explicit, schedules ready work concurrently, and joins the results only after prerequisites complete.

  • Task DAG: A directed acyclic graph whose nodes are executable tasks and whose edges state that one task depends on another task’s output.

The reported speed and cost improvements are results for the cited study, not universal guarantees. The transferable mechanism is dependency-aware scheduling.

Let \(G\) be the task graph, let \(\pi\) be one dependency-respecting path through it, and let \(t_v\) be the duration of task \(v\). Even with unlimited workers, the graph cannot complete sooner than its longest dependency path:

\[ T_{DAG}\ge\max_{\pi\in\mathrm{paths}(G)}\sum_{v\in\pi}t_v \tag{10.1}\]

The maximum ranges over all paths in \(G\); the summation adds task durations along one path. This is a lower-bound latency model. Scheduling overhead, resource contention, retries, and the final join add time in production.

Worked calculation - critical path versus serial execution

Three independent document summaries take 8, 6, and 5 seconds. A final synthesis depends on all three and takes 4 seconds.

  1. Serial execution takes 8 + 6 + 5 + 4 = 23 seconds before overhead.
  2. In a dependency graph, the three summaries can start together.
  3. The longest prerequisite path is max(8, 6, 5) + 4 = 12 seconds.

Result: The idealized graph reduces the dependency-limited time from 23 seconds to 12 seconds.

Interpretation: The gain exists because the summaries are independent. Mislabeling a real dependency can make the faster schedule produce an invalid result.

The scheduler needs a concrete rule for determining which unfinished nodes may run at scheduler time t.

\[ \mathrm{Ready}(t)=\{v:v\notin\mathrm{Done}(t),\mathrm{Pred}(v)\subseteq\mathrm{Done}(t)\} \tag{10.2}\]

Here, \(\operatorname{Done}(t)\) is the set of completed nodes, \(\operatorname{Pred}(v)\) is node \(v\)’s predecessor set, and the set-builder expression retains unfinished nodes whose predecessors are all complete. Readiness proves dependency completion only; authorization, rate limits, resource availability, and safe concurrency require separate checks.

Worked calculation - ready nodes after one dependency completes

A graph contains A -> B, A -> C, and both B and C -> D. Only A is complete.

  1. B’s predecessor set is {A}, which is contained in Done(t).
  2. C’s predecessor set is also {A}, which is contained in Done(t).
  3. D requires both B and C, so D is not ready.

Result: The ready set contains B and C, allowing them to run concurrently.

Interpretation: The scheduler exposes parallelism already present in the dependency graph; it cannot safely invent independence that the plan did not establish.

A scheduler dispatches only tasks whose dependencies are satisfied.

This abbreviated Python loop assumes task objects with id and dependencies, an initially empty results mapping, and an application-supplied run_in_parallel. It returns the joiner’s answer and raises InvalidPlan when no unfinished task is runnable.

Code example: A scheduler dispatches only tasks whose dependencies are satisfied.

def ready_tasks(tasks, results):
    return [
        task for task in tasks
        if task.id not in results
        and all(dep in results for dep in task.dependencies)
    ]

while len(results) < len(tasks):
    batch = ready_tasks(tasks, results)
    if not batch:
        raise InvalidPlan("cycle, missing dependency, or failed prerequisite")
    results.update(run_in_parallel(batch, results))

answer = joiner(results)

Graph evaluation

Test dependency correctness, peak concurrency, critical-path latency, joiner faithfulness, cancellation, and partial failure. A single end-answer score cannot reveal whether apparent speed came from skipping required work.

10.4 Compound work in a sandbox

Typed function calls are effective when each action maps cleanly to one bounded capability. Loops, conditionals, local variables, and library composition can require many separate calls and observations. CodeAct compresses that procedural work into executable code, but this expressiveness moves isolation and resource policy to the center of the design.

The hard requirement is sandboxing. The generated program is untrusted input even when the model is normally reliable.

CodeAct

This method applies to computational subtasks expressible as code over explicitly mounted data and approved libraries. It is useful when a compact program replaces many repetitive tool calls or performs deterministic data analysis.

The model writes a program, an isolated runtime enforces time, memory, network, filesystem, and output limits, and captured results return as an observation. Code is a powerful action language, but it is safe only when the executor supplies a deliberately small capability envelope.

A limit to keep in mind: sandbox escape risk, nondeterministic dependencies, large outputs, hidden side effects, and harder policy review

The sections above separated planning from the controlled execution of each ready action. Capabilities may still live in different processes or services and need a common discovery and invocation boundary. Model Context Protocol (MCP) standardizes capability exchange, while the host, server, and downstream service retain explicit responsibility for consent, identity, authorization, validation, and provenance.

10.5 Tool connections through Model Context Protocol (MCP)

The planners above can all call ordinary in-process functions. When multiple hosts and multiple capability providers evolve independently, custom adapters create an N x M integration burden. Model Context Protocol standardizes discovery and invocation while leaving product trust, permissions, and execution policy with the host.

  • Model Context Protocol: A client-server protocol through which an AI host can discover and use server-provided tools, resources, and prompts through standardized messages.

For N hosts and M services, the integration topology can move from N x M bespoke adapters toward N + M protocol implementations. Operations, authentication, and semantics still need clear operational responsibility.

The host is the application that manages model interaction and the user trust boundary; it creates a client session for each server. A server exposes capabilities backed by a database, API, filesystem, or other system. For a simple discovery exchange, the host sends a tools-list request, the server returns typed tool definitions, and the host applies its policy and asks for any required user approval before invocation. Local stdio transport minimizes network exposure; remote transport requires explicit authentication, authorization, and lifecycle handling.

The agent loop need not change when the transport changes. That separation is useful only if tool identity, permissions, errors, and provenance remain visible in traces.

A host keeps capability discovery separate from agent execution.

This abbreviated async Python example assumes an authenticated client, a policy object, and an application-supplied create_agent. It returns an agent restricted to allowed discovered tools; discovery or policy failures stop construction rather than yielding an unrestricted agent.

Code example: A host keeps capability discovery separate from agent execution.

async def build_agent(client, model):
    discovered = await client.get_tools()
    allowed = [
        tool for tool in discovered
        if policy.allows_server(tool.server_id)
        and policy.allows_schema(tool.name, tool.input_schema)
    ]
    return create_agent(model=model, tools=allowed)

A server implementation can expose the same typed capability boundary with FastMCP. The current FastMCP v3 decorator derives a JSON input schema from the function signature and validates arguments before calling the function, but application rules still constrain data access and side effects.

Code example 10.1 - FastMCP exposes narrow support capabilities while preserving approval boundaries.

This abbreviated server example assumes the three stores and search helper enforce their own access rules. It returns allowlisted records, bounded search results, or a draft; access failures must be returned as typed tool errors, and only the application may submit a draft after approval.

Code example: Code example 10.1 - FastMCP exposes narrow support capabilities while preserving approval boundaries.

from fastmcp import FastMCP

mcp = FastMCP(name="support-tools")

@mcp.tool
def lookup_ticket(ticket_id: str) -> dict:
    # Return allowlisted fields for one support ticket.
    return ticket_store.read_public(ticket_id)

@mcp.tool
def search_policy(query: str, top_k: int = 4) -> list[dict]:
    # Search approved policy documents without executing their text.
    bounded_k = min(max(top_k, 1), 8)
    return policy_search(query, top_k=bounded_k)

@mcp.tool
def draft_escalation(ticket_id: str, reason: str) -> dict:
    # Create a draft; submission still requires human approval.
    return escalation_store.create_draft(ticket_id, reason)

The decorator exposes schemas and documentation, while the underlying functions retain the system-of-record policy. lookup_ticket returns allowlisted fields, search_policy bounds result count, and draft_escalation deliberately cannot submit. FastMCP and MCP versions belong in the server manifest because component and transport behavior evolves.

10.6 Trust at the protocol boundary

A standard protocol makes a connection intelligible; it does not make the connected server or its outputs safe. Tool descriptions and returned documents are untrusted data. A malicious document can contain instructions intended to redirect the model, and an over-scoped credential can let an otherwise valid call perform actions the user did not permit.

  • Prompt injection defense: label retrieved content as data, isolate it from policy, constrain allowed actions, and require evidence for claims.
  • Confused-deputy defense: bind every call to user intent, tool identity, narrow scopes, current authorization, and destination.
  • Human approval: require explicit confirmation before sending, purchasing, deleting, publishing, or changing durable state.
  • Roots and credentials: share only required paths and short-lived capabilities; roots tell a server the relevant workspace scope, while access controls still enforce what it may read or write. Do not pass ambient secrets to every server.
  • Supply-chain control: pin or verify server packages, record version and provenance, and treat server updates as behavior changes.
  • Audit trail: log discovery, selected tool, normalized arguments, approval, server identity, result status, cost, and final state.

The current MCP specification defines stdio and Streamable HTTP as standard transports. A local stdio client launches the server process and exchanges newline-delimited JSON-RPC messages; Streamable HTTP uses one HTTP endpoint and requires origin validation, appropriate authentication, and careful session handling. Transport choice changes exposure and credential handling, not the semantics of the tool.

For HTTP authorization, the current specification builds on OAuth 2.1. Clients request a token for the intended MCP resource, and servers validate that the token audience names that server. An MCP proxy must not pass the inbound client token unchanged to a downstream API; it obtains a separate upstream token instead. Audience validation, short-lived credentials, PKCE for authorization-code flows, and per-client consent prevent the server from becoming a confused deputy.

A valid protocol message does not prove that the requested action is authorized. The host binds a user-approved intent to a resource-scoped token, and each server validates and executes with its own policy and credentials.

Dated supplement - elicitation and consent (MCP 2025-06-18)

The MCP 2025-06-18 elicitation specification lets a server request missing structured information from the user through the host. For example, the server sends elicitation/create with a response schema; the host identifies the requesting server, presents the request, and sends back an accept, decline, or cancel response.

The host must identify which server is asking, explain what information is requested, let the user decline or cancel, and validate the response schema.

A server must not request passwords, API keys, or other secrets through a form. A URL-based authorization flow, when separately supported, must bind the interaction to the same authenticated user who completes it.

After those protections are specified, the remaining choice is whether the protocol solves a real sharing boundary:

Chapter checkpoint

Choose a planner from dependency structure and uncertainty, not novelty. Keep execution bounded. Use MCP when standardized sharing solves a real integration boundary, and keep authorization, consent, provenance, and outcome evaluation outside the protocol.

Chapter 7 localized RAG failures by checking retrieved evidence, claim support, and answer relevance, while the planning and protocol sections above supplied controlled tool use and boundaries. A fixed retrieval pass can still stop too early when its first query or method misses necessary evidence. Agentic retrieval adds a limited recovery loop that checks evidence sufficiency, changes one retrieval action, and stops on success or an explicit attempt, latency, or cost budget.

10.7 Retrieval failure recovery within a budget

Planning and MCP have defined how an agent chooses and invokes bounded capabilities. One-shot retrieval still stops after the first query even when its evidence is visibly insufficient. Agentic retrieval adds a capped inspect-rewrite-retrieve loop and chooses the retrieval representation that matches the information need.

One-shot RAG assumes the user’s first query is a good retrieval query and that one retrieval contains enough evidence. Vague language, multi-hop questions, corpus mismatch, and ambiguous entity names break that assumption. Agentic RAG places a controlled decision loop between the question and the retriever so the system can route, inspect, rewrite, decompose, and stop.

  • Agentic RAG: A retrieval-augmented system in which an agent chooses and iterates retrieval actions from observations, within a bounded recovery loop.

The missing capability is not necessarily a larger embedding model. It is a recovery path that can recognize insufficient evidence and change the next retrieval action.

Iterative retrieval

This method applies to queries whose first retrieval may be noisy, incomplete, or expressed with the wrong vocabulary. It is useful when the system can cheaply inspect relevance and try a bounded number of refined searches.

The system retrieves candidates, grades or inspects the evidence, rewrites the query when evidence is insufficient, and generates only after a stop rule passes. End-to-end recall can rise because the system learns from each miss rather than treating the first candidate set as final.

A limit to keep in mind: extra latency and model calls, grader errors, semantic drift during rewriting, and loops without an attempt cap

The retriever itself is a product choice. Exact search is often strongest for symbols, identifiers, error strings, and rapidly changing code. BM25 fits keyword-rich corpora. Embeddings help with conceptual paraphrases and cross-language similarity. SQL or an API should answer structured filters and aggregates directly. Agentic control does not erase those differences; it selects among them.

10.8 Points of intervention in retrieval control

Chapter 7 separated retrieval relevance from answer faithfulness. The next design question is where control should intervene when evidence is missing. Iterative refinement retries one route, routing selects a route before retrieval, and decomposition creates multiple evidence subproblems.

The patterns may be composed, but each additional branch or loop needs its own budget, state, and evaluation slice.

A bounded iterative-retrieval state machine.

This abbreviated Python example assumes that the retriever, grader, and rewrite helper are supplied by the application and that state records attempts, a maximum, documents, and the latest grade. Each node returns updated state; a grade must be stored before the rewrite node can read its reason, and the budget-exhausted route returns an evidence-gap result rather than generating an answer.

Code example: A bounded iterative-retrieval state machine.

def retrieve_step(state):
    docs = retriever_for(state.route).search(state.query)
    return state.add_attempt(query=state.query, docs=docs)

def grade_step(state):
    verdict = evidence_grader(state.question, state.latest_docs)
    return state.with_latest_grade(verdict)

def route_after_grade(state):
    if state.latest_grade.sufficient:
        return "generate"
    if state.attempts >= state.max_attempts:
        return "insufficient_evidence"
    return "rewrite"

def rewrite_step(state):
    return state.with_query(
        rewrite_using_failure_reason(
            original=state.question,
            previous=state.query,
            reason=state.latest_grade.reason,
        )
    )

Stopping is part of retrieval quality

When the evidence budget is exhausted, the correct output may be an evidence-gap response. Forcing generation after a miss converts a retriever limitation into an unsupported answer.
