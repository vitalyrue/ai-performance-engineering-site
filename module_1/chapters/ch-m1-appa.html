13  Logging system execution

An answer or final tool result does not show how the application produced it. Logs preserve the inputs, decisions, outputs and failures needed to investigate that execution. Chapter 12’s cases show the request paths whose stages need logs.

13.1 What to log at each stage

A useful log lets a reviewer connect an outcome to the operations that produced it. Each request needs a shared identifier, with its steps and attempts identified separately. Nested or parallel work also needs parent or dependency links because timestamps alone do not show those relationships. Application code records event time, operation, component version, outcome and failure reason where applicable. Elapsed time belongs beside the operation it measures. These stage-specific fields apply established logging practices to the book’s examples. They are application choices. Some need logging code beyond the short examples.

These rows describe operations, rather than one mandatory sequence. Memory can be read before request assembly, and an agent can repeat retrieval and tool calls. The application logs only stages it uses and keeps each attempt distinct, including rejected, failed and timed-out attempts. A log containing only successful returns cannot explain the failed requests omitted from it.

13.2 Established standards and practices

An event log describes an occurrence, such as a rejected tool argument. A trace links the operations belonging to a request, including nested or repeated steps. An evaluation log adds the test case, expected result, rubric and scores. Together they connect runtime behavior to the comparisons developed in Chapters 4, 5 and 7.

Services need shared ways to identify related work. Applications also need rules for what to log and how to protect it. These standards and practices address those needs:

  • W3C Trace Context standardizes the HTTP headers traceparent and tracestate used to pass trace context between services. This lets participating services associate their work with the same trace.1
  • OpenTelemetry defines a stable data model for logs, with timestamps, log levels, event details, extra fields and optional trace-context fields.2 A span describes one operation, with its start and end times and associated information. Spans link through parent and trace identifiers to show related work.3
  • OWASP’s Logging Cheat Sheet gives application logging guidance: capture enough information about when an event occurred, where it occurred, who initiated it and what happened. It includes validation, authorization and execution failures, and guidance on protecting the logs.4

These sources establish shared formats and logging practices. The table in Section 13.1 adds the domain information needed here, such as chunk IDs, candidate ranks and validation outcomes. Those fields must have documented meanings in the application. A shared trace identifier alone does not explain which passages entered a model request or whether a tool action was permitted.

13.3 Logging tools

Application code must log the stage information needed for diagnosis. A library cannot infer application details it has not received. A configured library integration may log model calls automatically. Application checks and state changes need additional logging code. The examples below cover event logging, tracing within and across services, and tracking evaluation runs with their settings and scores.

For a small script, structured local logs can be sufficient. Section 12.7 writes one JSON object per request on a separate line in traces.jsonl. Each object contains session_id, question, latency_ms and the current request’s trace. A session can contain several requests, so a separate request identifier is needed to link each one’s logs. The example preserves the request steps, but a complete logging setup also needs its version information and a way to retain partial logs when a helper fails.

For work across services, application code passes trace context and records spans to connect model, retrieval and tool operations. A tracing service can then display the timing and relationships between operations. For repeated evaluation runs, application code keeps parameters and scores linked to the permitted log files used to calculate them. The same request identifier can appear in the application log, its trace and its evaluation result.

These optional tools serve different logging needs. Their interfaces and integrations depend on the version. The earlier examples do not depend on these tools.

13.4 Using logs to investigate a failure

For the RAG example in Section 6.7, follow the candidate IDs into the selected passages and then into model_request. If a supporting passage was retrieved but omitted from that request, inspect selection and request assembly. If it entered the request but the answer contradicts it, inspect generation and answer validation. Section 7.1 develops these distinctions. A final answer and a search-success message alone cannot separate them.

For the workflow in Section 8.3, inspect the inputs, validation decisions and transition at each step. For a tool call, distinguish a proposed action from an attempted action and its actual result. For an agent, preserve the ordered attempts and stop reason. A failure in a helper needs a partial log even when the main function cannot return its normal result.

Decide which data may be stored in the logs, who may read the logs and how long they remain available. Exclude credentials and other prohibited data. Where full text cannot be logged, preserve permitted identifiers, versions and protected references. A hash can check whether data matches, but cannot recover its contents. OWASP also recommends testing logging failures and restricting access to the logs.8

Logs support investigation; they do not themselves establish that an answer is correct or an action is authorized. Chapter 14 uses the logged execution and its evaluation results as evidence for release decisions.
