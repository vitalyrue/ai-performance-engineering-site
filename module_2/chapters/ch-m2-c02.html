2  Token IDs and batches

The prediction task now specifies which text is available and which token should come next. A numerical model still cannot use a character string directly. It needs a stable address for each token and a way to keep several sequences together without confusing added storage with observed text.

Token IDs provide those addresses. Batches organize them into arrays, while validity information records which positions belong to each original sequence.

2.1 Preparing token IDs

Suppose a tokenizer divides cat sat into two tokens. The model needs to refer to the same cat whenever that token appears. A vocabulary is a finite collection of tokens with fixed integer IDs. A token ID identifies an entry in that collection.

\[ V = \{v_0,\ldots,v_{\lvert V\rvert-1}\} \tag{2.1}\]

The vocabulary \(V\) contains \(|V|\) token types, written \(v_0\) through \(v_{|V|-1}\). The legal IDs therefore run from 0 to \(|V|-1\). The vertical bars denote the number of entries. They do not describe the length of a tokenized sentence.

For a four-token vocabulary [<pad>, cat, sat, dog], cat has ID 1 and sat has ID 2. The text cat sat becomes \([1,2]\). In the vocabulary used for Chapter 1’s example, the same words had IDs 4 and 8. Both assignments are valid, but a particular trained model requires its own exact mapping.

The conversion applies a lookup function at every position:

\[ x_t = \operatorname{id}(t_t) \tag{2.2}\]

Here \(t_t\) is the token string at position \(t\), \(\operatorname{id}\) is the vocabulary lookup, and \(x_t\) is the resulting integer. The lookup preserves order and length. It changes the representation of each token, rather than measuring its meaning. ID 8 is not twice as meaningful as ID 4, and adjacent IDs need not describe related words.

A model can later use an ID to select a parameter row or to identify the expected output token. If the vocabulary has 50,000 entries, a model that scores every possible next token needs 50,000 output coordinates. A larger vocabulary can reduce sequence length, but it also enlarges these vocabulary-dependent objects. Subword tokenization explains that trade-off.

Not every possible string needs its own vocabulary entry. The tokenizer may split an unfamiliar word into known pieces. Some vocabularies also supply an unknown token, usually written <unk>, as a fallback when an item cannot be represented. Recovering token strings from IDs is possible through the vocabulary. Recovering the exact original text additionally depends on whether preprocessing discarded information, such as capitalization or repeated spaces.

For a vocabulary with an unknown-token fallback, lookup has two cases:

\[ \mathrm{ids}[t]=\begin{cases}\mathrm{vocab}[\mathrm{token}_t],&\text{if }\mathrm{token}_t\text{ is represented in the vocabulary},\\ \mathrm{vocab}[\mathrm{UNK}],&\text{otherwise}\end{cases} \tag{2.3}\]

The array entry ids[t] receives the token’s vocabulary ID when it exists. Otherwise it receives the vocabulary’s unknown-token ID. For a toy mapping with cat at 1 and <unk> at 0, cat maps to 1 and an unrepresented item maps to 0. A tokenizer that can decompose that item into known pieces should apply that decomposition before resorting to a fallback.

Other special tokens represent structure. A beginning-of-sequence marker identifies a starting boundary, an end-of-sequence marker identifies an ending boundary, and a padding token fills reserved positions. The abbreviations BOS, EOS, and PAD refer to those roles. A mask token and chat-role markers serve other input formats, introduced in Section 3.3.

A sequence of IDs is an ordered one-dimensional array. Several sequences introduce another axis, which is where the storage problem begins.

2.2 Preparing batches

An operation can process several examples together, but sentences rarely contain the same number of tokens. A batch is a collection of examples processed together. To store it as one rectangular array, shorter sequences need additional positions. Padding supplies those positions while retaining which entries belong to the original text.

A tensor is an array described by its axes, shape, and element type. A scalar has no axes, a vector has one, and a matrix has two. The shape lists the length of each axis. A token-ID batch with shape \([B,T]\) contains \(B\) rows and \(T\) reserved positions per row. Its rank, or number of axes, is two.

For \(B=2\) and \(T=4\), there are eight stored IDs. The entry \(X_{b,t}\) selects one row and one position. Mathematical examples here count positions from 1, while Python indices start at 0. Thus X[1, 2] selects the third position of the second row. A tensor’s element type also matters: token IDs are integers, rather than continuous measurements.

Consider [BOS, cat, sat, EOS] and [BOS, dog, EOS]. Right padding to four positions gives [BOS, dog, EOS, PAD] for the second row. The rows now share a shape, but the last entry in the second row is still artificial.

A validity mask records that distinction. Let \(L_b\) be the original length of row \(b\) before right padding. For one-based positions, define:

\[ M_{b,t}=\begin{cases}1,&1\le t\le L_b,\\0,&L_b<t\le T\end{cases} \tag{2.4}\]

The mask \(M\) has shape \([B,T]\), matching the ID array. In this example it is [[1,1,1,1], [1,1,1,0]]. This length-based formula assumes right padding without truncation. With left padding or truncation, use the actual position metadata produced during preparation.

The distinction must come from preparation metadata when a tokenizer uses the same ID for EOS and PAD. In that case, a test such as input_ids != pad_id would incorrectly remove a real end marker. Equal integer values do not imply equal roles.

The next runnable PyTorch example isolates that case without downloading a tokenizer. Its IDs are supplied by a fixed toy vocabulary. BOS is 1, cat is 4, dog is 6, sat is 8, and EOS is 9. The padding configuration reuses ID 9. The integer tensors remain on the CPU, the processor used by default in this example.

The slice :len(sequence) selects the occupied positions in one row. The loop fills those positions and marks them valid. A separate clone() supplies labels so replacing ignored targets cannot change the input IDs. The operator ~ reverses a Boolean mask, selecting the positions that are not valid.

Code example: A real end marker and inserted padding can share an ID

import torch

sequences = [[1, 4, 8, 9], [1, 6, 9]]
lengths = torch.tensor([len(row) for row in sequences])
width = int(lengths.max())
input_ids = torch.full((len(sequences), width), 9, dtype=torch.long)
valid = torch.zeros_like(input_ids, dtype=torch.bool)
for row_index, sequence in enumerate(sequences):
    input_ids[row_index, :len(sequence)] = torch.tensor(sequence)
    valid[row_index, :len(sequence)] = True
labels = input_ids.clone()
labels[~valid] = -100

assert input_ids.tolist() == [[1, 4, 8, 9], [1, 6, 9, 9]]
assert valid.tolist() == [[True, True, True, True], [True, True, True, False]]
assert labels[1, 2].item() == 9
assert labels[1, 3].item() == -100
print(input_ids.tolist(), valid.int().tolist(), labels.tolist())

The second row contains two occurrences of ID 9. Its third position is a genuine EOS, so its mask value remains 1. Its fourth position was inserted, so its mask value is 0. The assertions make this difference observable.

A model may consume validity information in several places. An attention operation uses it to exclude padded source positions. A loss calculation uses it to exclude artificial targets. Pooling uses it to avoid treating padding as part of a document representation. These consumers need related information, but their exact mask shapes and conventions can differ.

In a tokenizer result, the field attention_mask commonly supplies this initial valid-position information, with 1 for valid and 0 for padding. It is separate from the causal restriction that stops an earlier token from reading a later token. Attention combines those restrictions explicitly.

For loss implementations that accept an ignore index, excluded targets receive a value such as \(-100\):

\[ \mathrm{label}_{b,t}=-100\quad\text{when }M_{b,t}=0 \tag{2.5}\]

Here \(M_{b,t}=0\) identifies an inserted position. The ignore index lies outside the vocabulary and is interpreted by the loss function. It must never be passed as an ordinary token ID to a vocabulary lookup. A real EOS target remains eligible for training.

The following transformers example performs the text preparation with the GPT-2 tokenizer. It requires that package and the tokenizer files, obtained from the model repository or a local cache. It prints the tensor shapes and verifies that unequal-length inputs actually produce padding.

Code example: Tokenizer batch with padding and mask

from transformers import AutoTokenizer

texts = ["cat", "the dog ran across the garden and stopped"]
tokenizer = AutoTokenizer.from_pretrained("gpt2")
tokenizer.pad_token = tokenizer.eos_token
batch = tokenizer(texts, padding=True, return_tensors="pt")
input_ids = batch["input_ids"]
attention_mask = batch["attention_mask"]
labels = input_ids.clone()
labels[attention_mask == 0] = -100

assert input_ids.shape == attention_mask.shape == labels.shape
assert (attention_mask == 0).any()
assert (labels[attention_mask == 0] == -100).all()
print(input_ids.shape, attention_mask.tolist())

# GPT-2 causal LM classes shift these labels internally.
# A direct loss calculation must perform its own next-token alignment.

The tokenizer returns integer input_ids and the aligned attention_mask. Copying the IDs preserves real target values, and the mask selects only inserted positions for replacement with \(-100\). The code follows the GPT-2 causal language-model interface, which performs the next-token shift internally. An implementation that calculates the loss directly must align predictions and next-token targets itself. Loss reduction shows both arrangements and prevents a double shift.

The common rectangular shape allows batch computation. It does not make every stored entry a valid token or supervised target. Truncation creates a different trade-off: it removes actual context to meet a length limit, so its policy must be considered when evaluating predictions.

We now have a numerical interface for text: IDs of shape \([B,T]\) and aligned validity information. The next chapter explains how a tokenizer chooses reusable pieces for the vocabulary, affecting both its size and the lengths of these sequences.
