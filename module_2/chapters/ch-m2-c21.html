21  KV cache and serving

A generated answer grows one token at a time. Recomputing the entire prefix for every prediction would repeat much of the same transformer work. A key-value cache preserves reusable attention state, while a serving scheduler decides how requests share computation and memory.

We follow one request first, then examine cache capacity, user-visible timing, and shared scheduling. This keeps the model’s state transitions connected to the costs that an application measures.

21.1 Prefill and decode

The causal block in Chapter 17 cannot change an earlier representation when a later token is appended. Under fixed weights and inference settings, its earlier keys and values can therefore be reused.

Prefill processes the available prompt and computes attention keys and values for its positions at every layer. The KV cache stores those keys and values. It does not need to store every earlier logit or complete hidden representation.

The final valid prompt position already produces logits for the first output token. Selecting that token uses the decoding rule from Chapter 7. A separate forward pass on the newly selected token is needed only to produce the following token’s logits.

Decode repeatedly processes the newest selected token, calculates its query, key, and value at each layer, and appends the new key and value. Its query reads the earlier cache together with the newly processed position.

\[ \mathrm{cache}_t=\operatorname{append}(\mathrm{cache}_{t-1},K_t,V_t) \tag{21.1}\]

For a three-token prompt, prefill creates three cached positions and produces the distribution for token four. Processing token four extends the cache to four positions and produces the distribution for token five. If generation stops after selecting token four, that token need not be processed into the cache.

The cache therefore counts processed positions, not necessarily every token already emitted. In a simple batch, prompt IDs have shape \([B,T_{\text{prompt}}]\) and prefill logits have shape \([B,T_{\text{prompt}},|V|]\). Selecting the final valid position gives logits \([B,|V|]\).

A subsequent decode input has shape \([B,1]\). Each layer reuses its earlier state and calculates only the new position’s transformation. For a right-padded batch, logits[:, -1, :] may select padding, so the final valid position or the model’s supported padding convention matters.

The new query still reads the permitted earlier keys and values. Its attention work grows with current context length even though earlier projections are reused. Caching reduces repeated computation without making each step independent of the prefix size.

21.2 Cache capacity

Reusing earlier values saves arithmetic but retains state for every active request. Its size depends on layer count, cached positions, numerical format, and the number of key-value heads.

In standard multi-head attention, each query head has corresponding key and value projections. Multi-query attention, or MQA, shares one key-value head across several query heads. Grouped-query attention, or GQA, shares one key-value head within each group of query heads.

These variants retain several query comparisons while reducing the number of stored key and value vectors. They are architecture choices, rather than a safe switch for arbitrarily discarding heads from an already trained model.

For one layer, the logical cache tensors have shape:

\[ K,V\in\mathbb{R}^{B\times H_{\mathrm{KV}}\times T\times d_h} \tag{21.2}\]

Here \(B\) is the number of requests in a uniform-length batch, \(H_{\text{KV}}\) is key-value head count, \(T\) is cached length, and \(d_h\) is head width. With \(L\) layers and \(s\) bytes per stored scalar, total logical storage is:

\[ \mathrm{bytes}=2\cdot\mathrm{layers}\cdot B\cdot H_{\mathrm{KV}}\cdot T\cdot d_h\cdot s \tag{21.3}\]

The factor two counts both keys and values. Appending one processed position for every request in that batch increases storage by:

\[ \Delta\mathrm{bytes}_{\mathrm{per\ token}}=2LBH_{\mathrm{KV}}d_hs \tag{21.4}\]

For one request, one layer, one key-value head, width two, and two-byte values, a three-position cache uses 24 bytes. Processing another token increases it to 32 bytes. Each of its key and value tensors changes from \([1,1,3,2]\) to \([1,1,4,2]\).

A separate example uses two layers, four key-value heads, width eight, one request, and two-byte storage. At five positions, each key or value tensor holds 160 values, or 320 bytes. Across both layers and both tensors, the total is 1,280 bytes.

Processed positions | Total logical cache bytes | |—:|—:| | 5 | 1,280 | | 6 | 1,536 | | 7 | 1,792 | | 8 | 2,048 |

Each additional processed position adds 256 bytes. The decode input remains \([1,1]\), while the attention operation reads the growing cache and returns the next vocabulary-logit vector.

The following function estimates this logical storage in gibibytes, where one GiB is \(1024^3\) bytes.

Code example: A simple KV-cache memory estimate.

def kv_cache_gib(
    layers, batch, kv_heads, seq_len, head_dim,
    bytes_per_value=2,
):
    bytes_total = (
        2 * layers * batch * kv_heads * seq_len
        * head_dim * bytes_per_value
    )
    return bytes_total / 1024**3

print(
    kv_cache_gib(
        layers=32, batch=1, kv_heads=8,
        seq_len=8192, head_dim=128,
    )
)
assert kv_cache_gib(32, 1, 8, 8192, 128) == 1.0

For 32 layers, eight key-value heads, 8,192 positions, width 128, and two-byte values, the result is one GiB per request. A model with 32 query heads would use four times as much cache if it also stored 32 key-value heads of that width.

For unequal request lengths, sum their cached positions instead of using one common \(BT\). Physical allocation also includes partially filled blocks and metadata. Shared prefixes can reduce duplication. Model weights, temporary activations, and other serving state are separate memory categories.

21.3 Latency and throughput

Cache capacity determines which requests can be admitted, but an application experiences waiting time and streaming speed. Define timing at the request boundary before comparing an optimization.

Time to first token, or TTFT, is the delay from submitting a request to receiving its first output token. A useful decomposition is:

\[ \mathrm{TTFT}=\mathrm{queue\ time}+\mathrm{prefill\ time}+\mathrm{first\ token\ selection\ and\ delivery\ time} \tag{21.5}\]

The final term includes selecting and delivering the first token, which is produced from prefill’s final-position logits. It is not inherently a separate transformer decode forward pass. If queueing takes eight milliseconds, prefill twenty, and remaining first-token processing five, TTFT is 33 milliseconds.

Time per output token, or TPOT, describes a request’s spacing between output tokens after its first token. If \(n\ge2\) tokens arrive at times \(t_1,\ldots,t_n\), its mean interval is:

\[ \mathrm{TPOT}_{\mathrm{request}}=\frac{t_n-t_1}{n-1},\quad n\ge2 \tag{21.6}\]

A one-token response has no such interval. Report distributions across requests or intervals, with the aggregation rule stated, because a mean can hide long pauses.

Aggregate throughput counts output tokens from all requests per unit time. If a batch produces forty tokens in 200 milliseconds, its throughput is 200 tokens per second. The reciprocal, five milliseconds per aggregate token, is not the TPOT experienced by each request.

For example, four active requests can each produce one token every twenty milliseconds. Across ten steps, they produce forty tokens in 200 milliseconds, while each stream has twenty-millisecond intervals. Batching raises total output rate without making each individual stream emit a token every five milliseconds.

Prefill often exposes large matrix operations over many positions. Decode processes fewer new positions per request and repeatedly reads weights and cache values. Whether either phase is limited by arithmetic, memory bandwidth, or scheduling depends on the workload and hardware.

Measure prompt and output lengths, active request counts, numerical formats, and arrival patterns alongside timings. An optimization can improve throughput while increasing queueing or delaying individual streams.

21.4 Scheduling requests

Requests arrive at different times and finish after different output lengths. A simple fixed batch can leave completed slots unused while a long request continues. Continuous batching admits and removes requests between model steps.

The scheduler combines currently active inputs, then routes each output back to its request. Token history, cache positions, validity rules, and sampling state remain separate. The stopping rules are those in Chapter 7.

A larger active batch can use hardware more efficiently, but may increase waiting or processing time for a particular request. Head-of-line blocking occurs when a long operation prevents later work from progressing on a shared schedule.

Chunked prefill splits an incoming prompt into smaller pieces that can be interleaved with existing decode work. Each chunk retains the prompt’s earlier state and correct positions.

Suppose one request has a twelve-token prompt while two others are decoding. An uninterrupted prefill processes all twelve prompt tokens before the existing requests receive their next scheduled step. With four-token chunks, a possible schedule is prefill four, decode, prefill four, decode, then prefill four.

In this illustrative schedule, the new prompt completes later because other work is interleaved. The existing streams encounter shorter interruptions. Actual timing also depends on how efficiently each chunk executes.

Continuous batching decides which requests share a step. Chunking limits the amount of prompt work admitted at once. Both require a cache allocator that can accommodate changing request lengths without moving every earlier value.

21.5 Paged cache blocks

Reserving one large contiguous cache region for every request can waste space when lengths are uncertain. PagedAttention divides a request’s logical cache into fixed-size blocks and maps them to physical blocks that need not be adjacent. A block table tells the attention kernel where each logical segment resides. PagedAttention introduces this organization for language-model serving.

Consider a simplified allocator with four token positions per block. A nine-position request needs three logical blocks. Its block table might map them to physical blocks \([5,1,9]\).

Zero-based token position 6 belongs to logical block \(\lfloor6/4\rfloor=1\) at offset \(6\bmod4=2\). The block table maps it to physical block 1, offset 2. Token position 8 maps to physical block 9, offset 0.

The request occupies twelve allocated positions, of which nine contain values. Its last block has three unused slots. The internal fragmentation in this example is the space reserved inside that partially filled block.

Appending positions 9, 10, and 11 fills the remaining slots. Position 12 requires another physical block and a new table entry. The earlier logical positions keep their meanings even if physical blocks are scattered in memory.

The kernel uses the mapping while reading keys and values. Allocation can therefore grow without requiring one adjacent region for the entire sequence. It still needs metadata and suitable access patterns, and block size affects wasted capacity and management cost. The vLLM design description explains the kernel-side layout.

When a request finishes, blocks can return to the free pool once no other request references them. Reference counts or an equivalent mechanism are needed if multiple requests share cached prefixes.

21.6 Prefix reuse and offloading

The per-request cache avoids recomputing a growing continuation. A prefix cache extends reuse across requests whose initial token sequences match. Their shared prompt state can be computed once and referenced by later requests.

Reuse requires the same effective model weights, including active adapters, and a compatible cache interpretation. Token IDs, position handling, attention settings, and any input features affecting the prefix must match. Similar-looking text is insufficient if its tokenization differs.

Shared blocks must remain unchanged while other requests reference them. If a request needs to extend a partially shared block, a copy-on-write policy can allocate its own copy before modification. Other requests retain their original prefix state.

Prefix caching can reduce repeated prompt processing. It does not directly remove queueing or the work of generating a new suffix. Full-prefix hits also require a valid way to obtain the next-token logits, since stored keys and values alone are not those logits. The vLLM prefix-caching guide describes the scope of its reuse.

Cache offloading stores selected cache blocks in another memory tier, such as host memory, when accelerator capacity is tight. A later attention operation must make any required offloaded values available again. The capacity saving therefore introduces transfer and scheduling costs.

For two long requests whose caches do not fit together, offloading can admit more stored context. A decode step may then wait for required blocks to transfer. Compare capacity, transfer time, TTFT, and TPOT under the actual request mix.

High-level model.generate(use_cache=True) supports an initial inspection of state reuse with a compatible model. Serving runtimes such as vLLM, SGLang, and TensorRT-LLM add scheduling and memory-management choices. Their precise controls differ, so engine-specific flags are not interchangeable transformer operations.

Cache layout and scheduling aim to preserve the model’s computation while changing its execution. Numerical kernels and sampling state can still affect reproducibility. Check output behavior as well as speed when changing a serving configuration.

The same representation and resource questions extend beyond text. Chapter 22 examines the additional input processing required for images, audio, and tables.

Chapter checkpoint

A three-token prompt has just produced its first output token. How many positions must already be in its ordinary KV cache?

Feedback: Three prompt positions. The selected fourth token enters the cache when a subsequent forward pass processes it to predict token five, if generation continues.

An optimization doubles aggregate throughput while the spacing within each response is unchanged. Is its TPOT twice as good?

Feedback: No. More concurrent streams can raise throughput while each stream keeps the same token intervals. Report per-request timing separately from total token rate.

A prefix string is unchanged after switching adapters. Can the old prefix state be reused automatically?

Feedback: No. The effective weights changed, so the cached keys and values may differ. The reuse key must account for the active model and adapter configuration.
