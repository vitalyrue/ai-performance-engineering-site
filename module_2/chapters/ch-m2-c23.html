23  Tensor storage and execution

A model can fit a mathematical shape contract and still exceed device memory or spend time copying data. Shape describes the logical array. Storage, layout, and tensor lifetime explain the resources that executing it requires.

The tensor basics in Section 2.2 already support the earlier models. This chapter follows their physical representation, then connects shared storage and training state to useful memory measurements.

23.1 Tensor size and storage

Estimating memory starts with the values an operation must represent. A tensor’s shape lists the lengths of its axes, and its dtype specifies the numerical representation of each element. Its device identifies where its values reside, such as CPU memory or a CUDA GPU.

Creation establishes both the initial values and their representation. torch.tensor([1, 2]) infers an integer dtype, while an explicit dtype=torch.float32 produces floating-point values. Choose the dtype from the operation’s contract: token IDs index a table, while learned weights participate in floating-point arithmetic.

zeros and ones initialize every element to a known value. arange(start, stop, step) generates a sequence excluding the stop value. linspace(start, stop, steps) requests a count of evenly spaced values, including both endpoints when that count exceeds one.

empty allocates a tensor without assigning useful initial values. Its contents must be written before they influence a result. It saves initialization work only when the subsequent operation overwrites every element that will be read.

Random initialization requires a distribution as well as a shape. rand samples uniformly from \([0,1)\), while randn uses a normal distribution with mean zero and standard deviation one. normal accepts other means and standard deviations. poisson draws nonnegative counts using supplied nonnegative rates. These choices model different quantities and cannot be exchanged just because their output shapes agree.

For reproducible small checks, set a random seed and record the environment. A seed controls a random-number sequence, but it does not guarantee identical results across every device or library version. The initialization discussion in Section 12.3 explains how the distribution affects learning.

The logical element count is:

\[ \operatorname{numel}(X)=\prod_i d_i \tag{23.1}\]

Here \(d_i\) is the length of axis \(i\). A tensor with shape \([2,3,4]\) contains 24 logical elements. For fixed element size, their logical byte count is:

\[ \mathrm{logical\ bytes}(X)=\operatorname{numel}(X)\cdot\mathrm{bytes\ per\ element} \tag{23.2}\]

Float32 uses four bytes per element, so this example represents \(24(4)=96\) bytes of values. The estimate excludes object metadata, allocator overhead, and unrelated tensors.

Storage is the underlying allocation that holds values. Several tensor objects can refer to the same storage. A small slice may also keep a much larger allocation alive. Consequently, adding every tensor’s logical byte count can double-count shared values or miss unused portions of retained storage.

The following example preserves the earlier \([4,8,16]\) batch. Its three axes represent examples, sequence positions, and hidden features. Inspecting those meanings alongside dtype and device establishes what later operations receive.

Code example: PyTorch tensors carry dimensions, dtype, and device metadata.

import torch

x = torch.randn(4, 8, 16, dtype=torch.float32)
print(x.shape)   # batch=4, sequence=8, hidden=16
print(x.dtype)   # float32
print(x.device)  # cpu unless moved to cuda
print(x.numel(), x.numel() * x.element_size())
assert x.numel() == 512
assert x.numel() * x.element_size() == 2048
assert not x.requires_grad

It reports 512 logical elements and 2,048 logical bytes on CPU. requires_grad is false, so this creation does not request gradient tracking. The values themselves are irrelevant to the size calculation.

For dense strided tensors, untyped_storage().nbytes() reports the size of the underlying storage. It does not establish how much additional memory that tensor required, because another tensor may own the same allocation. Device-wide allocator measurements answer a different question, revisited in Section 23.5.

23.2 Axes and broadcasting

The logical shape also determines whether an operation is valid. Before optimizing a tensor path, identify what each axis means and which axes the operation combines.

A feature vector has shape \([D]\), a batch of feature vectors \([B,D]\), and a token-ID batch \([B,T]\). Embedding lookup adds a feature axis, producing \([B,T,E]\). A language-model head then replaces the hidden width with a vocabulary axis, producing logits \([B,T,V]\).

For the matrix convention used in Chapter 5, a linear transformation is:

\[ X\in\mathbb{R}^{B\times D_{\mathrm{in}}},\quad W\in\mathbb{R}^{D_{\mathrm{in}}\times D_{\mathrm{out}}},\quad Y=XW+b\in\mathbb{R}^{B\times D_{\mathrm{out}}} \tag{23.3}\]

The input \(X\) has shape \([B,D_{\mathrm{in}}]\), and the mathematical matrix \(W\) has shape \([D_{\mathrm{in}},D_{\mathrm{out}}]\). Contracting the shared input dimension leaves \([B,D_{\mathrm{out}}]\). Thus a \(2\times3\) input and a \(3\times4\) matrix produce a \(2\times4\) result.

PyTorch nn.Linear stores a parameter \(A\) with shape \([D_{\mathrm{out}},D_{\mathrm{in}}]\). The same operation is therefore \(XA^T+b\), with \(A=W^T\). Keeping these symbols separate avoids treating one stored matrix as both orientations.

Broadcasting applies an operation across compatible axes without requiring the caller to create repeated copies of the smaller operand. Dimensions align from the right. At each aligned axis, their lengths must agree or one must be one. Missing leading axes behave as length one.

For bias \(b\) with shape \([4]\) and output shape \([2,4]\), broadcasting adds the same four bias values to both rows. It does not turn this elementwise addition into matrix multiplication. A bias of shape \([2]\) would fail this contract, despite having one value per example.

Vectorization expresses a collection of operations through tensor kernels rather than a Python loop over examples. One matrix multiplication can process the whole batch. This often reduces interpreter overhead, but a valid vectorized expression can still create large intermediate tensors.

An operation can also change its input storage. x.exp() returns elementwise exponentials in a new tensor. The trailing underscore in x.exp_() means it writes the result into x. Likewise, x.add_(b) modifies x, including values visible through any other tensor sharing that storage.

Comparisons expose a second distinction. x.gt(0) produces a Boolean mask for values greater than zero. x.gt_(0) overwrites the original tensor with zero and one in its existing dtype. It destroys the original values and does not turn a floating-point tensor into a Boolean tensor.

Code example: Comparison masks and changes to existing values

import torch

x = torch.tensor([-1., 0., 2.])
mask = x.gt(0)
assert mask.dtype == torch.bool
assert mask.tolist() == [False, False, True]
assert x.tolist() == [-1., 0., 2.]
x.gt_(0)
assert x.dtype == torch.float32 and x.tolist() == [0., 0., 1.]

a = torch.tensor([0., 1.])
b = a.exp()
assert a.tolist() == [0., 1.]
a.exp_()
assert torch.allclose(a, b)
print(mask, x, a)

The ordinary comparison preserves \([-1,0,2]\). Its in-place counterpart changes the original to \([0,0,1]\). The exponential example similarly distinguishes a retained input from overwritten values. During training, an in-place change may invalidate a value needed for backward computation. Autograd checks many such conflicts, but avoiding unnecessary mutation makes the dependency easier to inspect.

For attention, Section 17.1 establishes the head layout \([B,H,T,d_h]\). Permuting axes preserves the values’ intended relationships only when the storage interpretation follows those axes. The next section makes that interpretation explicit.

23.3 Views, strides, and copies

A transpose can exchange axes without moving every value. It changes how logical coordinates address existing storage. A view is a tensor that shares storage with another tensor, while a copy has its own allocation.

A stride is the change in storage position, measured in elements, when one coordinate increases by one. The storage offset locates the tensor’s first logical element within its underlying storage. For a two-dimensional tensor:

\[ \operatorname{element\ offset}(i,j)=o_0+i s_0+j s_1 \tag{23.4}\]

Here \(o_0\) is the storage offset and \(s_0,s_1\) are the strides. To obtain a byte offset, multiply the entire element offset by the dtype’s element size.

Consider values \([0,1,2,3,4,5]\) arranged as a \(2\times3\) matrix. Its strides are \([3,1]\) and its storage offset is zero. Coordinate \((1,2)\) reads element offset \(1(3)+2(1)=5\).

Transposing gives shape \([3,2]\) and strides \([1,3]\), while retaining the same six stored values. Its coordinate \((2,1)\) also reads offset \(2(1)+1(3)=5\). The axes changed, but the address still identifies the same value.

The second row of the original matrix has shape \([3]\) and storage offset three. Its logical size is twelve float32 bytes, yet it shares the original 24-byte storage. This is why a slice’s element count is not its full retained allocation.

Contiguous layout places values in the expected adjacent order for a specified memory format. With the usual row-major format, the last axis advances by one element. The transposed matrix above is not contiguous in that format.

view() changes shape only when the existing strides support the requested grouping. Contiguity is sufficient for many common reshapes, but not required for every possible view. Calling view() on the transpose to flatten it fails because its logical traversal cannot use one consistent stride.

reshape() returns a view when possible and otherwise copies. contiguous() returns the original tensor when it already has the requested layout, or copies it into that layout. clone() explicitly creates a copy. Code that depends on shared storage must not assume that every reshape() shares values.

The following trace checks shape, stride, offsets, and storage sharing. It also shows a noncontiguous slice whose evenly spaced values can still form a one-dimensional view.

Code example: Shared storage, transpose, reshape and an evenly strided view

import torch

x = torch.arange(6, dtype=torch.float32).reshape(2, 3)
t = x.T
row = x[1]
assert x.stride() == (3, 1) and t.stride() == (1, 3)
assert row.storage_offset() == 3
assert row.numel() * row.element_size() == 12
assert row.untyped_storage().nbytes() == 24
assert x.untyped_storage().data_ptr() == t.untyped_storage().data_ptr()
assert x[1, 2].item() == t[2, 1].item() == 5
try:
    t.view(-1)
except RuntimeError:
    print("The transpose cannot use a flat view")
else:
    raise AssertionError("Expected an incompatible view")
flat_copy = t.reshape(-1)
assert flat_copy.tolist() == [0, 3, 1, 4, 2, 5]
assert flat_copy.untyped_storage().data_ptr() != x.untyped_storage().data_ptr()
assert x.contiguous() is x
assert t.contiguous().is_contiguous()

spaced = torch.arange(12).reshape(3, 4)[:, ::2]
flat_view = spaced.view(-1)
assert not spaced.is_contiguous()
assert flat_view.stride() == (2,)
assert flat_view.tolist() == [0, 2, 4, 6, 8, 10]
assert flat_view.untyped_storage().data_ptr() == spaced.untyped_storage().data_ptr()
print(x.shape, t.shape, row.storage_offset(), flat_view.stride())

The transpose shares storage, but its flattened reshape uses a copy. The final slice retains every second column of a \(3\times4\) matrix. Its offsets are \(0,2,4,6,8,10\), so a flat view with stride two is valid.

Sharing can extend beyond PyTorch objects. torch.from_numpy uses the same CPU memory as a supported NumPy array and retains its numerical dtype. Changing either object therefore changes the other’s values. By contrast, torch.tensor(array) copies the input values.

For a supported CPU tensor without gradient tracking, .numpy() normally exposes shared memory too. detach().cpu().numpy() disconnects the graph and transfers to CPU when needed, but does not promise a separate copy if the tensor is already on CPU. Add .copy() to obtain an independent NumPy array when later mutation must be isolated.

Code example: NumPy sharing and explicit copies

import numpy as np
import torch

array = np.array([1., 2., 3.], dtype=np.float64)
shared = torch.from_numpy(array)
copied = torch.tensor(array)
array[0] = 9.
assert shared.dtype == torch.float64
assert shared[0].item() == 9. and copied[0].item() == 1.
roundtrip = shared.numpy()
roundtrip[1] = 8.
assert shared[1].item() == 8.
isolated = shared.detach().cpu().numpy().copy()
isolated[2] = 7.
assert shared[2].item() == 3.
scalar = torch.tensor(4.)
assert scalar.shape == torch.Size([]) and scalar.item() == 4.
print(shared, copied, isolated)

The first mutation changes both the NumPy array and its shared tensor, while the copied tensor retains the old values. The conversion back to a NumPy array shares the tensor’s storage. A final NumPy copy isolates subsequent changes. Never change data needed by an unfinished backward computation through a shared NumPy view: those writes can bypass PyTorch’s normal mutation checks.

A tensor with one value can be scalar-shaped, with shape \([]\), or retain an axis, such as \([1]\). .item() extracts its value as a Python scalar in either case. It requires exactly one element and removes the tensor interface, so it is useful for logging rather than differentiable computation.

Copying a transpose into contiguous order can help a later kernel, but it adds allocation and transfer work. Measure the complete operation sequence before deciding that the copy improves performance. A kernel may already support the original strides efficiently.

23.4 Training state and tensor lifetimes

Storage sharing explains individual tensors, while memory exhaustion often depends on how many tensors remain alive together. Training retains parameters, gradients, saved activations, and optimizer state for different purposes.

The forward and backward sequence is taught in Chapter 10. Here its consequence is lifetime: backward computation may need values created during the forward pass. Autograd retains the information necessary for those derivatives until the graph is released or deliberately retained.

A leaf tensor is not the result of an operation recorded in the current autograd graph. A trainable leaf parameter can have requires_grad=True and grad_fn=None. Intermediate tensors produced by recorded differentiable operations usually carry a grad_fn describing their backward operation.

detach() creates a tensor without that autograd connection, but it shares storage with the original. It does not release every reference to the graph and does not create an independent value copy. Use detach().clone() when both disconnection and separate storage are required.

A dense gradient buffer has the same logical shape as its parameter:

\[ \operatorname{shape}(G_{\theta})=\operatorname{shape}(\theta) \tag{23.5}\]

Here \(G_\theta\) stores the derivatives of the scalar loss with respect to entries of \(\theta\). A linear weight with shape \([4,3]\) therefore receives a dense .grad tensor with shape $[4,3]`. Some operations support sparse gradients, whose storage is different despite the same logical parameter shape.

The optimizer mechanics in Chapter 11 determine which additional state persists between updates. Adam normally maintains two moment arrays for each updated parameter:

\[ \operatorname{state}_{\mathrm{Adam}}(\theta)=\{m_{\theta},v_{\theta}\},\quad\operatorname{shape}(m_{\theta})=\operatorname{shape}(v_{\theta})=\operatorname{shape}(\theta) \tag{23.6}\]

The first moment \(m_\theta\) and second moment \(v_\theta\) each have the parameter’s shape. Implementations also keep small step counters and may allocate temporary update buffers.

One million float32 parameters occupy 4 MB. Float32 gradients add 4 MB, and two float32 Adam moments add 8 MB. These four arrays alone total 16 MB, using decimal megabytes.

This is a component estimate, not a complete training peak. Saved activations and temporary tensors add memory. Some mixed-precision arrangements also retain a higher-precision parameter copy. Quantization and sharding change the accounting, so inspect the actual implementation.

Inference usually omits gradients and optimizer state but still needs parameters, active intermediate values, and request state such as the KV cache from Chapter 21. Calling model.eval() changes modules’ evaluation behavior. It does not by itself disable autograd tracking. A suitable no_grad() or inference_mode() context controls that separate concern.

Saving an output tensor in a Python list can also retain its graph during training. For a scalar log, storing loss.item() avoids keeping the loss tensor. Such extraction may synchronize device execution, so logging frequency can affect timing.

23.5 Devices, precision, and measurement

The same tensor expression can run on CPU or GPU, but its operands need compatible placement. Moving only a model or only its batch leaves the linear operation with mismatched devices.

A CUDA device is a GPU execution and memory target exposed by PyTorch, commonly cuda:0. The following example moves the model and constructs its input on the selected device. CPU remains a valid fallback for checking the interface.

Code example: Moving a model and its batch to one device

import torch
import torch.nn as nn

# The same code runs on a GPU when CUDA is available and on CPU otherwise.
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = nn.Linear(3, 2).to(device)
features = torch.tensor([[1.0, 0.0, -1.0]], device=device)

logits = model(features)
assert logits.device == features.device == next(model.parameters()).device
print(device, logits.shape)
assert logits.shape == (1, 2)

The result has shape \([1,2]\) and shares its device with the model and features. A CPU run checks placement logic. It does not measure GPU throughput or exercise CUDA kernels.

to(device) returns a tensor on the requested device, potentially allocating and copying when placement changes. It may return the original object when no conversion is required. Moving a CUDA tensor to a CPU-only NumPy path also requires an explicit transfer, with gradient tracking handled appropriately.

Mixed precision uses different floating-point dtypes for different operations or state. Lower-precision matrix operations can reduce memory traffic and use faster hardware paths. Sensitive reductions and optimizer state may retain higher precision. The mathematical operation remains the same, but rounding and representable range can change its numerical result.

A floating-point format divides its bits among a sign, an exponent and a fraction. The exponent mainly determines the range of magnitudes. The fraction determines how closely nearby values can be represented within that range.

Format | Sign bits | Exponent bits | Fraction bits | Bytes per value | | — | — | — | — | — | | float32 | 1 | 8 | 23 | 4 | | float16 | 1 | 5 | 10 | 2 | | bfloat16 | 1 | 8 | 7 | 2 |

Float16 and bfloat16 therefore have the same storage width but different numerical behavior. Bfloat16 retains float32’s exponent width while representing fewer nearby values. Around 1, adjacent representable values are spaced by approximately 0.000977 in float16 and 0.0078125 in bfloat16. These gaps grow at larger magnitudes.

Underflow loses values too small for the format, potentially rounding them to zero. Overflow exceeds its finite range. Gradient scaling temporarily multiplies the loss to reduce underflow during the backward calculation, then removes that scale before the optimizer update. It cannot repair every source of numerical instability.

Check loss values, gradients, and evaluation behavior against an appropriate reference. Float16 training may require gradient scaling to avoid underflow. The choice of dtype should follow the hardware, operation and training setup.

Data parallelism replicates a model across devices that process different local batches. An all-reduce combines corresponding gradients across replicas so their optimizer updates remain consistent. Communication and synchronization add costs, and changing total batch size can change optimization behavior.

The memory question also determines the measurement. torch.cuda.memory_allocated() counts tensor memory managed by the CUDA allocator. memory_reserved() includes memory the allocator retains for reuse. Neither is identical to the sum of every live tensor’s logical size or every byte shown by a system-level GPU monitor.

GPU kernels execute asynchronously relative to the host in many operations. A host timer around a launch can therefore measure dispatch instead of completion. Use CUDA events or explicit synchronization around a bounded benchmark, include warmup, and specify whether transfers are included.

Resetting peak-memory statistics before a representative operation helps isolate its peak. Report the batch, sequence length, dtype, and whether the run trains or serves. Those conditions connect the measurement to the tensor lifetimes and layouts studied here.

Chapter checkpoint

A tensor slice has twelve logical bytes but its storage reports 24 bytes. Is either measurement necessarily wrong?

Feedback: No. The slice can expose three float32 elements while retaining a six-element shared allocation. Neither measurement alone establishes its additional device allocation.

A transpose becomes slower after adding contiguous(), although the following matrix kernel becomes faster. What should the comparison include?

Feedback: Include allocation and copying in the complete path. The kernel’s improvement must repay those costs under the actual reuse pattern.

An inference run calls eval() but still retains a growing graph. Which separate controls and references should you inspect?

Feedback: Check gradient-tracking context and stored output references. Evaluation mode alone does not disable autograd, and retained tensors can keep computation history alive.
